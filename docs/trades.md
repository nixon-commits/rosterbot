# Trades

Split out of `CLAUDE.md` (2026-08-19) to keep the root file under its char budget. Internal
implementation detail for trade valuation and the dashboard's Trades tab — read before touching
`internal/tradevalue`, `internal/tradeboard`, `cmd/trades.go`, `internal/lineupapi/trades.go`,
`internal/lineupapi/reports.go`, or `web/dashboard/trades.js`.

**`internal/tradevalue`** — the pure n-sided trade-valuation leaf (imports only `fmt`, `math`, `sort`, `internal/hkb`). `Side.Raw()` is the plain HKB sum; `Side.Adjusted()` sorts assets descending and contributes the k-th at `Value × (1 − PackageDiscount(k, leagueSize))`. `Evaluate([]Side)` returns a `Verdict` under a four-branch rule: any unpriced asset → `incomplete`; both methods exactly level → `dead-even`; the methods naming different leaders, *or* exactly one of them coming out level → `too-close`; otherwise `favors`, with both percentages reported. **`leader()` returns an empty team for a method that came out exactly level** — a method that ties has not named a winner — and that is what makes the last two branches honest (rosterbot-h688). Before it, a symmetric 1-for-1 swap rendered as `favors <whoever sorted first> (+0%)`: the sort's lexical tiebreak escaping as an answer, the rosterbot-hx5 shape of a statistic answering confidently on no input. Worse, the raw-tie-but-adjusted-separates case was decided by **luck** — it read `too-close` or `favors` depending on whether the tiebreak happened to coincide with the adjusted winner. `dead-even` is deliberately neither of the existing states: `too-close` means the two methods *disagree*, which a tie is not, and reusing it would break the documented invariant that `RawLeader`/`AdjLeader` differ there; `incomplete` means an asset could not be priced, which would blame data that priced fine. It also subsumes the all-sides-worth-zero case by the same route rather than by a guard of its own. `internal/dynasty.GradeTrade` gained the mirrored `TradeDeadEven` for the same reason, and it is *not* folded into that package's pre-existing zero guard: `football.js` renders `incomplete` with `UnpricedAssets == 0` as "No value in this format", which is a true statement about a pick-for-pick redraft trade and a false one about a 500-vs-500 swap. One renderer, `tradevalue.MethodReading`, is shared by the Pushover body and the `trades` console output so the two cannot word the same trade differently. **Withholding the call on disagreement is the point of the package, not caution** — on the live 2-for-1 that motivated it (Gage Jump 1391 + Emmet Sheehan 1234 for Kyle Harrison 2292) the raw sum favors you by 333 (+12.7%) and the discounted sum (1391 + 0.62×1234 = 2156) favors them. A single number would have been confidently backwards.

**The package discount is MEASURED (rosterbot-492, 2026-09-04), and measuring it did not promote it to the headline.** It was `PackageDecay = 0.70`, a geometric ladder fitted to *one* HKB screenshot (589+540+366 → 1144, ~0.2% residual) in the style of `certaintyMargin` in `internal/optimizer/gs_budget.go`. Nineteen one-sided packages were then typed into HKB's public calculator in a single sitting and captured in `internal/tradevalue/testdata/hkb_calculator_2026-09-04.csv` — package sizes 1 through 24, values from 10,000 down to 10, players, draft picks and mixes, swept across every league size their picker offers (8–30). The real ladder is **arithmetic in the discount, not geometric in the retained share**: the k-th best asset (0-indexed) is discounted by `min(0.78, max(0, 0.36 − (leagueSize−12)×0.01) + 0.02k)`, and the best asset is never discounted at all. At 12 teams the retained shares run 1.00, 0.62, 0.60, 0.58, … where the old model ran 1.00, 0.70, 0.49, 0.34. It reproduces every captured row **exactly** — HKB floors its deduction, so their rendered total is this figure rounded up, and the test pins that as `total − adjusted ∈ [0,1)` rather than as a percentage tolerance.

That is also the honest account of what one data point buys: the old curve still passes through the original trio (redrawn 2026-09-04 as 590/540/366 → 1145, which it hits within 2.3) and is out by **38%** on a 24-asset package and 22% on eight picks — in *both* directions depending on package size, so no rescale of 0.70 would have fixed it. Two terms are worth naming. The `0.78` ceiling **is** observed (row 14 is 24 assets deep). The `max(0, …)` floor on the base is **not** — it needs a 48-team league and the picker stops at 30 — so it is carried because HKB's client-side code carries it, and is flagged in the source rather than quietly asserted. `DefaultLeagueSize = 12` is HKB's own calculator default, which is what makes an adjusted figure here comparable to the number a league mate reads off their screen; `Side.AdjustedForLeague` exists for a caller that knows better.

**What was measured is HKB's penalty schedule, not this league's roster economics** — their tooltip calls it "a deduction when combining lower value players to acquire a high value player", i.e. an editorial judgement keyed to a league size we supply as a constant. Knowing it precisely settles what HKB would print; it does not settle which team won the trade. So `too-close` stays exactly as it was, and its justification changed rather than weakened: the finding is no longer "the constant is fitted to one point" but "which side won depends entirely on whether you charge the discount".

**HKB nets the two sides' deductions before display and `Side.Adjusted()` deliberately does not.** Verified live the same day (`testdata/hkb_netting_2026-09-04.md`): with both sides filled, only the side carrying the larger deduction is charged, and only for the excess. That shifts both sides by the same amount, so it can change neither the leader nor the gap — un-netted `16344.36 − 16049.96 = 294.4`, netted and floored `20053 − 19758 = 295` — and a function of the *opposing* side has no signature to live in on a per-side method. Percent difference is symmetric — `|a-b| / mean(a,b)` — which reproduces HKB's own reported 91.6%. `NewAsset("")` yields an unpriced `Draft pick (unidentified)`: Fantrax sends pick rows with an empty `playerName` (`internal/fantrax/client.go` appends them unconditionally, so an unresolved `scorerId` is a blank row, not a dropped one).

**Draft-pick identity recovery (rosterbot-uc3, closed 2026-08-11).** The empty `playerName` was never the whole story — the raw TRADE-view row also carries a `draftPickDisplayParts` field (`{year, roundInfo}`, both inline-HTML display strings) that the upstream parser discarded entirely; the go-fantrax fork now parses it into `Transaction.{IsDraftPick, DraftPickYear, DraftPickRound, DraftPickNumber, DraftPickOriginalTeam}`. Fantrax renders `roundInfo` two ways depending on whether the draft order is settled yet: `"Round N (Team)"` while the pick is still tied to that team's future standing, or `"Round N Pick M"` once resolved — the parenthetical team is the pick's *original* owner, not this trade's from/to, since a pick can be re-traded before it's ever drafted. `NewDraftPickAsset(year, round, pickNumber, originalTeam, players)` builds the priced `Asset`: HKB prices picks generically by projected slot (Early/Mid/Late per round: 18 assets, values 45–1419) rather than by team, and the recovered identity has no team standing to pick one of the three tiers over another, so `hkb.PickAverage` means whichever tiers HKB currently lists for that year+round and the result is flagged `Estimated` — a deliberately coarser number than a direct name match, in the same "disagreement over false precision" spirit in which `Evaluate` withholds a verdict when its two pricing methods diverge. A resolved pick (`DraftPickNumber > 0`) came from a draft that has already happened, which also means HKB has stopped listing it as upcoming — `PickAverage` reports zero tiers and the asset stays unpriced by construction, exactly as an unidentified pick did before this. `NewAsset` itself is unchanged and still used wherever identity truly isn't available (a bare empty-name row, or the pending-offer path via `internal/tradeboard`, which this ticket left untouched since no live pending trade existed to confirm `GetLeagueHomeInfoRaw` encodes pick identity the same way).

**The pending-offer side of that gap is still open (rosterbot-1o5).** `tradeboard.BuildOffers` still falls back to `NewAsset`'s `"Draft pick (unidentified)"` for any pick in a *live* offer, because `internal/fantrax.PendingTrade` (parsed by `fetchPendingTrades` from `GetLeagueHomeInfoRaw`'s `pendingTransactions.scorerMap`, keyed by `scorerId`) carries only `PlayerName`/`Position`/`FromTeam`/`ToTeam`/`TradeID` — a different Fantrax response shape than the TRADE-view history endpoint the paragraph above describes, and one that has never been captured with a pick in it. `internal/fantrax/diag_pending_trades_test.go` (`//go:build diag`, never runs in CI) is the capture harness: point it at a live pending offer that includes a pick and it authenticates, calls `GetLeagueHomeInfoRaw` directly (bypassing `GetPendingTrades`' cache), and reports both a per-offer summary and any JSON keys that look like pick identity (via the hermetically-tested `scanForDraftPickKeys`, needles `draftpick`/`pick`/`round`/`displayparts`). The one command to run when such an offer exists:

```
DIAG_PENDING_TRADES=1 go test -tags diag -run TestDiagPendingTradesDraftPickIdentity -v ./internal/fantrax/
```

(add `DIAG_PENDING_OUT=/path/to/file.json` to save the raw payload). A hit extends `PendingTrade` with the recovered fields and wires `tradeboard.BuildOffers` to call `tradevalue.NewDraftPickAsset` for pick rows, the same way `internal/transactions.buildTrade` does for executed trades; a clean miss (checked by hand, not just by the needle list) closes rosterbot-1o5 as "the pending view genuinely omits pick identity."

Measured over the league's 25 executed trade groups (reproduced exactly by an independent Python implementation per rosterbot-aei), pick-tier averaging moved several previously pick-blocked `incomplete` groups to `favors`/`too-close` (those carrying a still-upcoming, priceable pick); the rest carried an already-resolved pick HKB no longer lists, so identity recovery named them without pricing them. The corpus is a live cache file that grows with every trade, so `corpus_test.go` asserts those exact counts only while the group count matches the baseline and otherwise falls back to the corpus-independent invariants (no HKB name-miss, non-degenerate verdict, pick-blocked incompletes only) — a gate that goes red on every league trade is one you learn to bump without reading. `internal/transactions` shares this package rather than carrying its own `side.Total += tp.Value`, so the Pushover report and the dashboard can never name opposite winners; the migration also turned `Trade.Sides` from a `[2]TradeSide` — which silently dropped every side past the second and was filled in random map order — into a name-sorted slice.

**`internal/tradeboard`** — the two artifacts behind the dashboard's Trades tab, plus the durable offer log. It **deliberately does not import `internal/fantrax`** (that would drag chromedp in); callers map their own rows onto `OfferInput`, the same constraint that forces `internal/opsalert` to redeclare its ledger fields. `BuildOffers` groups by `TradeID`, sides by receiving team, and prices each through `tradevalue`. `BuildValuesTable` joins every rostered player onto HKB by `playername.Normalize` and appends HKB's 18 pick assets as a league-wide reference list — picks cannot be attributed to a team because Fantrax never says who holds which. `BuildImpact` replays an offer against the `teamvalue.Row` set and reports my five value dimensions (Total/Hitters/Pitchers/MLB/Minors) before and after, with league rank in each; `addToLeaf` mirrors `teamvalue.Aggregate`'s bucketing exactly. **It returns `(nil, reason)`, never a partial answer** — and the reason is returned rather than swallowed because *pricing and placement are different requirements*: pricing needs only an HKB entry, placing a player in a value leaf needs their current Fantrax roster row. An offer can therefore be fully priced and still have no impact, observed 2026-08-09 with Heriberto Hernandez, who priced cleanly and belonged to no team. Without the reason the tab would quietly omit the section and look like it had decided not to bother. The **offer log** (`log.go`, `dt=YYYY-MM-DD/offers.ndjson` over `internal/ndjsonstore`) is the only record that a declined offer ever existed — Fantrax keeps none, hence `NoBackfill: true` — so it is written even on an empty window, both to advance outcomes and to keep the partition present rather than leaving a hole the Infra gap scan would flag. `InferOutcome` matches a vanished offer's `(player, To)` multiset against the executed feed and labels it `accepted` or **`not-executed`, never `rejected`**: withdrawn, expired and declined are indistinguishable in the data.

**Trades producers and cadence.** Two artifacts on two schedules, because the time-sensitive half is cheap and the expensive half cannot be fresher than HKB's own 8h TTL. `cmd/optimize.go` calls `captureTradeOffers` **hourly** after `lineuprun.Run` — one small league-home call, notably *not* the 10.7 MB player pool — writing `trades/current.json` and appending the log. `cmd/team-values.go` writes `tradevalues/values.json` **daily**, since that job already holds the pool, the HKB rankings and the team names. Both writes **soft-fail**, on the precedent of `cmd/grade.go`'s lineup gaps: a trades hiccup must never take down the hourly lineup apply or the irreplaceable Team Value Store write. The values table is built *before* the dry-run gate so `--dry-run` exercises everything but the write — a producer whose output only materializes in production can only be tested in production. **The pool's position string comes from `PosShortNames`, not `MultiPositions`**: the latter is populated only for players eligible at more than one *named* position, so most single-position players (e.g. Juan Soto, Paul Skenes) come back empty and the Pos column shipped blank for the majority of rows. Deriving from the `Positions` IDs is worse — everyone carries the UT flex slot and Fantrax hides it except where it is a player's only hitting eligibility. `positionDisplay` strips the markup upstream documents on that field (`<b>UT</b>,SP`) because the string lands in a durable JSON artifact.

**Trades API and tab.** `GET /v1/trades` and `GET /v1/trades/values` (`internal/lineupapi/trades.go`) pass the stored bytes through untouched, the same contract as `GET /v1/runs/{id}/progress`. They are on `/v1/*` and therefore passkey-gated **on purpose**: `report/*` is world-readable through CloudFront's default behavior, and an open offer is not something to publish before deciding on it. No new S3 adapter was needed — `s3lineup.Store` is already generic over its prefix despite the package name. The SPA's `trades.js` builds every row with `createElement`/`textContent` for the reason `views.js` documents. It renders **four** verdict states, not two: "too close" (the models disagree) and "cannot be priced" (an asset has no price at all) are different kinds of not-knowing and the tab says which.

**Private dashboard reports (`GET /v1/reports/{name}`, rosterbot-crq.3).** The Trades reasoning above generalized: three more of `projection-site`'s artifacts were the operator's own performance sitting on an unauthenticated URL, so they moved. `model` (projection accuracy), `gap` (points left on the bench) and `views` (recap readership) now live in `STATE_BUCKET`'s `reports/` prefix — which no CloudFront distribution fronts — and are served by `internal/lineupapi/reports.go` through the same `serveBlob` passthrough as Trades. `value.json`, `football.json` and `football-trades.json` stay on the public `report/` prefix: league-wide standings and completed trades every manager can already read off Fantrax and Sleeper.

Three choices are load-bearing:
- **The bytes moved, rather than a CloudFront behavior being added to block them.** Blocking `report/{gap,model,views}.json` publicly would leave the private data in a bucket a distribution serves, one behavior edit away from re-exposure — and CloudFront path patterns have no "deny" primitive, so it would have meant an allowlist that a future filename silently falls outside of. **A path that is not served cannot be accidentally re-exposed.** The cost was a producer change; there was no `statePairs` change, because `reports/` is written per-key through `statestore.ReportsStore()` like `trades/`, not bulk-synced from a directory.
- **`{name}` is an allowlist (`reportNames`), not an echoed key.** Go's `ServeMux` already refuses a `/` inside a path segment, so this is the second lock; what it actually buys is that the route can never be widened into a general reader of the `reports/` prefix by adding an object to it.
- **One prefix for all three, unlike the two Trades artifacts.** The rule stated in `layout.go` is producer-and-cadence: Trades split because an hourly job and a daily job would otherwise be judged by whichever object is newest. These three share one producer and one schedule, so one age reading is honest. The residual gap — one of the three soft-failing while the others succeed does not move the Infra row — is recorded in the layout comment rather than papered over.

**Cutover is automatic and worth verifying.** `publishSite` mirrors `./report` with `--delete` scoped to that prefix, and `./report` no longer contains the three files, so the next `ProjectionSite` run deletes `report/{model,gap,views}.json` as orphans and invalidates the distribution. Until that run lands the stale public copies are still readable — so the post-deploy check is an unauthenticated `curl` of the three old URLs expecting 403/404, not merely a working dashboard.
