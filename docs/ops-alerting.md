# Ops Alerting: opsalert, the heartbeat, build drift, and the fan-out gate

Split out of `CLAUDE.md` (2026-09-07) to keep the root file under its char budget. Internal implementation detail for job-failure alerting — read before touching `internal/opsalert`,
`opsnotify/`, `lambda/dispatch`, `JOB_SCHEDULES` in `infra/infra.go`, or the run ledger's fields.

**`internal/opsalert`** — decides whether a finished job run is worth waking an operator, and renders the message. A **stdlib-only leaf**: its only consumer is the `opsnotify` Lambda, and `internal/lineupapi` (where the run ledger's wire types live) transitively pulls `internal/fantrax` and therefore chromedp, so `opsalert.Record` redeclares the eight ledger fields it needs and `internal/lineupapi/opsalert_contract_test.go` (`package lineupapi_test`, so it can import both without `opsalert` importing `lineupapi`) marshals a real `lineupapi.RunDetail` into it to guard the duplication. `Streak(recs, command, userID)` reads newest-first ledger records and returns one of four verdicts: `Started` (first failure after a success), `Escalated` (the `EscalateAt`=3rd consecutive failure, matched on `==` so an eleven-failure outage escalates exactly once), `Recovered` (first success after failures), or `None`. **The whole decision is derived from the append-only ledger**, which is what removes the counter object and the cooldown timer a naive design needs — streak transitions deduplicate themselves. `RUNNING` records are skipped: they are the start-of-run write that the terminal write later overwrites at the same key, so an in-flight sibling job must not break a streak. The message body quotes the **last non-empty line** of the record's `log_tail`, capped at 300 chars *before* append because `SendPushover` truncates at 1024 silently — for the 2026-07-01 outage that line is the `STALE_CLIENT` error itself, which is the difference between "something broke" and a diagnosis.

**Heartbeat: the alert Streak structurally cannot produce (rosterbot-ys8).** `Streak` is reactive — an ECS task has to *stop* for the notifier to hear anything — so a job that never launches (disabled EventBridge rule, broken cron, unreachable cluster) emits no event, writes no ledger record, and produces perfect silence, which is indistinguishable from perfect health. `Overdue(recs, scheds, now)` inverts the direction: it asserts on a timer that every job has a run recent enough to be alive. Three rules are load-bearing:
- **Any status counts as "it launched"**, including `RUNNING` and `FAILED`. The question is strictly whether the job started; whether it then succeeded is `Streak`'s, and treating a failed run as a missed one would double-report every ordinary outage.
- **The lookback is bounded by *time*, not count** (`Horizon` = 2× the longest declared cadence; `ledgerReader.since` walks back to it and stops). A fixed record count is unsound here: a high-frequency job's daily record volume would push a low-frequency job's perfectly healthy run out of any small fixed window, reporting a live job as never having run.
- **Deduplication compares a token, not a key** (`MarkerKey` is per *(job, tenant)*; `AlertToken`/`NeedsAlert` compare the last-run id stored under it). A per-run key looks self-deduplicating and is not: every long outage eventually pushes its last run past the horizon, at which point the key moves and the same outage alerts again — once per horizon, forever (caught by a test, not by inspection).

The cadence table itself lives in `infra/infra.go` beside the crons it describes and reaches the Lambda through the `JOB_SCHEDULES` env var, because a tolerance restated in Go would drift from its schedule silently — surfacing only as an alert that never fires. The command string is the join key across all three sides: EventBridge passes it as the container override, `entrypoint.sh` joins argv with spaces into `run-ledger --command`, and `opsalert` matches that exact string.

**Both decisions key on `(command, user_id)`, not on the command alone (rosterbot-crq.1).** Under the per-tenant fan-out of `rosterbot-crq`, N tenants run the *same command string* into the one ledger, and a command-only key inverts both functions silently: `Streak` walks newest-first where a SUCCESS breaks the streak, so a tenant failing *every* hour grades healthy on its neighbours' successes; `Overdue` keeps the newest run per command, so "Lineup ran recently" is true for everyone the moment any one tenant runs — the exact rosterbot-ys8 blindness one level down. `Record.UserID`/`Run.UserID` (`user_id`, omitempty) carries it; **empty is an ordinary tenant value, not a wildcard**, so the entire pre-fan-out ledger keeps grading as the single tenant it describes. Consequences: which tenants `Overdue` asserts on comes from the ledger, not `Schedule` (a stdlib-only leaf can't enumerate users, so a tenant that never ran even once needs the identity store to detect it, while one that ran and stopped is always caught); the heartbeat's `MarkerKey` gains the tenant but the untagged key stays byte-identical, so existing S3 markers keep deduplicating across the deploy; and the task path's `dedupeKey` needs no tenant, since fan-out already runs one ECS task per tenant per job — it takes the tenant from the stopped run's own terminal ledger record, since the ECS event carries none.

**A `connect` exit code alone cannot say what `Streak` needs to know (rosterbot-cnn9).** `cmd/connect.go`'s routeTenant path exits 0 on a credentials/team fault specifically so this package does not page the operator, which makes that SUCCESS row indistinguishable from a real recovery — and under a Fantrax outage that alternates with tenant faults, every such row broke the failure streak and `EscalateAt` was never reached. The fix rides on the ledger record rather than the connection record `lineupapi.Run.Connect` joins in at HTTP read time, because opsalert cannot import lineupapi at all (the chromedp weight this whole leaf exists to avoid); `Record.Outcome` mirrors `lineupapi.Run.Outcome`, written via `RUN_OUTCOME_FILE` and read back by `run-ledger --outcome`. `Streak` reads a SUCCESS carrying `OutcomeTenantActionable` as evidence about nothing: None when it is the newest record (not a false Recovered, and not a silent skip either, which would re-report the older streak), and dropped from history entirely when older, so it neither breaks a failure streak nor extends one.

**Build drift: the question neither `Streak` nor `Overdue` asks (rosterbot-7p1i).** Both of those are about **runs**, and a run executing a stale image satisfies them perfectly — the ledger records a healthy SUCCEEDED job and the heartbeat sees a fresh launch, while the code doing the work is days behind main. They answer "did the job run", never "is it the right image". The gap is not hypothetical: CodeBuild's `ConcurrentBuildLimit` **throttles** an excess build rather than queueing it, and rejects it at the webhook *before a build record exists*, so a merge landing inside another build's window produces no build, no outcome, no event and nothing red anywhere. It dropped two deploys in two days (6056658, bb1cc1e); the only evidence in the entire system was an HTTP 400 in a GitHub webhook delivery log.

`opsalert.Check` compares main's HEAD against the newest commit that actually built, and `BuildDriftRule` runs it every two hours. Four properties are load-bearing:
- **The baseline is read from CodeBuild, not accumulated from the build-outcome events this same Lambda already receives.** A check derived from the event stream it is auditing cannot see that stream fail — the same reason `internal/roster`'s `CheckILStarters` joins against MLB's probables instead of asking Fantrax whether Fantrax believes a player is injured.
- **`AlertToken` is the BUILT sha, not the head sha**, and that choice is the entire dedup. The built sha is precisely the value that does *not* move while the trigger is broken — main keeps advancing, the last good build does not — so one outage records one token and every later tick recognises it. Keying on the head would alert once per merge for as long as the outage lasted. `NeedsAlert`'s middle case mirrors `Missed.NeedsAlert`: once alerted, losing sight of the baseline must not read as a fresh outage forever.
- **Blindness is never a finding.** An unreadable GitHub or CodeBuild, and a head commit that cannot be *dated*, all return "no finding" rather than an alert — a check that cries wolf on healthy deploys gets muted, which costs more than the narrow gap. `driftGrace` (30 m) exists for the same reason: a merge younger than a build legitimately has no build yet. But **an empty baseline IS a finding** — a project that has never built successfully is drifting by any definition.
- **`GITHUB_REPO`/`BUILD_PROJECT` are set by the CDK from the same literals that declare the webhook source and the project**, the `JOB_SCHEDULES` principle one rule over: a checker that restated its target's coordinates could drift from the thing it checks. IAM is two read actions scoped to the project ARN; the check never starts a build. Verify live with `DIAG_BUILD_PROJECT=… go test -tags diag -run TestDiagBuildDrift ./` in `opsnotify/`.

**The `-1` on `ConcurrentBuildLimit` is an assertion, not a value anyone wants.** The limit was set to 1 and reverted the same day (rosterbot-ill) by *deleting the line* — and **the revert never took effect**. CloudFormation does not clear a CodeBuild property you stop sending; AWS states the rule on `CfnProject` ("to unset or remove a project value via CFN, explicitly provide the attribute"). Measured 2026-08-20, six days and ~68 deploys later: the deployed template carried no `ConcurrentBuildLimit` while the live project still reported `1`. So an omitted property is not an assertion that it is unset — it is silence, and the resource keeps whatever it had. `-1` is the API's remove-the-limit sentinel (the field reads back *absent*) and the CFN schema puts no minimum on it. **Anywhere this repo "removes" a property to change behaviour, the claim is unverified until the live resource is read, not the template.**

**Alert deduplication across deliveries (rosterbot-chs).** EventBridge can deliver one event more than once and async-invoke retries on a returned error; since the verdict is a pure function of a ledger that does not move between deliveries, a repeat recomputes the identical alert and pushes it again. `opsnotify/marker.go` records sent alerts under the `opsalert/` S3 prefix (its own prefix, not `notifications/` — that one is the user-facing feed the dashboard serves). Two invariants: the order is **check → send → mark**, never claim-then-send, because a claim taken before sending must be released on failure and a failed release leaves a permanent suppression — trading a duplicate alert for a missing one; and **every marker-store failure degrades to a duplicate, never to silence**. The task path keys on the **task id alone, not id+`detail.version`** — AWS documents version for exactly this, but ECS can emit several distinct STOPPED events for one task as container state settles, and those are not duplicate deliveries, so version would let each through even though they describe one dead run. Version is written into the marker body instead, where it dates the delivery that won without weakening the key. The prefix expires on a 30-day lifecycle rule, far past EventBridge's retry horizon.

**Tenant fan-out gate (rosterbot-2twx, 2026-08-17).** `lambda/dispatch` launches a per-tenant job only for tenants whose Fantrax connection is `Usable()` (`ConnVerified`) — a pre-flight of the refusal every launched task applies anyway (`AuthorizeRun`). Without it, minting an invite immediately enrolled the tenant in the hourly fan-out (invite creates the user `active` before they've clicked the link), so every job failed at `tenantcreds` and paged the operator per (command, tenant) — a page-storm beginning the moment a tester was invited. Three rules are load-bearing: the store is **required, not optional** (`dispatch` errors on a nil `conns` — an optional gate silently admitting everyone is the fallback-is-a-valid-value shape); a connection-**read failure launches** (fail open — the task's own `AuthorizeRun` is the authority and fails loudly, where a Dynamo blip silently skipping every tenant is the invisible direction); and **`publishRoster` carries only the launchable tenants**, because the roster feeds `opsalert.Overdue`'s never-ran discovery and publishing every active tenant would re-page for exactly the never-connected testers the gate just silenced. A previously-running tenant whose connection breaks still gets one Overdue alert (their old runs age past the horizon), which is the intended "this tenant went dark" signal.
