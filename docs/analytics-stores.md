# Analytics & Reporting Stores

Split out of `CLAUDE.md` (2026-08-19) to keep the root file under its char budget. Internal
implementation detail for the model-performance and dynasty-value pipeline — read before
touching `internal/ndjsonstore`, `internal/analysis`, `internal/report`, `internal/teamvalue`,
`internal/valuereport`, or `internal/lineupgap`.

**`internal/ndjsonstore`** — shared plumbing for the durable, date-partitioned NDJSON stores (`internal/analysis` and `internal/teamvalue`). Generic over the row type (`Marshal[T]`/`Unmarshal[T]`/`Write[T]`/`ReadAll[T]`) over a byte-level **`Store`** seam (`Put`/`Get`/`List`), mirroring how `cache.FileCache[T]` sits over `cache.Store`. `NewFileStore(root)` and `NewMemStore()` (tests) live in the zero-dep leaf; the S3 adapter `s3ndjson` (`internal/ndjsonstore/s3ndjson`) is its own package so the AWS SDK stays out — same arrangement as `cachestore/s3store`, and like it a thin shim over `internal/s3blob`. It replaced the near-identical hand-rolled marshal/writer/reader plumbing the two stores each carried, including two separate paginated S3 `ListObjectsV2`-then-`GetObject` loops (rosterbot-c4m). Store keys are **prefix-relative** on both backends, so key-derived fields (the Analysis Store's `system=` segment) parse identically locally and on S3. What each domain package keeps is its row type, its partition key layout, and a `decorate` hook for fields the key carries but the body does not.

**`internal/analysis`** — the durable **Analysis Store** (model-performance history, opposite lifecycle to the ephemeral Cache). The daily `grade` command reuses `backtest.RunProjectionAnalysis` to materialize **Graded Snapshots** (`analysis.GradeRow`: per (date, player) projected/actual/diff + bucket/role/is_pitcher) and writes them as NDJSON to `analysis/grades/dt=YYYY-MM-DD/system=<sys>/grades.ndjson`. **System is a Hive partition owned by the object path, not the NDJSON body** (`GradeRow.System` is `json:"-"`) so it never collides with the Athena `system` partition column; writers take it as a `WriteGrades(date, system, rows)` argument and readers populate it from the key via `SystemFromKey`. Legacy partitions written before the system dimension (`grades/dt=X/grades.ndjson`, no `system=` segment) are read back under `analysis.LegacySystem` (`"depthcharts-ros"`, the system the bot ran) so the detail dashboard keeps its pre-migration history. **`LegacySystem` IS the production system's string, so `System` alone cannot tell a pre-migration row from a current one** — which is why `GradeRow.Legacy` (`json:"-"`, key-derived exactly like `System`, set by `SystemAndOriginFromKey`) exists. Consumers that merely display history ignore it; the head-to-head comparison in `internal/report` must not (rosterbot-kb4). `analysis` defines `GradeRow`/`MarshalNDJSON`/`Writer`/`Reader`/`NewWriter`/`NewReader`/`NewFileWriter`/`NewFileReader`/`ObjectKey`/`SystemFromKey`/`SystemAndOriginFromKey`/`LegacySystem` — the row, the partition layout, and the system dimension. Everything below that (marshal, the partition walk, the storage seam) lives in **`internal/ndjsonstore`**, shared with the Team Value Store. `cmd/grade.go` writes via S3 when `STATE_BUCKET` is set, else local `.analysis/`, looping the 4 shadow systems (actuals fetched once, graded per system).

**A day with no baseball gets a `SkipMarker`, because absence cannot carry that meaning on its own** (rosterbot-u9u). A date on which no rostered player appeared produces no graded rows and therefore no `dt=` partition, which the Infra page's gap scan counted as a hole indistinguishable from a real missed day — re-running `grade` for a no-baseball day silently did nothing. `grade` now writes `analysis/grades/dt=<date>/no-actuals.json` for those days. Three properties are load-bearing: it is a **distinct key**, not a zero-row `grades.ndjson`, because an empty NDJSON is indistinguishable from a truncated write; it carries **no `system=` segment**, so it falls outside every projected Athena partition and `Reader`'s `grades.ndjson` suffix filter skips it, leaving both read paths untouched; and the decision comes from the day's **own roster snapshot** (`ungradeableDays`), not the MLB schedule — 2026-07-14 *had* a game, the All-Star Game, which Fantrax scores nothing for, so a schedule lookup would have called that day gradeable and left the false gap in place. A date the fetch never returned, or returned with an empty roster, is **not** marked: an empty snapshot is a failed fetch, not evidence of no baseball, and marking it would suppress exactly the real gap the page has to keep showing. The read side mirrors the write side: one walk of the `grades/` prefix filtered on the `grades.ndjson` filename picks up both `dt=*/system=*/` and legacy `dt=*/` partitions (matching on filename rather than a fixed key depth is what makes one pass cover both layouts), and `SystemFromKey` stamps `System` on each row via `ndjsonstore.ReadAll`'s decorate hook. `cmd/projection-site.go` wires the appropriate store by `STATE_BUCKET`. The CDK-managed Athena table `rosterbot_analysis.grades` (partition projection on `dt` + `system`-enum, no crawler) makes the store queryable for model auditing (MAE/bias by position **and by system** over time). Snapshots persist because `entrypoint.sh` syncs `.backtest/` (under the `backtest/` prefix). See `docs/adr/0001-s3-not-db-for-cache.md` and `docs/aws-deployment.md`.

**`internal/report`** — pure aggregation package (no I/O, no rendering). Consumes `[]analysis.GradeRow` and produces a `Model`. The **detail dashboard** (`Views`/`Trends`, keyed `"window|role"`) is computed from the **`detailSystem` slice only** (`= analysis.LegacySystem` = `"depthcharts-ros"`, the bot's production system) so its meaning is unchanged; each `View` holds a `Scorecard` (MAE/Bias/RMSE/N), `[]PositionRow`, `[]CalibPoint`, `[]Miss`, plus a `[]TrendPoint` and rule-based `[]Insight`s. On top of that sits the **system-comparison panel**: `Compare` (keyed `"window|role"` → `[]SystemScore` ranked by **within-day Spearman rho descending**; `Best` is flagged only when the leader beats the runner-up by more than the combined standard error **on at least `minCompareDays` (10) shared days**, otherwise the panel reports *too close to call*. **`Compare["<w>|all"]` is nil** — a pooled cross-role ranking has no defensible order, so the panel stacks the hitters and pitchers tables instead) and `CompareTrends` (keyed `"window|role"` → system → `[]TrendPoint`) span **every captured system**, driving the headline ranking table + overlaid per-system MAE trend lines. `Aggregate` normalizes empty-`System` rows to `detailSystem` (matching the reader's legacy attribution) so un-attributed input still feeds the detail views. `rankSystems`/`filterSystem`/`distinctSystems`/`dropLegacy`/`commonPlayerDays` are the comparison helpers.

**The comparison panel is PAIRED, and both halves of that are load-bearing (rosterbot-kb4).** Three defects made the `Best` flag untrustworthy, each verified against the live Analysis Store by an independent Python reimplementation and reproduced by the shipped Go:
- **Unequal samples.** `rankSystems` filtered each system independently and never intersected, guarding only on `N>0`. It now scores every system on the **intersection of `(dt, PlayerID)` across the competing systems** (`commonPlayerDays`; a system with zero rows is skipped rather than intersected, since intersecting against an empty set would blank the panel instead of narrowing it). The effect is not cosmetic: paired, **the incumbent's pitcher rank fell from 1st to last** — its entire apparent lead was extra days no challenger ran on. Each system's own pre-pairing count survives as `SystemScore.TotalN` ("646 of 722"), so a comparison that discards coverage doesn't repeat the invisibility one level down.
- **Legacy pooling.** `dropLegacy` removes pre-migration rows from the whole panel (ranking *and* trend lines); detail `Views` keep them — pooled, the incumbent was credited with pre-challenger days that dragged its reported MAE down. Pairing alone is **not** sufficient: re-grading a legacy date (the recovery procedure in rosterbot-n30) writes `dt=X/system=Y/` while the old `dt=X/grades.ndjson` survives, giving the incumbent two rows for one player-day, both passing the pairing filter.
- **The SE gate inverted on thin samples.** `withinDayRho` can only compute a standard deviation from two or more daily correlations, so a one-day sample leaves `SE` at 0; `flagBest`'s separation term became `sqrt(0+0) = 0` and *any* difference cleared it, crowning a system with literally zero measured skill as best. Hence `minCompareDays = 10`: a **floor, not a fitted optimum** — the SE the gate divides by is itself estimated from d days with relative uncertainty `~1/sqrt(2(d-1))`, so 10 is where the quantity doing the gating is known well enough to gate with. It does not bind on current data and changes no verdict today.

**Measure this package against the tenant prefix, not `analysis/grades/`.** `layout.Analysis` is `PerTenant`, so the deployed reader is rooted at `analysis/grades/user=<uid>/`; the bare `dt=` copies are pre-migration orphans the rosterbot-crq.11 backfill left behind, and syncing the whole prefix double-counts every row (3508 → 7016). `internal/report/diag_compare_test.go` is the build-tagged harness: `DIAG_GRADES=<dir> go test -tags diag -run TestDiagCompare -v ./internal/report/`, with `DIAG_MODEL_OUT=<path>` to dump the real `model.json` the dashboard fetches. There is no `Render`/`template.html` anymore (Dashboard v2 deleted both) — the `Model` is serialized straight to JSON and the dashboard SPA owns presentation. The daily `ProjectionSite` EventBridge schedule (`cron(0 15 * * ? *)`, ~90 min after `grade`) runs `projection-site`, which reads from the Analysis Store, calls `report.Aggregate`, and **publishes the model to `STATE_BUCKET`'s `reports/` prefix** (`reports/model.json`) via `statestore.ReportsStore()` — **not** to the dashboard bucket's `report/` prefix, which CloudFront's default behavior serves unauthenticated (see **Private dashboard reports** below). The SPA's `projections.js` fetches it over `GET /v1/reports/model` and renders the scorecard/trend/calibration/misses/comparison views client-side (vendored Chart.js, ported from the deleted template's inline script — no recomputation, just reshaping the precomputed `Model` into DOM), surfaced as the native "Projections" tab (no iframe). Distinct from the recap's `SITE_BUCKET`, which remains its own separate site.

**Rank skill is the headline metric** (`internal/report/rank.go`, rosterbot-aei). MAE at player-day grain is near-blind to model skill: measured over 850 production rows, hitter MAE actually *lost* to a constant-at-sample-mean baseline, because projections barely vary against daily outcome variance. What the model does have is rank skill — exactly what a lineup optimiser consumes — so `RhoStat` carries the mean of per-day Spearman correlations plus its standard error, day count and days-positive. Three rules are load-bearing: **Spearman is tie-corrected** (average ranks, Pearson over ranks) because every player who didn't play sits at `actual = 0` and the `1 - 6Σd²/(n(n²-1))` shortcut is invalid under ties; **rho is never pooled across roles** — `View.Rho` and `SystemScore.Rho` are `*RhoStat` and nil for `role == "all"`, since a pooled number would reward knowing only that starting pitchers outscore bench catchers, which the optimiser never uses (it runs the two roles in separate passes); and **`minDayRows = 3` is a calibrated floor, not a guess** — a spec-proposed floor of 5 failed the reproduction gate on pitchers (most graded pitcher-days carry only 3-4 rows, so it discards most usable days and inflates rho on a collapsed sample); a threshold sweep shows 3 is where both roles are simultaneously well-supported (see the sweep table in `rank.go`'s doc comment). `Metrics.SkillVsMean` (`1 - MAE/MAE_constantAtMean`) renders under the MAE tile so the demotion stays a daily-recomputed fact rather than an assertion, reproduced exactly against the production Analysis Store and matching independent triage measurements to four decimal places.

**`internal/teamvalue`** — the durable **Team Value Store**: each fantasy team's aggregate HKB dynasty value for one day, as date-partitioned NDJSON (`dt=YYYY-MM-DD/values.ndjson`). Shares its NDJSON plumbing with `internal/analysis` via **`internal/ndjsonstore`**, but is single-entity (no `system` dimension), so the partition key is just `dt=` and the entity name lives in the S3 prefix (`analysis/team-values/`) / local dir (`.teamvalue/`). `teamvalue.Row` stores value as **four leaf cells** — hitter/pitcher × MLB/minors — plus matching count leaves and `RosteredCount`/`MatchedCount` (join-coverage transparency); `TotalValue`/`MLBValue`/`MinorsValue`/`HitterValue`/`PitcherValue` are derived methods. `teamvalue.Aggregate(date, pool, hkbPlayers, teamNames, teamLogos)` joins each rostered player (`FantasyTeamID != ""`) to its HKB `Value` by `playername.Normalize` (the same join as `claims`/`transactions`), buckets by Fantrax `MinorsEligible` (minors) and `positions.IsPitcherSlot` (pitcher; a two-way player with any pitcher eligibility resolves to pitcher), and denormalizes team name + logo into each row so the read+render path needs no Fantrax call. Unmatched rostered players increment `RosteredCount` only (value/count leaves are matched-only) and their names are collected into that team's `Row.Unmatched`, which **is** durable (`json:"unmatched,omitempty"`) — the dashboard's Matched column hovers to show them, and the staleness objection that once kept it out does not apply, since the names ride in the same `Row` as the two counts they explain. The consequence is that **nil is ambiguous and must never be read as "everyone matched"**: this store is `NoBackfill`, so every partition written before the field was persisted decodes to nil forever while still carrying `MatchedCount < RosteredCount`. Only the counts separate "nothing to record" from "not recorded"; `render.js`'s `unmatchedTitle` is the one place that rule is enforced. `cmd/team-values.go`'s `printTeamValueSummary` still prints the names on a follow-up log line under any team with a shortfall. `Writer`/`Reader`/`NewWriter`/`NewReader`/`NewFileWriter`/`NewFileReader`/`MarshalNDJSON`/`ObjectKey`. The series **accumulates forward** — HKB has no history and rosters aren't archived, so past compositions are unrecoverable; there is no backfill (see `docs/adr/0002-team-value-store-accumulates-forward.md`).

**`internal/valuereport`** — pure aggregation (mirrors `internal/report`; no I/O, no rendering). `BuildModel([]teamvalue.Row)` produces a `Model` (per-team `Series` of the four leaves + a `Latest` total-descending standings snapshot; stable per-team colors by sorted TeamID). There is no `Render`/`template.html` anymore (Dashboard v2 deleted both) — the `Model` is serialized straight to JSON. The `team-values` command (`cmd/team-values.go`) is the daily producer — fetches HKB + `GetFullPlayerPool` + `GetScoringPeriodsAndTeams`, calls `Aggregate`, and writes today's partition (S3 when `STATE_BUCKET` set, else `.teamvalue/`); it runs on the `TeamValues` EventBridge schedule (`cron(30 14 * * ? *)`, after `Archive`'s HKB refresh, before `ProjectionSite`). `cmd/projection-site.go`'s `renderValueSite` reads the store (reader chosen by `STATE_BUCKET`) and writes `value.json` to `--out`, published under `DASHBOARD_BUCKET`'s **public** `report/` prefix, soft-failing independently so a team-value hiccup never blocks the accuracy dashboard deploy. It is one of only three artifacts that stay public (with `football.json` and `football-trades.json`), because a per-team dynasty-value standings table is league-wide information every manager can already read off Fantrax — unlike the three private reports beside it. The SPA's `value.js` fetches `report/value.json` and renders the multi-team Chart.js time plot with a **metric selector** deriving Total/MLB/Minors/Hitter/Pitcher client-side, a team legend toggle (+ All/None), and a current-standings table with logos and join coverage, surfaced as the dashboard SPA's native "Value" tab (no iframe).

**`internal/lineupgap`** — the durable **Lineup Gap Store**: how each day's applied lineup scored against the hindsight-optimal one, as date-partitioned NDJSON (`dt=YYYY-MM-DD/gaps.ndjson`) over `internal/ndjsonstore`, plus its own pure `BuildModel` (following `internal/recaplog`'s store-plus-model shape rather than the `teamvalue`/`valuereport` split, since the model is a few dozen lines of windowed sums). `Row` carries actual/optimal/gap points and started/benched counts; `Efficiency()` is derived. **There is no system dimension** — exactly one lineup was applied each day and hindsight-optimal doesn't depend on a projection system — so the partition key is `dt=` alone and the entity lives in the prefix (`analysis/lineup-gaps/` ↔ `.lineupgap`), mirroring `teamvalue`. The consequence: rho answers *which projection system*, the gap answers *what the whole pipeline costs*; they are complementary, not comparable. The producer is `cmd/grade.go`, which already holds the `DailyFantasyPoints` result and a live client (`projection-site` has neither), and calls the existing `backtest.RunLineupAnalysis`; the write **soft-fails** so a gap hiccup never takes down the irreplaceable grades. Unlike the Team Value Store it is `NoBackfill: false` — past-period roster snapshots are immutable and cached, so a missed day is recoverable with `grade --dates`. `cmd/projection-site.go`'s `renderGapSite` publishes the gap report to the private `reports/` prefix beside the model and views ones, soft-failing independently; the SPA's Projections tab leads with it, fetched over `GET /v1/reports/gap`. It is private for the most direct reason of any of the three: it is a running scoreboard of how many points the manager left on their own bench, which is precisely what a league rival would want.
