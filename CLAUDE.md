# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make build              # build binary + lambda module (or: go build -o rosterbot .)
make build-modules      # cross-compile every nested Go module (lambda/, opsnotify/, infra/)
make check-pins         # assert shared `replace` pins agree across all four go.mod files
make install            # install to $GOPATH/bin
make test               # run all unit tests (or: go test ./internal/...)
go test ./internal/optimizer/...  # run a specific package's tests
make dry-run            # run optimizer locally without applying changes
go run . optimize --dry-run --dates 2026-04-01  # test a specific date
go run . optimize --dry-run --dates 2026-03-26:2026-03-28  # test a date range
go run . optimize --dry-run --dates all  # test full season from today
go run . optimize --dry-run --matchup    # test remaining days in current matchup period
go run . prospects --dry-run  # run prospect report locally
go run . gs-check --dry-run          # check league-wide GS violations for the most recently completed period
go run . transactions --dry-run      # check recent trades with HKB valuations
go run . waivers --dry-run           # Statcast-driven free-agent picks (top 15 by default)
go run . waivers --dry-run --top 25 --positions OF,SP   # bigger list, position filter
go run . backtest                                    # backtest last completed matchup week
go run . backtest --dates 2026-04-13:2026-04-19      # backtest a specific window
go run . backtest --skip-projections                 # lineup-only backtest (faster)
go run . optimize --dry-run --snapshot               # write projection snapshots in dry-run (non-dry-run runs write by default)
go run . recap --out /tmp/recap.html                 # render weekly HTML recap (most recent completed week)
go run . recap --dates 2026-04-20:2026-04-26 --out /tmp/recap.html  # specific window
go run . recap --out /tmp/recap.html --open          # render and auto-open in default browser
go run . recap-site --out dist                       # render every completed week into a static site dir
go run . recap-site --out dist --open                # build site and auto-open dist/index.html
go run . shadow                                      # capture today's projections from all 4 RoS systems (read-only; for model comparison)
go run . shadow --dates 2026-06-30                   # capture a specific date
go run . archive --dry-run           # capture today's ephemeral data (HKB, projections, Savant, prospects); --dry-run prints sizes
go run . archive --date 2026-06-30   # capture a specific date
go run . version-check               # probe Fantrax with the pinned API version; fails on confirmed STALE_CLIENT or a gate that stopped discriminating
make clean-cache        # rm -rf .cache/  (cold-pass baseline before make run-all)
make run-all            # exercise every command in dry-run / read-only mode + print cache size
```

**`make run-all` is the canonical end-to-end smoke test** — it iterates every CLI command in dry-run / read-only mode with `time` on each step and prints the final `.cache/` size. Use it for two things: (1) a single-command sanity check before pushing changes, and (2) observing cache behavior — stderr `cache hit:` / `cache miss:` lines show what each command touched. **Whenever you add a new top-level CLI command (a new `cmd/<x>.go` registered on `rootCmd`), append a corresponding line to the `run-all` recipe in the `Makefile`** so the smoke target stays comprehensive. Pair with `make clean-cache && make run-all` for a cold pass, then `make run-all` again to see warm-cache behavior.

After making code changes, always run `go vet ./...` and `go mod tidy` to catch issues early. Note: `gofmt` and `go vet` run automatically via PostToolUse hooks on every Edit/Write.

**`lambda/`, `opsnotify/` and `infra/` are SEPARATE Go modules** (each with its own `go.mod`) — the root `go build ./...` / `go vet ./...` / `go mod tidy` do **not** descend into them. Two guards now exist: `.github/workflows/ci.yml` runs `make build-modules` on every PR (a stale nested module blocks merge), and `.github/dependabot.yml` watches all four module directories and **groups** them into one PR so root and nested modules never drift apart. CDK bundles `lambda/` and `opsnotify/` as `GoFunction` assets, so a stale `go.mod` in any of them only surfaces as a failed `cdk deploy`. They pull the root module via `replace ../`, so **every dependabot bump to a shared root dep re-stales them** (this broke the dashboard-v2 deploy twice — first `lambda/`, then `opsnotify/`). After touching a nested module (or after a dep bump), run `make build-modules`; fix a failure with `cd <dir> && go mod tidy`. `make build` runs it automatically so the break fails locally instead of at deploy.

**A third guard covers what `build-modules` structurally cannot**: each module that imports a forked dep carries its **own** `replace` line for it (root `go.mod` and `lambda/go.mod` both pin `github.com/pmurley/go-fantrax` to a fork commit), and nothing makes them agree. `build-modules` only notices the drift when the bump changes an API — which is exactly why rosterbot-7i3 *looked* covered. In the real recovery scenario, bumping `auth_client.APIVersion`'s **string** with no API change, a stale `lambda/go.mod` compiles clean, CI stays green, and the Lambda ships the old constant; `version-check` can't see it either, since it probes the root binary's pin only. **`make check-pins`** (run by CI and by `make build`) asserts that any module path replaced in more than one `go.mod` resolves to the same target everywhere. It compares **version-pinned replaces only** — `replace <root> => ../` appears in both `lambda/` and `opsnotify/` and the strings match, but only by luck, since a filesystem path resolves against its own module dir; filtering on a non-empty version drops those honestly rather than passing them by accident. Missing `jq` is a hard error, not a skip — a guard that silently no-ops is the false-confidence failure this one exists to kill (rosterbot-00e).

Tests require no credentials — all network dependencies are mocked via interfaces or test servers.

For local dev, create a `.env` file (gitignored) with `FANTRAX_USERNAME`, `FANTRAX_PASSWORD`, `FANTRAX_LEAGUE_ID`, `FANTRAX_TEAM_ID`, `FANTRAX_IL_SLOTS`, `FANTRAX_MINORS_SLOTS`. Loaded automatically by `godotenv`.

Optional env vars with defaults: `GS_TRACKING_ENABLED` (false) — enables games-started tracking, used by both the optimizer (weekly GS budget) and gs-check (league-wide violation detection). The real min/max are always fetched live from Fantrax's own per-period `getTeamRosterInfo?view=GAMES_PER_POS` configuration (see `internal/fantrax.GetGSLimits`) — there's no numeric env var for the limit itself, since Fantrax scales it whenever a period spans more than one calendar week (season opener, All-Star break). `PROSPECT_ROLLING_DAYS` (14), `PROSPECT_MIN_GAMES` (8), `PROSPECT_RANK_CACHE_HOURS` (168), `PROSPECT_UPGRADE_RANK_THRESHOLD` (20).

GS-check env vars (required only for `gs-check` command): `GS_TRACKING_ENABLED=true`, `PUSHOVER_GROUP_KEY`, `PUSHOVER_API_TOKEN`. If the live GS-limit fetch fails, both `optimize` and `gs-check` send a Pushover alert via `PUSHOVER_USER_KEY`/`PUSHOVER_API_TOKEN` (the personal ops-alert channel, same as the cache's stale-fallback notification) rather than falling back to a stale static number.

## Architecture

The optimizer runs as a single binary (`main.go`) with Cobra subcommands (`cmd/`) that wire together four independent packages:

```
fantrax client  ──┐
mlb schedule    ──┼──► optimizer ──► apply lineup (or dry-run print)
fangraphs proj  ──┘
```

**`internal/cache`** — generic TTL cache using Go generics (`FileCache[T]`). Stores JSON with a `fetched_at` timestamp envelope behind a byte-level **`Store`** seam. `Get(key, fetchFunc)` returns cached data if fresh, otherwise calls `fetchFunc`, saves, and returns. All I/O errors are non-fatal. TTL of 0 bypasses cache (`--no-cache` flag). Storage is pluggable: `fsStore` (default; `<dir>/<key>.json` flat under `.cache/`) and `MemStore` (tests) live in the zero-dep leaf; the S3 adapter `s3store` (`internal/cachestore/s3store`) lives in its own package so the AWS SDK stays out of the leaf, and is itself a thin shim over the shared `internal/s3blob` (see below). `cache.SetDefaultStore(store)` swaps storage process-wide for every `FileCache` without touching the ~30 `New[T](dir, ttl)` call sites (mirrors the `Verbose`/`Notify` package globals). On AWS, `cmd` calls `SetDefaultStore(s3store…)` keyed under the `cache/` prefix when `STATE_BUCKET` is set, so the bot reads/writes the cache per-key live to S3 and `entrypoint.sh` no longer syncs `cache/`. See `docs/adr/0001-s3-not-db-for-cache.md`.

**`internal/statestore/layout`** — the single declaration of the STATE_BUCKET key layout: every prefix the bot writes, its local-dir equivalent, and the operator-facing metadata (`MaxAge`, `Producer`, `Partitioned`, `NoBackfill`). A **zero-dependency leaf**, because two packages need the table and can't import each other: `statestore` builds typed stores from it (and imports `lineupapi`, so the dependency only runs one way), while `lineupapi` serves it on `GET /v1/infra`. `NoBackfill` marks the one artifact whose missing days are unrecoverable (the Team Value Store — see `docs/adr/0002`), which is what lets the Infra page rank a gap there above a merely stale prefix.

**`internal/statestore`** — the composition root's single owner of the durable-state backend choice: S3 when `STATE_BUCKET` is set (Fargate), else a local directory. It centralizes the one `os.Getenv("STATE_BUCKET")` read (`statestore.Bucket`), the prefix/local-dir layout table for every durable artifact (`cache/`, `analysis/`, `analysis/team-values/`, `runledger/`, `runs/`, `notifications/`, `lineup/` ↔ their `.cache`/`.analysis`/`.teamvalue`/`.lineup/*` local roots), and the sole S3-vs-local branch (`pick[T]`). It exposes one typed constructor per artifact (`CacheStore`, `AnalysisWriter/Reader`, `TeamValueWriter/Reader`, `RunLedger`, `Output`, `Notifications`, `Progress`, `LineupPublisher`). **Only `cmd` imports it** — no leaf imports it back, so the AWS SDK it pulls in (via the three s3 adapters) never reaches leaves like `internal/lineuprun`, which receives its `lineupapi.Publisher` from `cmd` via `Options.Publisher` instead of reading the environment itself. The `cmd/sync.go` bulk dir-sync gating and `cmd/migrate_run_ledger.go` (require-S3) share the one env read via `statestore.Bucket()` but keep their distinct, non-store-constructor behavior. Compatible with ADR-0001.

**`internal/s3blob`** — the one place aws-sdk-go-v2's S3 client is constructed and driven. A `Blob` is a bucket+prefix scoped view exposing `Get`/`GetWithETag`/`Put`/`PutJSON`/`PutJSONIfAbsent`/`PutJSONIfMatch`/`Delete`/`Walk`/`List`; every key handed to or returned from it is **relative to the prefix** (joined on the way in, stripped on the way out), so key-derived fields parse identically against S3 and against each adapter's local-directory backend — the Analysis Store's `system=` segment, the run ledger's inverted-timestamp ordering. `Get` reports a missing object as `(nil, false, nil)` rather than an error, since absence is an ordinary outcome for every caller (cache miss, run with no captured output yet, unregistered passkey). `Walk` follows `NextContinuationToken` and lets its callback return `false` to stop early — that combination is what makes "newest N" listings safe, and is the bug class rosterbot-432 hit when a single-page listing let sub-objects sharing a prefix hide the ledger block entirely.

**The two conditional writes are the only compare-and-swap in the tree, and exist for exactly one artifact** (rosterbot-crq.2). Every other store here is write-once-per-key; the WebAuthn identity record is read-modify-written by concurrent HTTP requests (register appends a credential, login updates a sign counter, revoke removes one), so a blind `PutJSON` silently drops whichever change lost — a registration that returns 200 and later simply is not there, with nothing logged. `PutJSONIfAbsent` (`If-None-Match: *`) and `PutJSONIfMatch` (`If-Match: <etag>`) push the decision to S3, which is the only place it can be made correctly across independent Lambda invocations; both normalize a lost race onto `ErrPrecondition` — including the 409 `ConditionalRequestConflict` AWS documents alongside the 412, and the 404 an `If-Match` returns when the object was deleted, since all three mean "not the state you asserted" and all three recover by re-reading. This does **not** loosen the rule above: the `Store` interfaces stay unshared, and only the conditional-`PutObject` plumbing is centralized. `s3blobtest` evaluates both preconditions rather than accepting every write — a fake that rubber-stamps conditional writes reports success for precisely the interleaving the condition exists to reject.

All ten S3-backed stores are thin shims over a `Blob`: `s3store` (cache), `s3ndjson` (Analysis + Team Value), and the seven in `s3lineup` (lineups, run ledger, per-run output, progress, notifications, WebAuthn identity, infra listing) plus the ledger `MigrateStore`. Each shim owns only its key layout, its interface shape and its own not-found policy — `s3store` returns the miss, `s3ndjson` turns it into an error because `ReadAll` only ever `Get`s keys it just listed. Before rosterbot-oye each of these hand-rolled `config.LoadDefaultConfig`, a private `api` interface, prefix joining and `NoSuchKey`/`NotFound` mapping, and four of them had their own list loop — of which only one paginated correctly.

**The WebAuthn identity record is the one store here under optimistic concurrency.** `lineupapi.Identity` carries a `Version IdentityVersion` (`json:"-"`) that `GetIdentity` reports and `PutIdentity` conditions on — empty means "create, and fail if a record exists"; non-empty means "write only if still at this version" — with a lost race surfacing as `ErrIdentityConflict` and a successful write advancing `Version` in place. The version **rides on the struct rather than the method signature**, matching the DynamoDB conditional-write this record migrates to (epic rosterbot-crq) and removing the chance for a call site to forget to thread it through; it is **opaque** because the backends disagree on what a version is (S3's ETag, the file store's content SHA-256, DynamoDB's own attribute) and a decimal counter in the JSON body would be decoration on S3, where the real precondition still has to be the ETag. The consequence of an unchanged signature is that an implementation ignoring `Version` still compiles, so **`internal/lineupapi/identitytest.Run` is the contract** and every implementation must be run through it. `Config.mutateIdentity` owns the retry: it re-reads and **re-applies the mutation to the current record** (never re-writing a stale snapshot), bounded at 5 attempts, which is what lets a concurrent registration and login both survive. `FileIdentityStore` gets a mutex plus atomic rename — honestly scoped to one process, since the file backend has no OS compare-and-swap and `serve` is a single-operator dev server; the backend that actually runs concurrently is S3, where the precondition is enforced server-side.

**This must not be used to unify the `Store` interfaces above it.** `cache.Store` (`Get`→`([]byte, bool, error)`/`Put`/`Remove`) is a delete-capable keyed TTL cache with no enumeration; `ndjsonstore.Store` (`Get`→`([]byte, error)`/`Put`/`List`) is an enumerable append-only partitioned log with no delete. Those signatures encode the real lifecycle difference between the Cache and the durable stores that ADR-0001 and ADR-0002 rest on; only the SDK plumbing beneath them is shared. `internal/s3blob/s3blobtest` is the shared in-memory `API` double — it emulates real ListObjectsV2 pagination (lexicographic order, `PageSize` per call, `IsTruncated`/`NextContinuationToken`) precisely because pagination bugs only surface against a fake that actually pages. The real AWS path is exercised by a build-tagged live test: `STATE_BUCKET=<bucket> AWS_REGION=us-west-1 go test -tags live ./internal/s3blob/`, which writes and cleans up under a `scratch/s3blob-live/` prefix and skips when `STATE_BUCKET` is unset. The three s3 adapters it wires are now shims over one shared `internal/s3blob` (rosterbot-oye); their constructor signatures (`New*(ctx, bucket, prefix)`) are unchanged, so `pick[T]` was untouched by that change.

**Caching at a glance**: three TTL tiers map to three mutability classes.

| Tier | TTL | Use for | Examples |
|------|-----|---------|----------|
| `PastPeriodTTL` | **∞** (100 y) | Settled past-period snapshots (immutable once the period closes and stops settling) | `fantrax-roster-stats-<teamID>-<season>-<period>`, `fantrax-pitcher-gs-<teamID>-<season>-<period>`, `fantrax-recent-stats-pitcher-<teamID>-<season>-<period>` (hitter recency now comes from the `fantrax-roster-stats` daily series, not a dedicated snapshot), `fantrax-{hitter,pitcher}-roster-<teamID>-<season>-<period>`, `fantrax-gs-limits-<teamID>-<season>-<weeklyPeriod>`, `mlb-schedule-<YYYY-MM-DD>` (past dates), `mlb-player-id-<name>-<team>` |
| `stableTTL` | 7 d | Season-invariant config | `fantrax-{hitter,pitcher}-slots-<leagueID>`, `fantrax-{hitter,pitcher}-scoring-<leagueID>`, `fantrax-season-range-<leagueID>` |
| `todayTTL` | 15 m | "Today, but stable for a window" — drifts during the day, but fine to reuse for an hourly GHA loop or local-dev iteration | `fantrax-{hitter,pitcher}-roster-<teamID>`, `fantrax-current-period-<leagueID>-<YYYY-MM-DD>`, `fantrax-player-pool-<leagueID>`, `fantrax-minors-roster-<teamID>`, `fantrax-available-prospects-<leagueID>`, `fantrax-pending-trades-<leagueID>`, `fantrax-all-trades-<leagueID>`, `fantrax-all-transactions-<leagueID>` |

**`PastPeriodTTL` is unbounded on purpose, and two invariants are what make that safe** (rosterbot-qoa). It was 30 days until 2026-07-31, which quietly made `recap-site` cost O(season length): the Monday build re-renders *every* completed week, so every week older than a month re-fetched from Fantrax — 1,637 supposedly-immutable snapshot objects rewritten on 2026-07-20 alone, wall time 192 s → 1411 s between April and 2026-07-27. The two invariants:
- **Volatility.** A period only reaches the past tier once it can no longer move — `periodIsVolatile(period, curPeriod)` (`recentPeriodLookback = 3`) keeps the current period *and the last three closed ones* on `todayTTL`, covering Fantrax's StatsType=1 YTD settling lag and the slop between UTC period math and ET game times. `tierFor` applies it to the `cacheTier` path, `snapshotTTL` to the two caller-supplied snapshot caches (`DailyFantasyPoints`, `GetTeamPitcherStarts`). A bare `period < curPeriod` test was fine at 30 days — a mid-settle capture self-corrected within the month — and is *not* fine now: one day too early pins a wrong snapshot for the rest of the season.
- **Season scoping.** Every key at this tier carries the season year (`seasonScopedKey` → `<prefix>-<teamID>-<season>-<period>`, matching the older `fantrax-period-date-map-<leagueID>-<year>`). Daily *and* weekly period numbers restart each season; the 30-day TTL used to flush that collision for free over the ~6-month off-season, and an unbounded TTL does not.

The one-time cost of the season rename is that every pre-2026-07-31 `fantrax-{roster-stats,pitcher-gs,hitter-roster,pitcher-roster,recent-stats-pitcher,gs-limits}-<teamID>-<period>` object is orphaned — the next `recap-site` build does one cold rebuild (the work that used to happen weekly) and then never again. The orphans are inert; prune at leisure.

A handful of provider-specific TTLs sit outside this scheme: `fangraphs-{bat,pit}-*` (24 h, `projections.ProjectionCacheTTL`), `mlb-handedness` (7 d), `savant-*` (24 h, `statcast.CacheTTL`), `hkb-*` (8 h), `prospect-rankings-*` (168 h via `PROSPECT_RANK_CACHE_HOURS`), `mlb-game-logs-<playerID>-<group>-<season>` (1 h, prospects MiLB game log), `mlb-game-log-<playerID>-<group>-<season>` (1 h, MLB-only game log used by the internal `backfillDailyFPts`). These predate or sit between the three-tier scheme and use whatever TTL fits the upstream's update cadence. The FanGraphs and Savant TTLs are **single exported constants** (`projections.ProjectionCacheTTL` / `statcast.CacheTTL`, both 24 h matching the once-daily upstream cadence) so every consumer (optimize, backtest, waivers, claims) shares one freshness policy on the shared cache entry — TTL is a per-read max-age against the stored `fetched_at`, not baked into the key, so divergent TTLs across callers would otherwise cause needless refetches.

**Cache key naming**: `<source>-<entity>[-scope...]` where `source` ∈ {`fantrax`, `mlb`, `fangraphs`, `savant`, `hkb`, `prospect`, `mlb-handedness`}, `entity` is the data shape (e.g. `roster-stats`, `pitcher-gs`, `matchups`, `schedule`, `bat`, `pit`), and `scope` is whatever disambiguators apply (teamID, period, leagueID, date). The repeated prefixes are named constants owned by the package that builds them — the whole `fantrax-*` / `mlb-game-log` family in `internal/fantrax/cachekeys.go`, plus `keySavant` (`statcast/load.go`) and `keyFanGraphs` (`projections/fangraphs.go`) — so a prefix rename lands in one place; genuine single-use keys (`mlb-schedule`, `mlb-handedness`, `mlb-player-id(s)`, `mlb-game-logs`) stay inline literals. Old `backtest-snapshot-mlb-*` files (pre–roster-stats rename), `backtest-snapshot-*` files (StatsType=2 era), and `player-ids.json` (pre-FileCache prospects bulk file) are orphaned and safe to delete.

**Claims cursor and ledger**: `.cache/last-claims.json` is a small JSON file written by `internal/claims` after each successful run; it records the most recent transaction timestamp seen so the next run fetches only new events (cursor-based incremental delivery). The audit ledger is written to `.waivers/claims/<date>.json` (one file per UTC calendar date); the `.waivers/claims/` directory is created on first write and is safe to include in the GHA cache alongside `.cache`.

**`Client.SetCache(cacheDir)`** in `internal/fantrax/client.go` enables the file cache for every cached method on `*fantrax.Client`. `cmd/root.go`'s `initApp` calls it on every command's client unless `--no-cache` is set, so commands inherit caching automatically — no per-command opt-in. The cache-plumbing *policy* every cached method shares — short-circuit to the uncached `fetchXxx` sibling when `cacheDir` is empty (the `--no-cache` flag, and how tests stay hermetic), otherwise read-through a `FileCache` at the method's tier TTL — lives in three generic helpers in `internal/fantrax/cached.go`: `cached(c, key, tier, fetch)` for the fixed-tier methods, `cachedForPeriod(c, prefix, teamID, period, fetch)` for per-period snapshots, and `cachedForSeason(c, prefix, teamID, period, tier, fetch)` for a fixed tier over a season-restarting period number (GS limits). Each call site names only its key parts, its tier, and its fetch (rosterbot-nrr collapsed ~20 hand-copied branches into these). The three-tier scheme is a named `cacheTier` type (`tierToday`→`todayTTL` 15m / `tierStable`→`stableTTL` 7d / `tierPast`→`PastPeriodTTL` ∞), so which tier a method gets is a visible, checkable choice rather than whichever `time.Duration` constant the author typed. Per-period methods (`GetHitterRosterForPeriod`, `GetRecentPitcherStats`, etc.) resolve **both** their tier and their key's season scope from one `c.periodCachePolicy(period)` call — settled periods get `tierPast`, the current and still-settling ones fall back to `tierToday` (see `tierFor`/`periodIsVolatile`) — and the two period-aware helpers call it only *after* the empty-`cacheDir` short-circuit, because the resolution reads the season range and the no-cache path must not trigger it. That read goes through the **cached** `GetSeasonDateRange` (7 d on disk), not the raw `fetchSeasonDateRange`, so repeated per-period calls cost a disk hit rather than a Fantrax round-trip. The "current" bound comes from `PeriodForDate(seasonStart, time.Now().UTC())`.

**`c.periodCacheKey(prefix, teamID, period)` is the one place a per-period key is built**, returning both the key and its tier from a single policy read. It is a method rather than two inlined lines because it wasn't: `InvalidatePeriodRosterCache` assembled its own key by hand, so when rosterbot-qoa spliced the season into the grammar the writer moved and the invalidator didn't. **Removing a nonexistent cache key is not an error**, so the function went on reporting success while dropping nothing for four days (**rosterbot-sza**) — its whole purpose, letting a second `optimize` run after `ApplyLineup` see the applied lineup instead of the pre-apply snapshot, silently not happening. Bounded only by the 15 m `todayTTL` on the current period, which is also why it stayed quiet: hourly runs are 60 min apart, so the exposure was a second run inside that window — exactly what the **Idempotency** section below prescribes as the verification, making that check unsound after an apply. `TestInvalidatePeriodRosterCache_DropsTheEntryTheReaderWrote` pins the two sides together by driving the real reader rather than comparing key strings, so any future divergence fails regardless of how the key is built. The current-day keys in the same function keep the plain unscoped grammar on purpose — they sit at `todayTTL`, where no period number appears and a stale entry expires on its own.

**`PastPeriodTTL` is exported because it is also an argument, not only a tier.** `DailyFantasyPoints` and `GetTeamPitcherStarts` take their TTL from the caller, and that value was re-typed as a bare `30 * 24 * time.Hour` literal at six sites (`cmd/{recap,recap_site,backtest,grade}.go`, `internal/recap/site.go`, `internal/lineuprun/recent.go`). So "the" past-period TTL named only a quarter of the caches it appeared to govern, and the two families that actually dominated `recap-site`'s runtime (`fantrax-roster-stats-*`, `fantrax-pitcher-gs-*`) were **not** among them — changing the package constant alone would have fixed nothing measurable. All six now reference `fantrax.PastPeriodTTL`.

The matchups response is also memoized in-memory per `*fantrax.Client` (via `allMatchups()`) — five different helpers consume the same `GetAllMatchups` payload during a single `recap-site` build, and in-memory is the right scope since the in-progress week mutates intra-day.

**`internal/config`** — loads env vars via `godotenv`, validates that all four required vars are set, and returns a `Config` struct used by the CLI commands to wire everything together.

**`internal/scoring`** — the single home for the stat→fantasy-points algebra. `ApplyHitter`/`ApplyPitcher` take a neutral `HitterLine`/`PitcherLine` of raw counts and apply `Weights` (the `fantrax.ScoringWeights` alias). Pure, imports nothing else in the tree, so `fantrax` (game-log backfill) and `projections` both depend on it without a cycle. See the **Scoring model** section below for the adapter pattern.

**`internal/positions`** — the single source of truth for Fantrax position-ID semantics: ID constants (filling `"003"`/`"008"`, which `auth_client` omits), `SlotName`, `AcceptsINF`, `IsPitcherSlot`, and `HitterBucket` (C>INF>OF>UT reporting precedence). A leaf package (depends only on `auth_client`); `fantrax` and `backtest` import it instead of hardcoding position-ID switches.

**`internal/fantrax`** — wraps `github.com/pmurley/go-fantrax` (public read API) and `go-fantrax/auth_client` (authenticated API + lineup writes). Key details:
- `auth_client` uses chromedp (headless Chrome) to log in and obtain a session cookie. Cookie is cached in `.fantrax-cache/`. On first run or cache miss, a browser opens.
- Credentials read from env: `FANTRAX_USERNAME`, `FANTRAX_PASSWORD`, `FANTRAX_LEAGUE_ID`, `FANTRAX_TEAM_ID`.
- **Fantrax API version** — every `/fxpa/req` POST body must include `"v": "<current>"`. This lives in exactly one place: the exported `auth_client.APIVersion` constant in the go-fantrax fork (`auth_client/fantrax_client.go`), whose doc comment is the runbook (the `curl` probe for the current version string and the unauthenticated STALE_CLIENT-vs-logged-in check). `gs_check.go` builds its `/fxpa/req` payload via `auth_client.BuildFullRequest`, so it — like every other caller — picks up the constant automatically rather than carrying its own copy. When Fantrax deploys a new version and calls start returning `STALE_CLIENT` (empty `responses` array), bump `APIVersion` in the fork; nothing in this repo needs a matching edit. The daily `version-check` command (see Commands) probes Fantrax unauthenticated against the pinned version and fails on a confirmed `STALE_CLIENT`, catching the drift before it hits a real job.

**The probe carries a positive control, because a green reading is only worth what the job's ability to go red is worth** (rosterbot-0a1). Fantrax's gate is a **minimum** check, not an equality check — measured live 2026-08-05, the floor sat between `181.0.0` (`STALE_CLIENT`) and `182.0.0` (`WARNING_NOT_LOGGED_IN`), and `999.999.999` passes. The headroom is narrow: upstream `pmurley/go-fantrax` main was pinned at `182.0.0` that same week — one release above the floor. So whenever the pinned probe reads OK, a second probe sends `fantrax.ControlVersion` (`1.0.0`), which a working gate must reject; if it comes back anything but `STALE_CLIENT`, the gate has stopped discriminating, every "version OK" this job has been reporting is meaningless, and the run fails with `PROBE_BLIND`. Without it the failure is invisible in the worst way: the job launches, exits 0, the ledger records SUCCESS, and `opsalert` — including the `Overdue` heartbeat, which only asks whether a run *happened* — has nothing to react to. The control is deliberately far below the floor rather than just under the pin: it must fail only when the **mechanism** breaks, never when the **threshold** moves, and a moved threshold is already the real probe's job to report. A control transport error is a warning, not a failure — the gate answered the pinned probe moments earlier, so an undelivered control proves nothing, on the same rule that keeps a Fantrax outage silent.
- **Position IDs are numeric strings** (`"001"` = C, `"002"` = 1B, `"003"` = 2B, `"004"` = 3B, `"005"` = SS, `"008"` = INF, `"012"` = OF, `"014"` = UT). These come from the roster API and must be used as-is for slot assignment and eligibility checks. Their semantics live in **`internal/positions`** (the single source of truth): ID constants — filling `"003"`/`"008"`, which upstream `auth_client` omits — plus `SlotName`, `AcceptsINF`, `IsPitcherSlot`, and `HitterBucket` (the C>INF>OF>UT reporting precedence). `fantrax` and `backtest` both import it instead of hardcoding switches.
- This league's active slot names: `C`, `1B`, `2B`, `3B`, `SS`, `INF`, `OF` (×4), `UT` (×3). Mapped in `posNameToID` in `client.go` (which references `positions` constants).
- Scoring group code is `BASEBALL_HITTING` (not `HITTING`).
- **Scoring periods are daily** (period 1 = season opener), though Fantrax merges consecutive days into one period number around multi-day breaks (e.g. the All-Star break) and can insert extra daily periods mid-season (doubleheader/postponed-game makeups) — so plain `1 + days since season start` arithmetic can drift. Matchup data from `GetAllMatchups()` has weekly matchup entries, not daily — don't use it for period lookup.
- **Two distinct period axes, two distinct helpers — do not cross them.** The two axes are distinct Go named types — `WeeklyPeriod` and `DailyPeriod` (`period_types.go`) — so passing a weekly value where a daily one is required (or vice versa) is a compile error, not a silent bug (rosterbot-1i3, the fix for the rosterbot-uv6 / rosterbot-z3b bug class). `GetScoringPeriodsAndTeams()` returns `[]ScoringPeriod` parsed from Fantrax's standings `SCHEDULE` view captions ("Scoring Period N (date - date)"); despite the name, `N` is the **weekly matchup** number (~7 days/period, merged wider around breaks — e.g. period 16 spans 2026-07-13..07-26 across the All-Star break, per `TestFindCurrentPeriod_MergedAllStarBreakPeriod`). `FindCurrentPeriod(periods, date)` / `FindJustEndedPeriod` answer "which weekly period contains/just-ended for this date" from that list — correct for GS-limit lookups (`GetGSLimits` takes the weekly number) and standings-style questions. Roster/apply/GS-snapshot endpoints (`GetHitterRosterForPeriod`, `GetPitcherRosterForPeriod`, `ApplyLineup`, `getPlayerGSSnapshotForPeriod`) are keyed by a completely different, **daily** period number (advances one per calendar day, e.g. 104…110 across a week) that Fantrax never exposes as a list — only as "the current period" via `GetCurrentPeriod()`. **`fantrax.DailyPeriodFor(seasonStart, date)`** (`gs_period_walk.go`) is the single source for that axis — the **Period Map** (see `CONTEXT.md`): the authoritative `periodList` date map first, then `PeriodForDate(seasonStart, date)` day math as its only fallback. It depends on nothing but `(seasonStart, date)` — notably not on "today" nor on `GetCurrentPeriod()`. `GetTeamGS`/`GetTeamPitcherStarts` walk each day of a (weekly) `ScoringPeriod` via **`gsPeriodWalk`**, which calls `DailyPeriodFor` per day — never the weekly `ScoringPeriod.Number` itself, which would make every day in the period fetch the identical snapshot. `internal/lineuprun.Run`'s per-date apply loop (`optimize`/`shadow`) resolves each `--dates`/`--matchup` date to its daily period the same way, via `DailyPeriodFor` directly — **not** via `FindCurrentPeriod`/the weekly `periods` list, and not via a `periods`-first resolver.
  - A prior change (**rosterbot-uv6**, commit 92ed478) mistakenly routed `GetTeamGS`'s daily walk through a periods-list-first resolver (`fantrax.ResolvePeriod`, since deleted); every day then fetched the *same* weekly-numbered snapshot, collapsing all day-over-day deltas to zero and under-counting each team's weekly GS to ~one day's worth. That surfaced as a whole-league false "Under Min" GS alert at the first All-Star-break boundary (2026-07-13) and was reverted to daily numbering (**rosterbot-wd5**).
  - The exact same class of bug independently recurred in the lineup-apply path: `rosterbot-z3b` (2026-07-12) introduced `fantrax.ResolvePeriod` — a periods-list-first, three-tier resolver intended as "the single entry point for mapping a calendar date to its scoring period number" — and wired `internal/lineuprun.go`'s per-date apply loop through it. Its tier 1 trusted the weekly `periods` list as if it were daily-grained; since virtually every in-season date falls inside some weekly period's date range, tier 1 won on nearly every call. When the All-Star break merged two weeks into period 16 (2026-07-13..07-26), every `--matchup` date in that 11-day span resolved to the identical period 16: `GetHitterRosterForPeriod`/`GetPitcherRosterForPeriod` fetched the same stale snapshot for all 11 dates, `ApplyLineup` wrote all 11 dates' changes to the same period, and — because the diff for each date's "actual" target day never converged — the same lineup swap re-applied and fired a fresh Pushover notification for all 11 dates on **every hourly `Lineup` run**, the flood of duplicate lineup-change alerts diagnosed 2026-07-14. Fixed by switching the apply loop to `DailyPeriodFor` directly and deleting `ResolvePeriod` (no safe production use case remained: every real caller needs the daily axis, and the weekly `periods` list can't provide it). The baseline-day lookup (`dayBeforePeriod`) resolves via the same `DailyPeriodFor` daily numbering. Historical/backtest-facing period lookups (`DailyFantasyPoints`, `GetTeamPitcherStarts`) are **resolved** (**rosterbot-ren**) via the authoritative season-wide date→daily-period map: `DailyPeriodFor` consults `periodDateMap` (`period_date_map.go`), parsed once from `getTeamRosterInfo`'s `DisplayedLists["periodList"]` dropdown (`"104 (Mon Jul 6)"` … — the label for period N *is* the date whose snapshot lives at period N, so it's self-correcting across Fantrax's mid-season period insertions), cached season-stable (`fantrax-period-date-map-<leagueID>-<year>`, `stableTTL`) plus in-memory memoized like `allMatchups`; it soft-falls-back to naive `PeriodForDate` on any miss/fetch error, so hermetic tests and credential-less renders are unaffected. The Class-A anchored path (lineup-apply + `GetTeamGS`) was **unified onto the same authoritative map** (**rosterbot-2ax**, closed 2026-07-16), and then (**rosterbot-xyk**, 2026-07-25) the two near-twin resolvers were **collapsed into one**: `Client.dailyPeriodForDate` and the anchor tier are gone, leaving a single `DailyPeriodFor(seasonStart, date)` of map → day math. The decision was measurement-driven — against the live `periodList` map (187 entries covering the whole 2026 season) the **daily axis is strictly 1:1 with calendar days**: zero merged or inserted periods across 122 elapsed days, and naive day math agrees with the authoritative map on **all 187 dates**. So the anchor tier never once supplied an answer day math wouldn't have, while its own input (`GetCurrentPeriod()`) demonstrably lagged a day and caused the 2026-07-16 failure below. The merging Fantrax *does* do — the All-Star break — happens on the **weekly** axis only. Measured the same day: the two weekly notions (standings-caption `ScoringPeriod.Number` vs `MatchupWeekBounds` from `GetAllMatchups`) agree **exactly** — same count, bounds and numbering across all 23 weeks including both irregular ones — so they are one concept reached two ways, documented as *Weekly Period* / *Matchup Week* in `CONTEXT.md` rather than unified in code. The "identical output today — zero drift" assumption the deferral was filed under broke the very next day: on 2026-07-16, live `GetCurrentPeriod()` returned 113 for that date while the freshly-refetched (not stale-cached) periodList map said 113 = 2026-07-15 and 114 = 2026-07-16 — Fantrax's own "current period" pointer lagged a full calendar day behind its periodList dropdown. The lineup-apply hot path submitted changes against the already-closed period 113; Fantrax rejected the affected players as "already locked," and `applyLineupWithLockedPlayerRetry`'s locked-player retry masked the resulting no-op as "Lineup applied successfully" (a separate follow-up: that retry path trusts an empty/benign post-retry response instead of verifying the intended change actually landed — filed as **rosterbot-48z**). `gsPeriodWalk` takes a leading `*Client` param (nil-safe) to thread the map through to `GetTeamGS`/`GetTeamPitcherStarts`.
- **Future lineup apply** requires a two-step confirmation flow: first API call returns a confirmation prompt (`ShowConfirmWindow=true`), second call with the same payload applies the changes. Handled in `ApplyLineup`.

**`internal/projections`** — FanGraphs projections via the `--projections` flag. Supported systems: `steamer`, `depthcharts`, `thebatx`, `atc`, plus their rest-of-season variants `steamer-ros`, `depthcharts-ros`, `thebatx-ros`, `atc-ros`. Default is `depthcharts`; the bot currently runs on `depthcharts-ros` in season. Wraps the configured system with a rolling-stats fallback chained via `ChainedSource`. FanGraphs returns **JSON** (not CSV); player name field is `PlayerName`. The `Projection` struct includes derived stats (`Singles`, `XBH`, `TB`) that must be computed from raw fields before scoring. Separate `Source` (hitters) and `PitcherSource` (pitchers) interfaces.

**Blended scoring** — wraps the configured FanGraphs source with recent Fantrax stats, in the **`BlendSources`** phase (`internal/lineuprun/blend.go`). The recent signal differs by role. **Hitters** use a **trailing 30-day window**: `windowedHitterRecent` reconstructs the per-day FPts series (`DailyFantasyPoints` over the last ~35 days, backfilled) and collapses it via `projections.WindowedRecent` + `WindowWeight(30)` into per-player FP/game + games-in-window, as of today. That splits into two pure pieces worth knowing about — `hitterWindowBounds` (the 35-day lookback, clamped to the opener, ending yesterday) and `collapseHitterWindow` (series → recency map, no client) — because an error in the collapse doesn't fail, it silently shifts every hitter's Expected Points. **Pitchers** still use **season-to-date** YTD FP/G from a single roster snapshot: the Fantrax roster API returns cumulative YTD `FantasyPointsPerGame` regardless of the period requested, so `GetRecentPitcherStats` reads the latest completed period's snapshot. Both fall back to 100% base projection when no recent data. Weights are **dynamic** (not fixed) and shift toward recent stats as a player accumulates a stable sample. The hitter window **replaced** unbounded YTD after `backtest --recency-experiment` (**rosterbot-2nd**) showed w30 beating unbounded YTD by ~1 realized pt/game/day over both the full season (109d) and the last 8 weeks — raw YTD double-counts the in-season signal already regressed into `depthcharts-ros`. Pitchers showed **identical** lineup outcomes across every strategy (pitcher slotting is game-availability-bound, not projection-bound), so they stay on YTD. The harness compares base / ytd / 14d / 30d / decay variants for **both** roles; see `docs/superpowers/specs/2026-06-06-windowed-recency-strategy-replay-design.md`.

**The hitter window is roster-scoped, and that had to be corrected for mid-window acquisitions** (rosterbot-6tw). `DailyFantasyPoints` walks **our own** per-period roster snapshots, so a player's games-in-window is really *games while on our roster* — and since `WindowedRecent` builds its series only from days a player appears in, pre-acquisition days contribute **no row at all** rather than a zero. Nothing distinguished the two: measured 2026-08-11, Sam Antonacci (4 periods of tenure) and Zach Neto (4) both reported ~3-4 GP and a **96%/94%** base weight, indistinguishable from Carson Williams' genuine 96% after **70** periods. So the recency signal `rosterbot-2nd` measured at ~1 realized pt/game/day was switched off for exactly the players a trade had just made hardest to value. `coverImportedHitters` now detects short coverage (`shortCoverageHitters`: first appearance later than the **30-day window** start — not the 35-day fetch start, since the extra lookback days only populate the far edge) and **replaces** those players' entries with ones rebuilt from `fantrax.MLBDailyFPts`. Antonacci and Neto both moved to **74%**, the everyday-player band, while Williams (94%) and Genao (92%) correctly stayed high.

**`MLBDailyFPts` is the roster-independent sibling of `DailyFantasyPoints` and the two must not be merged.** `DailyFantasyPoints` answers *"what did MY team score on this day"* and is consumed by `cmd/grade.go`, `cmd/backtest.go` and `internal/recap` — all of which would be **wrong** if credited with production a player earned on someone else's roster. `MLBDailyFPts` answers *"what did this player produce"*, from their MLB statsapi game log scored with the league's weights, which is the only correct input to a recency window. Replacement rather than splicing is deliberate: the game log already covers the overlapping days, so merging would double-count them. The path **soft-fails** to the roster-derived window, matching `DailyFantasyPoints`' own backfill contract, and prints an `mlb recency coverage:` line **unconditionally** — including the zero case — naming any unmatched player, because a silently truncated window is precisely what kept this invisible for a season. An unmatched name is not automatically a defect: verified 2026-08-12, Marcelo Mayer resolves correctly (691785) but has no MLB game after 2026-06-25, so there is genuinely nothing to backfill. Naming him is what made that a ten-second check rather than an assumption.
- **Hitters** (`BlendedSource`): `seasonWeight = approxPA / (approxPA + 250)` where `approxPA = GP × 3.8` and **GP is games in the trailing 30-day window** (caps ~26), so recent weight tops out near ~28% but reflects only recent form; base weight = `max(1 - seasonWeight, 0.30)`, never below 30%. `PtsPerGameSource` interface (type assertion) lets the optimizer use pre-computed values.
- **Pitchers** (`PitcherBlendedSource`): role-aware stabilization — SP equal weight at 15 GP, RP at 25 GP; base floor 35%. Requires minimum GP before blending. GP here is season-to-date (YTD snapshot). `PitcherPtsPerGameSource` interface.

**`internal/playername`** — the single home for `Normalize`, the cross-source name-matching key used everywhere Fantrax names get joined against another provider (HKB, FanGraphs, MLB statsapi): `internal/teamvalue`, `internal/claims`, `internal/transactions`, `internal/hkb`, `internal/waivers` (via `ResolveMLBAMIDs`), `internal/recap` (League Leaders), `internal/schedule`, `internal/fantrax` (MLB backfill, apply-lineup scorer IDs), and `projections.NormalizeName` (a thin wrapper, so the optimizer/blending/backtest paths inherit it too). It strips diacritics (NFD decomposition), lowercases, drops periods/commas/apostrophes — including the "smart quote" variants (`'`/`'`) a source's text pipeline may substitute for a straight `'`, and a comma before a suffix ("Guerrero, Jr." vs "Guerrero Jr.") — treats hyphens as word breaks (`"Ha-Seong Kim"` vs `"Ha Seong Kim"`), and strips `Jr`/`Sr`/`II`/`III`/`IV` suffixes. A join miss that isn't one of these known gaps (a call-up too new for HKB's rankings, a genuine nickname like "Vlad" for "Vladimir") isn't fixable by string transformation — see `internal/teamvalue`'s `Unmatched` below for how those surface instead of silently undercounting.

**The normalized key is not unique, so the HKB join resolves through `hkb.Lookup` rather than a map** (rosterbot-5z7). The suffix- and diacritic-stripping that makes the join work is exactly what merges distinct players: measured 2026-08-14, 1752 HKB players collapse to 1748 keys, and `luis garcia` covers both Luis García Jr. (NYY, MLB, value 1142) and a rookie-ball namesake (value 10). The old `BuildLookup` assigned unconditionally, so **the last row in scrape order won** — and a wrong match is worse than a miss in a specific way: a miss is absent and every wire field is `omitempty`, so it renders as unknown, while a wrong match renders as a confident number **and counts toward join coverage**. On the day this was found, DillonP33's rostered García Jr. was being valued at 10 while `team-values` reported that team **49/49 matched** — the instrument built to expose undercounting displaying perfect health over a miscount, in the one store that is `NoBackfill`. Same failure class as `claimName` below, one provider up.
- `Find(name)` declines any contested key. Used where the caller holds only a name and a position (`internal/claims`, `internal/transactions`, the tradeboard offer path, and `lineuprun.hkbMeta` — whose roster carries `InMinors`, where the player *is*, not `MinorsEligible`, what he is *eligible for*; passing one as the other would resolve a called-up prospect against his MLB namesake).
- `FindFor(name, Hint{MLBTeam, MinorsEligible})` disambiguates, and is used by the two sites holding a pool row: `internal/teamvalue` and `tradeboard.BuildValuesTable`. **Neither signal suffices alone** — club settles 3 of the 4 live collisions but not `luis garcia` (both NYY), level settles 3 but not `max muncy` (both MLB), and together they settle all 4. **When the two signals name different rows, it refuses**; so does a signal that rules out every row, since a hint naming a club neither namesake plays for is stale rather than informative.
- **The level signal is one-way, by measurement.** Cross-tabbing `MinorsEligible` against HKB `Level` over 512 cleanly-resolving rostered players: `minors=false → MLB` holds 396/404 (98%), but `minors=true → non-MLB` holds only 91/108 (**84%**) — minors eligibility is an eligibility, not a location, and 17 called-up prospects (Volpe, Domínguez, Hyeseong Kim) sit at MLB. Reading it backwards to prefer the minor-league row would be confidently wrong at a 16% rate. Reproduce with `go test -tags diag -run TestDiagMinorsVsLevel ./internal/hkb/`.
- **Compare clubs with `sameTeam`, never `==`.** The feeds disagree on exactly two of 32 abbreviations — HKB `AZ` vs Fantrax `ARI`, HKB `CWS` vs Fantrax `CHW` — so raw equality would silently never match for Arizona or White Sox players.

**`ResolveMLBAMIDs` (name → MLBAM ID) has three rules that are each load-bearing, all established by live measurement on 2026-08-11** (rosterbot-bms, rosterbot-i52). It is the join key for five call sites — `internal/fantrax` (backfill + `MLBDailyFPts`), `internal/recap` (League Leaders wOBA/FIP), `internal/claims` (Statcast tagging), `internal/prospects` (×2) — so a wrong ID is a wrong join everywhere, not a local glitch.
- **Namesake collisions resolve toward the active player** (`claimName`). MLB's people-search deliberately spans historical players and every affiliated level, so common names collide with retired namesakes; the old unconditional `rp.ByName[k] = p.ID` was last-write-wins, and with the search batches running in parallel the winner was not even stable between runs. Measured: `"Jose Altuve"` → a catcher last active in the 2000s rather than the 2B, `"Jose Ramirez"` and `"David Peterson"` likewise. This produced **confidently wrong data, not a visible failure** — `fetchMLBGameLog` succeeds against the retired namesake, finds no game, and the row is written `FPts=0, HadGame=false` with `needsBackfill` **cleared**, i.e. permanently recorded as a genuine off day. Two *active* namesakes (MLB has had two Will Smiths) remain genuinely ambiguous; the lower-ID tie-break only guarantees the same answer every run, not the right one. **`"active"` must stay in the `WithFields` mask** — omit it and every `p.Active` is nil, silently collapsing the rule back to lower-ID-wins.
- **A degraded resolution is returned but never cached.** Every error path used to be swallowed (`return nil` per batch, `continue` per detail block) while `fetchAndResolve` returned a nil error, so `cache.Get` persisted a partial or empty result for the full 7-day TTL. Three all-zero entries existed in production, all written in one bulk-build hour. The failure itself is transient and unavoidable — reproduced live: 97 of 133 names dropped once, then 129/133 on the next three runs — so the fix is `errDegraded`, handed to `cache.Get` purely to suppress the write while the partial map is returned out-of-band. Batches also retry (`searchWithRetry`) before counting as failed.
- **Search sends the raw name first, then the normalized one for misses only.** Neither spelling is a superset: `"A.J. Blubaugh"`, `"T.J. Rumfield"` and `"Zach Cole Jr."` return **0** results raw and resolve normalized (periods and suffixes stripped), while `"Ha-Seong Kim"` is the reverse, since `Normalize` turns its hyphen into a space. The second pass costs extra requests only for names that already failed. A residual gap remains that normalization cannot close: `"Jake Latz"` → MLB's `"Jacob Latz"`, a legal-name/nickname difference.

Verified end-to-end against Sleeper's independent MLB table over 133 real Fantrax names: ID **disagreements went 6 → 0** and unresolvable names **4 → 1** (the remaining one being Latz). The `diag`-tagged harness that produced these numbers lives in `internal/playername/diag_*_test.go` — run with `DIAG_NAMES=... go test -tags diag ./internal/playername/`; it never runs in CI.

**`internal/statcast`** — leaf owner of Baseball Savant data and the derived buy-low / hot **Statcast Signals** (imports only `internal/cache` and `internal/archive`). Holds the **Statcast Bundle** (`Bundle` — the five Savant expected-stats / quality-of-contact slices joined by MLBAM ID), `LoadBundle` (cached at `CacheTTL` = 24 h; cache-key prefix `keySavant` = `"savant"`, unchanged from its former home so existing `.cache/savant-*` entries still hit), the signal engine (`Signal`, `TagHitter`/`TagPitcher` returning `(Signal, SignalMetrics)`), `Thresholds`/`DefaultThresholds`, and `ArchiveArtifacts` (raw-CSV archival). Extracted from `internal/waivers` so `waivers`, `claims`, and `recap` depend on this data leaf — not on each other's command package. `TagHitter`/`TagPitcher` return a `SignalMetrics` of the facts behind the classification; callers own identity/report fields (e.g. `waivers.Candidate` embeds `SignalMetrics`).

**`internal/waivers`** — Statcast-driven waiver wire audit. `Run(ft, today, opts)` fetches the full Fantrax player pool, filters to MLB free agents (FantasyStatus `"FA"` / `"W*"` / empty, excluding `MinorsEligible`), resolves names → MLBAM IDs via `playername.ResolveMLBAMIDs`, and joins each FA against (a) FanGraphs projections (configured system; default `depthcharts`) from `projections.LoadBattingProjections`/`LoadPitcherProjections` for the per-game point projection, and (b) a `statcast.Bundle` of five Baseball Savant CSVs for signal tagging (the Savant loader and signal engine live in **`internal/statcast`**, not here — see below). Two signals fire per player: **BUY-LOW** when xStats outpace surface stats (hitter: `xwOBA - wOBA ≥ 0.030` AND barrel ≥ 9 AND hard-hit ≥ 42; pitcher: `era - xera ≥ 1.00` AND `xwoba ≤ 0.310`) and **HOT** when recent production is backed by quality (hitter: 14d `wOBA ≥ .380` AND `xwOBA ≥ .360` AND season barrel ≥ 8; pitcher: 30d `era ≤ 3.20` AND `xera ≤ 3.50`). When both fire, the row is tagged `BOTH`. Sample guards: hitter season ≥80 PA, hitter 14d ≥20 PA, pitcher season ≥100 TBF, pitcher 30d ≥50 TBF. Defaults live in `statcast.DefaultThresholds()`; tests override. The design separates concerns deliberately — Statcast picks WHO surfaces, FanGraphs scores HOW MUCH — so the league's own `ScoringWeights` (via `ExpectedPtsFromProj`) drive the ranking and FAs without a FanGraphs projection are skipped (accepted v1 limitation). Output: stdout (always), GHA markdown summary (when `GITHUB_STEP_SUMMARY` set), Pushover (when `!DryRun` and creds set; `formatPushover` truncates to fit the 1024-char limit). CSV fetchers (in `statcast/load.go`) have URLs as `var` for test override; column lookup is by lowercased name with aliases so Savant header drift doesn't break parsing. CSVs are cached at 24h TTL (`statcast.CacheTTL`) via `cache.FileCache[T]` keyed by year + window-end-date.

**`internal/claims`** — league-wide CLAIM/DROP recap. `Run(ft, today, opts)` fetches all recent Fantrax transactions via `GetAllTransactions` (cached as `fantrax-all-transactions-<leagueID>`, `todayTTL`), filters to CLAIM and DROP events since the last run using a cursor persisted at `.cache/last-claims.json`, and pairs each CLAIM+DROP by `Transaction.ID` to reconstruct complete moves. Each picked-up player is valued via HKB rankings (reusing the same normalized-name join as `internal/transactions`) to produce a "value gained" metric and a per-team daily leaderboard. When `!opts.NoSignals`, picked-up players are enriched with Statcast signal tags (BUY-LOW / HOT / BOTH) by joining against the `statcast.Bundle` and FanGraphs projections — the same enrichment path as `internal/waivers`. Notable drops (HKB value above `opts.DropsMin` threshold) are flagged with a watch note. Results are written to an audit ledger at `.waivers/claims/<date>.json` (directory created on first write). On an empty claim window the command is a no-op. Sends Pushover when `!opts.DryRun` and creds are set. `opts.Since` overrides the cursor for one-off historical recaps without resetting the cursor state.

**`internal/backtest`** — grades past work against actual outcomes. Two analyses:
- **Lineup grading**: for each past day, computes an actual-points total (sum of FPts for active-slot players) and a hindsight-optimal total (the existing optimizer run against a `hindsightSource` that returns each player's actual FPts as pts-per-game via the `PtsPerGameSource` / `PitcherPtsPerGameSource` interfaces). `Gap = actual - optimal`; negative means points left on bench. SP-eligible pitchers who actually appeared are fed to the optimizer as "probable starters" so the `NonStarterSPDiscount` (0.05x) doesn't apply in hindsight.

  **The hindsight source floors each player's value at zero (`hindsightValue`), and that floor is load-bearing** (rosterbot-0gm). `optimizer.optimalAssignment` fills every slot it can and only leaves one empty when *no* eligible player remains — sound for a live lineup, where projections are never negative, and wrong here, where the values are realised outcomes that go negative. Unfloored, a negative day gets forced into a free slot and "optimal" can land *below* the lineup we actually ran: on 2026-07-02 a -9.00 **reserve** pitcher was activated into one of five empty P slots, reporting optimal 41 against actual 48 (`Gap = +7`, impossible by construction — the lineup we ran is itself a feasible assignment). Flooring is not a fudge: benching a player yields exactly 0 and that option is always available, so `max(0, FPts)` *is* the achievable optimum, and it makes `optimal >= actual` provable (the actual lineup's floored value is >= its raw value, and optimal dominates every feasible assignment). The fix was confined to the hindsight source rather than teaching `optimalAssignment` to leave slots empty voluntarily, because that would change live tie-breaks (equal-value "leave empty" branches would grow `ToBench`, churning the roster) and slow the search. `guardOptimal` backstops the invariant: a still-negative gap is clamped to `actual` with a stderr warning, so a future regression surfaces as a warning rather than a healthy-looking green day on the dashboard. Impact of the floor was not one day — over 2026-06-16..07-27, 13 of 42 days had understated optima and season efficiency fell 76.2% -> 74.6%.
- **Projection grading**: checks `.backtest/snapshots/<YYYY-MM-DD>.json` for archived per-player projection values written by `optimize`. Each snapshot row (`backtest.SnapshotPlayer`) records the projected pts/game plus look-back fields — `was_started`, `slot`, `locked`, `role`, and `eligibility` (position IDs) — so error can be sliced by position and lineup decision. When present, grading compares against actual FPts for an overall MAE/Bias/RMSE report, a per-position MAE table (buckets C/INF/OF/UT for hitters via eligibility precedence C>INF>OF>UT, and SP/RP for pitchers via role), and the top-10 signed-error misses (ordered by **absolute** error descending, `worstMisses` in `internal/report/aggregate.go`, tie-broken on player ID — the displayed sign is retained, and the list merely *looks* over-projection-skewed because SP blowups dominate the largest absolute errors). When a day's snapshot is absent, the day is marked `source="missing"`. When a snapshot exists but its `generated_at` falls on a different ET calendar day than the date it projects — a `--matchup` pre-write that was never refreshed on the day itself (e.g. every hourly run that day failed) — the day is marked `source="stale"` and excluded from the rollup, since grading a multi-day-old forecast inflates apparent projection error (`sameETDate` guard in `backtest.go`, keyed on ET since that's the zone the daily runs and matchup-day boundaries are anchored to; a zero `generated_at` predates the field and is graded as before). `FormatReport` prints an "Excluded from grading: N stale, M missing" line listing the dates, so a window thinned by stale/missing days is visible rather than silently shrinking the sample. The hourly `lineup.yml` workflow runs `optimize` (which writes snapshots by default on non-dry-run) and persists `.backtest/snapshots/` in the GHA cache (alongside `.cache`), so production accumulates a snapshot per day from the most recent hourly run. Local backtest runs that need the snapshots have to either (a) replay the workflow's cache or (b) run `optimize --archive-projections` themselves.

Per-day FPts come from `fantrax.DailyFantasyPoints` (in `internal/fantrax/daily_fpts.go`), which walks a period range and diffs consecutive YTD snapshots via `playerStatsFromTables`. This covers both `scGroup=10` (hitting) and `scGroup=20` (pitching). The Fantrax roster API is requested with `StatsType=1` (MLB stats — real per-player season totals) rather than `StatsType=2` (Fantasy Team — team-credited only) so reserve players' production is visible to hindsight callers; without this, the optimal lineup calc in the backtest/recap can never recommend a benched player and efficiency % stays artificially compressed (~95–99% across the league).

Players seen for the first time in the window have their `(deltaFP, deltaGP)` zeroed so the cumulative pre-window YTD doesn't leak in as same-day production (a waiver pickup with a 200-FPts season-to-date YTD would otherwise inject 200 phantom points on the day they appear). The zeroed row is flagged internally via the **unexported** `DayPlayerFP.needsBackfill`, and **`DailyFantasyPoints` resolves it before returning** (via the unexported `backfillDailyFPts` in `internal/fantrax/mlb_backfill.go`): it fetches the player's MLB statsapi game log for that date and computes FPts from raw stats × the league's `ScoringWeights` — bounded to a handful of API calls per recap week, soft-fails to "leave zero" on any error. **Callers never see the placeholder and never pair a second call** — folding the backfill into `DailyFantasyPoints` removed the six-call-site convention where five callers remembered the pairing and `recap.seasonToDateTeamMean` (the WP-model input) silently didn't, deflating every team's season-to-date mean by every mid-window waiver pickup/role crossing (rosterbot-8ue). Two-way crossings (Ohtani moving between the hitters and pitchers tables) are handled the same way: `diffYTD` detects the `prevOther` fallback (role-specific YTDs can't be meaningfully subtracted), zeroes the diff, sets `needsBackfill`, and the backfill computes the role-correct same-day FPts. The end-to-end path is covered by `TestDailyFantasyPoints_ResolvesBackfillInternally` (through the public entry point, via the `fetchPeriodSnapshotFn` seam). Both fixes verified against the Fantrax-authoritative `Matchup.HomeTeam.Points` for week 8 (recap matched all 10 team totals exactly); the fold-in leaves those team totals byte-identical since the recap's per-team path already ran the same backfill. Per-period snapshots are cached at `.cache/fantrax-roster-stats-<teamID>-<season>-<period>.json` at `PastPeriodTTL` since settled past periods are immutable. A parallel cache `.cache/fantrax-pitcher-gs-<teamID>-<season>-<period>.json` (same TTL) backs `GetTeamPitcherStarts`, used by the recap to enumerate every active-slot SP start; it's optional (pass `cacheDir=""` / `cacheTTL=0` to bypass, which the live `gs-check` path does because it always wants fresh data), and when the cache hits, the per-day 200ms upstream-throttle in `GetTeamPitcherStarts` is skipped. **Both build one cache per period, not one per window** — the caller hands in a single long TTL and `snapshotTTL` narrows it to `todayTTL` for any period still in the volatility window. `DailyFantasyPoints` has done this since the Sunday-night-recap bug; `GetTeamPitcherStarts` used a single flat-TTL cache until rosterbot-qoa, which was survivable at 30 days and would have pinned the live period for the season at `PastPeriodTTL`.

Snapshot writing is default-on for real (non-dry-run) `optimize` runs so the cron accumulates backtest data automatically. Dry-run stays side-effect-free unless you opt in with `--snapshot` (the older `--archive-projections` flag and `BACKTEST_ARCHIVE=1` env var are kept as backward-compatible aliases). Snapshots are rewritten if the same date is optimized twice — last write wins, which is fine for the hourly lineup workflow: the final write of the day captures the most recent projection state for that date, and is the version `backtest` grades against. If that final same-day write never lands (the day's runs all failed), the snapshot is left as an earlier `--matchup` pre-write and the stale-snapshot guard above excludes it from grading.

**Multi-system capture (`shadow`)** — `cmd/shadow.go` drives the full `internal/lineuprun.Run` pipeline (matchup adjustment included) once per RoS system in dry-run, capturing every system's projection side-by-side for the model-comparison report — no lineup applied, no notification. It shares the orchestration engine with `optimize` (zero pipeline duplication) by calling the same `Run` entry point in a loop: each iteration calls `initApp` fresh and builds an `Options` with `ProjectionSystem: sys`, `SnapshotRoot: systemSnapshotDir(shadowSnapshotRoot, sys)` (instead of the flat `.backtest/snapshots/`), and `ForceSnapshot: true`, looping over `shadowSystems` (`steamer-ros`, `depthcharts-ros`, `thebatx-ros`, `atc-ros`). `grade` then loops the same `shadowSystems`, calling `RunProjectionAnalysis(days, systemSnapshotDir(...))` per system (actuals fetched once) and writing each system's rows under its `system=` partition. The hourly `optimize`'s flat snapshot is untouched (it still feeds the local `backtest` command). The EventBridge `Shadow` schedule runs **23:40 UTC** — late ET evening but still the **same ET calendar day as the captured date**, so the snapshot's `generated_at` passes the `sameETDate` stale-guard and is graded by the next 13:30 UTC `grade` run. `.backtest/snapshots-systems/` rides the existing recursive `.backtest/` S3 sync (`del=false`), so the shadow task's `sync-up` and grade task's `sync-down` hand it across Fargate tasks with no entrypoint change.

**GS gate summary** (`gs_gate_summary.go`) — `SummarizeGSGate` reads the same projection snapshots as roster shape below and totals the starts the weekly game-start gate declined, keyed off `SnapshotPlayer.GSSuppressed`. `GateSummary` counts `DaysWithSnapshot` (present AND fresh, per the `sameETDate` rule `RunProjectionAnalysis` uses) separately from `DaysStale`: the gate runs for today's date only, so a `--matchup` pre-write for a future day always carries `GSSuppressed=false` for every pitcher, and counting that day as measured would report a real gap in the run history as a quiet, suppression-free week rather than excluding it the way a missing day already is. `SuppressedPts` is GROSS projected value declined, not a net weekly loss — the budget the gate withheld from the declined start went to a higher-ranked one instead, it wasn't destroyed, so summing it across days does not answer "how many points did this cost." `FormatGateSummary` renders the total suppressed starts/points plus a per-date breakdown for any day with at least one suppression.

**Roster shape** (`roster_shape.go`) is the analytical companion to `GateSummary`: per side, the share of *deployable* projected value the roster fielded, with slot counts and the weekly GS cap alongside. Two denominator rules are load-bearing. **`HasGame` is not the availability test for a starter** — `SnapshotPlayer.ProjPtsPerGame` is the *undiscounted* projection (`NonStarterSPDiscount` is applied downstream of the snapshot, inside `OptimizePitcherLineup`'s local slice) and `HasGame` means only "team plays", so a `HasGame` denominator credits an ace his full projection on four rest days in five and reports rotation cadence identically for every roster in the league; the test is `IsStarter || GSSuppressed`, which reconstructs the *pre-gate* probable-starter set. That puts every start `FormatGateSummary` names into this side's OWNED total, **not** stranded — whether a gate-declined start actually lands in stranded depends on what happens next: `applyGSGate` discounts the pitcher to 0.05x but `OptimizePitcherLineup` still adds him to the slot-assignment pool if he has a game, so on a light slate the pool fits inside the 6 P slots, the suppressed SP is slotted anyway, and his full undiscounted projection lands in fielded instead. **IL and Minors are excluded** via the new `SnapshotPlayer.Status`, since `WasStarted` collapses roster status to one boolean and an injury would otherwise read as a structural surplus. Each side is normalized against its own owned value, never against the other, so a roster carrying exactly its slot count reads 100% on both sides whether the league fields 13 hitters or 9 — the comparison cannot reduce to the slot ratio. Rates are value-weighted (`Σfielded / Σowned`), not a mean of daily rates. The block also prints each side's `DeployableCount`/`RosteredCount` as a Coverage line, because the pitcher denominator is narrow — measured at 2 of 13 rostered pitchers on 2026-08-06 — and a rate computed on that base would otherwise read as a confident statement about the whole staff rather than about a couple of probable starters. The two stranded figures share a unit but are never summed: a benched hitter starts tomorrow, a start above the weekly cap is dead, the same GROSS-not-net asymmetry `GSGateReport.SuppressedPts` documents. `Status` and `GSLimit` exist only from 2026-08-06 forward; a fresh snapshot in which *every* status is empty is counted as `DaysPreSchema` and excluded, because the deployable filter would otherwise leave it with zero owned value and make it indistinguishable from a fully-fielded day.

**`internal/recap`** — Sleeper-style weekly recap. `recap.Run(ft, opts)` aggregates all 12 (or however many) teams in parallel via `errgroup`: for each team it pulls `DailyFantasyPoints` for the matchup week and runs `backtest.RunLineupAnalysis` to compute actual + hindsight-optimal totals, plus `GetTeamPitcherStarts` (a sibling to `GetTeamGS` in `internal/fantrax/pitcher_starts.go`) to enumerate every active-slot SP start with its FPts. H2H pairings come from `GetAllMatchupEntries` (a passthrough wrapper added on `*fantrax.Client`); team weekly scores are aggregated from daily FPts (deterministic, doesn't depend on parsing the upstream `MatchTeam.Total`). Award functions in `awards.go` are pure and unit-tested. **League Leaders** (`leaders.go`, `buildLeaders`) ranks every rostered player league-wide (from `GetFullPlayerPool`, filtered to `FantasyTeamID != ""`) by season-to-date wOBA (hitters) and FIP (pitchers): names → MLBAM IDs via `playername.ResolveMLBAMIDs`, wOBA joined from `statcast.LoadBundle`'s qualified-hitter expected-stats CSV, FIP computed from a batched MLB statsapi season-pitching fetch (`mlbSeasonPitchingURL`, `parseIP` handles `.1`/`.2` thirds) with the FIP constant solved from the rostered-pitcher pool so displayed values land near league average (ranking is constant-invariant). Pitchers need ≥`fipMinIP` (30) innings. The whole path soft-fails to nil — the section is `{{if}}`-guarded out when empty, so archived/credential-less renders stay clean. The single-day leaderboards and league-leaders board both badge each row with the owning team's logo (`PlayerLine.OwnerTeamID` / `LeaderLine.OwnerTeamID` → `teamLogo`) instead of a rank number (rank implied by order); default board size is top 5 (`--top`). The season leaderboard (`RenderSite`) follows the same rank-implied-by-order convention: award categories drop the numbered chip (owner logo only), and the season Shellings list badges each row with the pitcher's **MLB-club** logo via `mlbTeamLogo` (abbrev → statsapi team ID → mlbstatic "spots" PNG endpoint; `mlbTeamAbbrevToID` covers both canonical and upstream-variant abbreviations, falling back to a text chip on an unknown code). Two render helpers centralize the avatar markup so award cards stay terse: `teamBadge(logos, id, name)` emits the fantasy-team logo-or-initial chip (used left of the name in Most/Least Efficient and every League Award card — winner-side cards pass `WinnerID`), and `mlbBadge(abbrev)` emits the MLB-club logo-or-text chip (used left of the pitcher name in the Pitching Highlights best/worst cards). Both return trusted `template.HTML` (our own URLs; names HTML-escaped). The renderer (`render.go` + embedded `template.html`) emits a single self-contained HTML file via `Render` (no nav) or `RenderSite` (with a cross-week dropdown). `recap.RunSite(ft, sopts)` (`internal/recap/site.go`) drives the multi-week build: it enumerates every completed matchup week via `GetMatchupWeekByNumber`, calls `Run` for each, and writes `dist/week-NN.html` plus `dist/index.html` (mirror of the latest week). Each page carries a `<select>` dropdown of all weeks. The `recap-site` CLI command exposes this for the GitHub Pages workflow.

**Week-completion signal** — `completedMatchupWeeks` and the `recap` command's range resolver treat a week as renderable when `weekEnd < today` (strict, date-only) **OR** `weekEnd == today AND every MLB game on that final day is over**. The same-day path lets a Sunday-ending week render the same evening once its games conclude. The completion check is `schedule.Client.AllGamesFinalOn(date)` (MLB statsapi `abstractGameState == "Final"`, plus Postponed/Cancelled via `detailedState`; vacuously true when no games are scheduled that day). The Fantrax weekly `Matchup.*.Points` field is **not** used for this — it's a **running in-week score** (non-zero from the week's first games onward), so an earlier `MatchupWeekIsFinal`/`IsMatchupWeekFinal` heuristic that keyed off `Points > 0` was removed for falsely flagging in-progress weeks (it rendered week 10 on its live final Sunday). `completedMatchupWeeks` takes a `dayCompletionChecker` interface (satisfied by `*schedule.Client`) so the cutoff logic is unit-testable without network; on a schedule lookup error the same-day week is conservatively excluded.

**WP model** — `wp.go` exposes `ComputeWPCurve`, `LeadChangeCount`, `MinWinnerWP`. `ComputeWPCurve` is a Go port of the formula Fantrax runs client-side in its live-scoring Angular bundle (`models.CalculateWinProbability` in go-fantrax): deterministic, no Monte Carlo, no sigma. At each of 8 points (pre-week + 7 day-ends) it feeds cumulative actual FPts, a **live-adjusted** weekly projection (`actual_so_far + remaining_days × HomeMeanDaily`, mirroring how Fantrax recomputes `calculatedProjectedTotalsMap` intra-week — without the live adjustment the projection ratio stays flat all week and the chart degenerates to 50% then a snap to 100%), and a uniform `timeLeft = 7 - i` for both teams into the Fantrax formula. Pre-week WP[0] reflects projection ratio (a 60/40 projected favorite starts at ~84/16, not 50/50). Final WP[7] is always 100/0 or 0/100 — on an exact-tie final the Fantrax formula awards the win to "away" (faithful port; ties never happen in practice with float FPts).

**Game of the Week** — always featured at the top of every week (no skip for quiet weeks). Picked by `GameOfTheWeek(curves, matchups)` using `score = LeadChanges + (1 - minWinnerWP)` — the "weeeeeh factor": back-and-forth swings plus how deep the eventual winner sank mid-week. Ties broken by smallest final margin then home `TeamID` asc. Ties (no winner) score with the comeback term zeroed. The hero chart is rendered as a 380×140 SVG with mirrored 100/75/50/75/100% y-axis labels, half tints (green=home favored on top, red=away favored on bottom), team name labels in their respective halves, and dated x-axis ticks. The matchup-results list marks the chosen game with a ⭐ badge.

**Comeback award** — winner whose mid-week WP dropped below `comebackThreshold = 0.30` (eventual-winner's minimum during `Points[1..6]`). Feeds into `AggregateSeasonAwards`. Game of the Week is intentionally excluded from the season leaderboard — it shows at the top of each week's page, so cumulative counts would be redundant.

**`internal/ndjsonstore`** — shared plumbing for the durable, date-partitioned NDJSON stores (`internal/analysis` and `internal/teamvalue`). Generic over the row type (`Marshal[T]`/`Unmarshal[T]`/`Write[T]`/`ReadAll[T]`) over a byte-level **`Store`** seam (`Put`/`Get`/`List`), mirroring how `cache.FileCache[T]` sits over `cache.Store`. `NewFileStore(root)` and `NewMemStore()` (tests) live in the zero-dep leaf; the S3 adapter `s3ndjson` (`internal/ndjsonstore/s3ndjson`) is its own package so the AWS SDK stays out — same arrangement as `cachestore/s3store`, and like it a thin shim over `internal/s3blob`. It replaced the near-identical hand-rolled marshal/writer/reader plumbing the two stores each carried, including two separate paginated S3 `ListObjectsV2`-then-`GetObject` loops (rosterbot-c4m). Store keys are **prefix-relative** on both backends, so key-derived fields (the Analysis Store's `system=` segment) parse identically locally and on S3. What each domain package keeps is its row type, its partition key layout, and a `decorate` hook for fields the key carries but the body does not.

**`internal/analysis`** — the durable **Analysis Store** (model-performance history, opposite lifecycle to the ephemeral Cache). The daily `grade` command reuses `backtest.RunProjectionAnalysis` to materialize **Graded Snapshots** (`analysis.GradeRow`: per (date, player) projected/actual/diff + bucket/role/is_pitcher) and writes them as NDJSON to `analysis/grades/dt=YYYY-MM-DD/system=<sys>/grades.ndjson`. **System is a Hive partition owned by the object path, not the NDJSON body** (`GradeRow.System` is `json:"-"`) so it never collides with the Athena `system` partition column; writers take it as a `WriteGrades(date, system, rows)` argument and readers populate it from the key via `SystemFromKey`. Legacy partitions written before the system dimension (`grades/dt=X/grades.ndjson`, no `system=` segment) are read back under `analysis.LegacySystem` (`"depthcharts-ros"`, the system the bot ran) so the detail dashboard keeps its pre-migration history. `analysis` defines `GradeRow`/`MarshalNDJSON`/`Writer`/`Reader`/`NewWriter`/`NewReader`/`NewFileWriter`/`NewFileReader`/`ObjectKey`/`SystemFromKey`/`LegacySystem` — the row, the partition layout, and the system dimension. Everything below that (marshal, the partition walk, the storage seam) lives in **`internal/ndjsonstore`**, shared with the Team Value Store. `cmd/grade.go` writes via S3 when `STATE_BUCKET` is set, else local `.analysis/`, looping the 4 shadow systems (actuals fetched once, graded per system).

**A day with no baseball gets a `SkipMarker`, because absence cannot carry that meaning on its own** (rosterbot-u9u). A date on which no rostered player appeared produces no graded rows and therefore no `dt=` partition, which the Infra page's gap scan counts as a hole — across the 2026 All-Star break that meant three fabricated gaps (07-13/14/15) sitting in the same "Re-runnable" list as one real one (07-01, where games *were* played and the shadow capture missed the day), and re-running `grade` for the fabricated three silently does nothing. `grade` now writes `analysis/grades/dt=<date>/no-actuals.json` for those days. Three properties are load-bearing: it is a **distinct key**, not a zero-row `grades.ndjson`, because an empty NDJSON is indistinguishable from a truncated write; it carries **no `system=` segment**, so it falls outside every projected Athena partition and `Reader`'s `grades.ndjson` suffix filter skips it, leaving both read paths untouched; and the decision comes from the day's **own roster snapshot** (`ungradeableDays`), not the MLB schedule — 2026-07-14 *had* a game, the All-Star Game, which Fantrax scores nothing for, so a schedule lookup would have called that day gradeable and left the false gap in place. A date the fetch never returned, or returned with an empty roster, is **not** marked: an empty snapshot is a failed fetch, not evidence of no baseball, and marking it would suppress exactly the real gap the page has to keep showing. The read side mirrors the write side: one walk of the `grades/` prefix filtered on the `grades.ndjson` filename picks up both `dt=*/system=*/` and legacy `dt=*/` partitions (matching on filename rather than a fixed key depth is what makes one pass cover both layouts), and `SystemFromKey` stamps `System` on each row via `ndjsonstore.ReadAll`'s decorate hook. `cmd/projection-site.go` wires the appropriate store by `STATE_BUCKET`. The CDK-managed Athena table `rosterbot_analysis.grades` (partition projection on `dt` + `system`-enum, no crawler) makes the store queryable for model auditing (MAE/bias by position **and by system** over time). Snapshots persist because `entrypoint.sh` syncs `.backtest/` (under the `backtest/` prefix). See `docs/adr/0001-s3-not-db-for-cache.md` and `docs/aws-deployment.md`.

**`internal/archive`** — stdlib-only leaf package for durable daily snapshots of ephemeral upstream data that can't be re-fetched later. Defines `Artifact{Filename, Bytes}`, a `Source` interface (`Fetch(ctx, date) ([]Artifact, error)`), `FuncSource` (adapter), `Writer` (writes raw bytes to `.archive/<source>/dt=YYYY-MM-DD/<filename>`), and a shared `Get` raw-fetch helper. Concrete source implementations live in each provider package: `ArchiveArtifacts(ctx, date)` in `internal/{hkb,projections,statcast,prospects}` covers HKB rankings, all four FanGraphs RoS systems (steamer-ros/depthcharts-ros/thebatx-ros/atc-ros, batting + pitching = 8 blobs), the five Baseball Savant CSVs (season plus 14d/30d rolling windows), and the FanGraphs prospect board. The `archive` CLI command (`cmd/archive.go`) runs all sources with per-source isolation — one failure doesn't block others; exits non-zero only if every source fails. Supports `--date YYYY-MM-DD` (default today UTC) and `--dry-run` (fetch + print sizes, write nothing). `.archive/` syncs to S3 `archive/` prefix via `statePairs` in `cmd/sync.go`, uploaded append-only (`del=false`, keep-forever). Distinct from the TTL cache (which overwrites on expiry) and additive to the projection snapshot/Analysis Store.

**`internal/report`** — pure aggregation package (no I/O, no rendering). Consumes `[]analysis.GradeRow` and produces a `Model`. The **detail dashboard** (`Views`/`Trends`, keyed `"window|role"`) is computed from the **`detailSystem` slice only** (`= analysis.LegacySystem` = `"depthcharts-ros"`, the bot's production system) so its meaning is unchanged; each `View` holds a `Scorecard` (MAE/Bias/RMSE/N), `[]PositionRow`, `[]CalibPoint`, `[]Miss`, plus a `[]TrendPoint` and rule-based `[]Insight`s. On top of that sits the **system-comparison panel**: `Compare` (keyed `"window|role"` → `[]SystemScore` ranked by **within-day Spearman rho descending**; `Best` is flagged only when the leader beats the runner-up by more than the combined standard error, otherwise the panel reports *too close to call*. **`Compare["<w>|all"]` is nil** — a pooled cross-role ranking has no defensible order, so the panel stacks the hitters and pitchers tables instead) and `CompareTrends` (keyed `"window|role"` → system → `[]TrendPoint`) span **every captured system**, driving the headline ranking table + overlaid per-system MAE trend lines. `Aggregate` normalizes empty-`System` rows to `detailSystem` (matching the reader's legacy attribution) so un-attributed input still feeds the detail views. `rankSystems`/`filterSystem`/`distinctSystems` are the comparison helpers. There is no `Render`/`template.html` anymore (Dashboard v2 deleted both) — the `Model` is serialized straight to JSON and the dashboard SPA owns presentation. The daily `ProjectionSite` EventBridge schedule (`cron(0 15 * * ? *)`, ~90 min after `grade`) runs `projection-site`, which reads from the Analysis Store, calls `report.Aggregate`, and **publishes the model to `STATE_BUCKET`'s `reports/` prefix** (`reports/model.json`) via `statestore.ReportsStore()` — **not** to the dashboard bucket's `report/` prefix, which CloudFront's default behavior serves unauthenticated (see **Private dashboard reports** below). The SPA's `projections.js` fetches it over `GET /v1/reports/model` and renders the scorecard/trend/calibration/misses/comparison views client-side (vendored Chart.js, ported from the deleted template's inline script — no recomputation, just reshaping the precomputed `Model` into DOM), surfaced as the native "Projections" tab (no iframe). Distinct from the recap's `SITE_BUCKET`, which remains its own separate site.

**Rank skill is the headline metric** (`internal/report/rank.go`, rosterbot-aei). MAE at player-day grain is near-blind to model skill: measured over 850 production rows, hitter MAE 4.380 *loses* to a constant-at-sample-mean baseline of 4.356 (−0.5% skill) because projections barely vary (sd 0.66) against daily outcome variance (sd 5.52). What the model does have is rank skill — exactly what a lineup optimiser consumes — so `RhoStat` carries the mean of per-day Spearman correlations plus its standard error, day count and days-positive. Three rules are load-bearing: **Spearman is tie-corrected** (average ranks, Pearson over ranks) because every player who didn't play sits at `actual = 0` and the `1 - 6Σd²/(n(n²-1))` shortcut is invalid under ties; **rho is never pooled across roles** — `View.Rho` and `SystemScore.Rho` are `*RhoStat` and nil for `role == "all"`, since a pooled number would reward knowing only that starting pitchers outscore bench catchers, which the optimiser never uses (it runs the two roles in separate passes); and **`minDayRows = 3` is a calibrated floor, not a guess** — the original spec proposed 5 without measuring it, which failed the reproduction gate on pitchers (most graded pitcher-days carry only 3-4 rows, so a 5-row floor discards 15 of 23 usable days and inflates rho to +0.53 on a collapsed 8-day sample); a threshold sweep against the same 850 rows shows 3 is where both roles are simultaneously well-supported (below it, 1-2-row days inject noise into the hitter mean; above it, the pitcher sample collapses toward a near-single-day statistic — see the sweep table in `rank.go`'s doc comment). `Metrics.SkillVsMean` (`1 - MAE/MAE_constantAtMean`) renders under the MAE tile so the demotion stays a daily-recomputed fact rather than an assertion. **Reproduced exactly against the production Analysis Store** (41 `dt=` partitions, 850 `depthcharts-ros` rows, 2026-07-30) at `minDayRows = 3`: hitter rho +0.1218 (SE 0.0373, 40 days, 30 positive) and pitcher rho +0.4292 (SE 0.0982, 23 days, 18 positive) — matching, to four decimal places, the +0.1218 / +0.4292 measured independently twice during triage.

**`internal/teamvalue`** — the durable **Team Value Store**: each fantasy team's aggregate HKB dynasty value for one day, as date-partitioned NDJSON (`dt=YYYY-MM-DD/values.ndjson`). Shares its NDJSON plumbing with `internal/analysis` via **`internal/ndjsonstore`**, but is single-entity (no `system` dimension), so the partition key is just `dt=` and the entity name lives in the S3 prefix (`analysis/team-values/`) / local dir (`.teamvalue/`). `teamvalue.Row` stores value as **four leaf cells** — hitter/pitcher × MLB/minors — plus matching count leaves and `RosteredCount`/`MatchedCount` (join-coverage transparency); `TotalValue`/`MLBValue`/`MinorsValue`/`HitterValue`/`PitcherValue` are derived methods. `teamvalue.Aggregate(date, pool, hkbPlayers, teamNames, teamLogos)` joins each rostered player (`FantasyTeamID != ""`) to its HKB `Value` by `playername.Normalize` (the same join as `claims`/`transactions`), buckets by Fantrax `MinorsEligible` (minors) and `positions.IsPitcherSlot` (pitcher; a two-way player with any pitcher eligibility resolves to pitcher), and denormalizes team name + logo into each row so the read+render path needs no Fantrax call. Unmatched rostered players increment `RosteredCount` only (value/count leaves are matched-only) and their names are collected into that team's `Row.Unmatched`, tagged `json:"-"` so the diagnostic never enters the durable NDJSON schema (a Row read back from the store round-trips with `Unmatched` nil, pinned by `TestNDJSON_RoundTrip`) — the dashboard's Matched column can only ever show the ratio it read off disk, so `cmd/team-values.go`'s `printTeamValueSummary` is the one place the actual names surface, printed on a follow-up line under any team with a shortfall for whoever reads the job log. `Writer`/`Reader`/`NewWriter`/`NewReader`/`NewFileWriter`/`NewFileReader`/`MarshalNDJSON`/`ObjectKey`. The series **accumulates forward** — HKB has no history and rosters aren't archived, so past compositions are unrecoverable; there is no backfill (see `docs/adr/0002-team-value-store-accumulates-forward.md`).

**`internal/valuereport`** — pure aggregation (mirrors `internal/report`; no I/O, no rendering). `BuildModel([]teamvalue.Row)` produces a `Model` (per-team `Series` of the four leaves + a `Latest` total-descending standings snapshot; stable per-team colors by sorted TeamID). There is no `Render`/`template.html` anymore (Dashboard v2 deleted both) — the `Model` is serialized straight to JSON. The `team-values` command (`cmd/team-values.go`) is the daily producer — fetches HKB + `GetFullPlayerPool` + `GetScoringPeriodsAndTeams`, calls `Aggregate`, and writes today's partition (S3 when `STATE_BUCKET` set, else `.teamvalue/`); it runs on the `TeamValues` EventBridge schedule (`cron(30 14 * * ? *)`, after `Archive`'s HKB refresh, before `ProjectionSite`). `cmd/projection-site.go`'s `renderValueSite` reads the store (reader chosen by `STATE_BUCKET`) and writes `value.json` to `--out`, published under `DASHBOARD_BUCKET`'s **public** `report/` prefix, soft-failing independently so a team-value hiccup never blocks the accuracy dashboard deploy. It is one of only two artifacts that stay public (with `football.json`), because a per-team dynasty-value standings table is league-wide information every manager can already read off Fantrax — unlike the three private reports beside it. The SPA's `value.js` fetches `report/value.json` and renders the multi-team Chart.js time plot with a **metric selector** deriving Total/MLB/Minors/Hitter/Pitcher client-side, a team legend toggle (+ All/None), and a current-standings table with logos and join coverage, surfaced as the dashboard SPA's native "Value" tab (no iframe).

**`internal/lineupgap`** — the durable **Lineup Gap Store**: how each day's applied lineup scored against the hindsight-optimal one, as date-partitioned NDJSON (`dt=YYYY-MM-DD/gaps.ndjson`) over `internal/ndjsonstore`, plus its own pure `BuildModel` (following `internal/recaplog`'s store-plus-model shape rather than the `teamvalue`/`valuereport` split, since the model is a few dozen lines of windowed sums). `Row` carries actual/optimal/gap points and started/benched counts; `Efficiency()` is derived. **There is no system dimension** — exactly one lineup was applied each day and hindsight-optimal doesn't depend on a projection system — so the partition key is `dt=` alone and the entity lives in the prefix (`analysis/lineup-gaps/` ↔ `.lineupgap`), mirroring `teamvalue`. The consequence: rho answers *which projection system*, the gap answers *what the whole pipeline costs*; they are complementary, not comparable. The producer is `cmd/grade.go`, which already holds the `DailyFantasyPoints` result and a live client (`projection-site` has neither), and calls the existing `backtest.RunLineupAnalysis`; the write **soft-fails** so a gap hiccup never takes down the irreplaceable grades. Unlike the Team Value Store it is `NoBackfill: false` — past-period roster snapshots are immutable and cached, so a missed day is recoverable with `grade --dates`. `cmd/projection-site.go`'s `renderGapSite` publishes the gap report to the private `reports/` prefix beside the model and views ones, soft-failing independently; the SPA's Projections tab leads with it, fetched over `GET /v1/reports/gap`. It is private for the most direct reason of any of the three: it is a running scoreboard of how many points the manager left on their own bench, which is precisely what a league rival would want.

**`internal/tradevalue`** — the pure n-sided trade-valuation leaf (imports only `fmt`, `math`, `sort`, `internal/hkb`). `Side.Raw()` is the plain HKB sum; `Side.Adjusted()` sorts assets descending and contributes the k-th at `Value × PackageDecay^k`. `Evaluate([]Side)` returns a `Verdict` under a three-branch rule: any unpriced asset → `incomplete`; the two methods naming different leaders → `too-close`; otherwise `favors`, with both percentages reported. **Withholding the call on disagreement is the point of the package, not caution** — on the live 2-for-1 that motivated it (Gage Jump 1391 + Emmet Sheehan 1234 for Kyle Harrison 2292) the raw sum favors you by 333 (+12.7%) and the decayed sum (1391 + 0.7×1234 = 2255) favors them by 37. A single number would have been confidently backwards. **`PackageDecay = 0.70` is an unmeasured prior**, fitted to *one* HKB screenshot (589+540+366 → 1144, ~0.2% residual) in the style of `certaintyMargin` in `internal/optimizer/gs_budget.go`; that is exactly why the adjusted figure never stands alone as the headline (rosterbot-492 is the follow-up to measure it). Percent difference is symmetric — `|a-b| / mean(a,b)` — which reproduces HKB's own reported 91.6%. `NewAsset("")` yields an unpriced `Draft pick (unidentified)`: Fantrax sends pick rows with an empty `playerName` (`internal/fantrax/client.go` appends them unconditionally, so an unresolved `scorerId` is a blank row, not a dropped one).

**Draft-pick identity recovery (rosterbot-uc3, closed 2026-08-11).** The empty `playerName` was never the whole story — the raw TRADE-view row also carries a `draftPickDisplayParts` field (`{year, roundInfo}`, both inline-HTML display strings) that the upstream parser discarded entirely; the go-fantrax fork now parses it into `Transaction.{IsDraftPick, DraftPickYear, DraftPickRound, DraftPickNumber, DraftPickOriginalTeam}`. Fantrax renders `roundInfo` two ways depending on whether the draft order is settled yet: `"Round N (Team)"` while the pick is still tied to that team's future standing, or `"Round N Pick M"` once resolved — the parenthetical team is the pick's *original* owner, not this trade's from/to, since a pick can be re-traded before it's ever drafted. `NewDraftPickAsset(year, round, pickNumber, originalTeam, players)` builds the priced `Asset`: HKB prices picks generically by projected slot (Early/Mid/Late per round: 18 assets, values 45–1419) rather than by team, and the recovered identity has no team standing to pick one of the three tiers over another, so `hkb.PickAverage` means whichever tiers HKB currently lists for that year+round and the result is flagged `Estimated` — a deliberately coarser number than a direct name match, in the same "disagreement over false precision" spirit as `PackageDecay`. A resolved pick (`DraftPickNumber > 0`) came from a draft that has already happened, which also means HKB has stopped listing it as upcoming — `PickAverage` reports zero tiers and the asset stays unpriced by construction, exactly as an unidentified pick did before this. `NewAsset` itself is unchanged and still used wherever identity truly isn't available (a bare empty-name row, or the pending-offer path via `internal/tradeboard`, which this ticket left untouched since no live pending trade existed to confirm `GetLeagueHomeInfoRaw` encodes pick identity the same way).

Measured over the league's 25 executed trade groups (2026-08-11, reproduced exactly by an independent Python implementation per rosterbot-aei), pick-tier averaging moved the corpus from **15 favors / 1 too-close / 9 incomplete** to **18 favors / 3 too-close / 4 incomplete** — 5 of the 9 pick-blocked groups carried a still-upcoming (2027) pick `NewDraftPickAsset` can now price (3 newly resolve to `favors`, 2 to `too-close`, since pricing a pick can flip the raw/adjusted leaders same as any other asset); the remaining 4 carried an already-resolved pick HKB no longer lists, so identity recovery named them without pricing them. The corpus is a live cache file that grows with every trade, so `corpus_test.go` asserts those exact counts only while the group count matches the baseline and otherwise falls back to the corpus-independent invariants (no HKB name-miss, non-degenerate verdict, pick-blocked incompletes only) — a gate that goes red on every league trade is one you learn to bump without reading. `internal/transactions` shares this package rather than carrying its own `side.Total += tp.Value`, so the Pushover report and the dashboard can never name opposite winners; the migration also turned `Trade.Sides` from a `[2]TradeSide` — which silently dropped every side past the second and was filled in random map order — into a name-sorted slice.

**`internal/tradeboard`** — the two artifacts behind the dashboard's Trades tab, plus the durable offer log. It **deliberately does not import `internal/fantrax`** (that would drag chromedp in); callers map their own rows onto `OfferInput`, the same constraint that forces `internal/opsalert` to redeclare its ledger fields. `BuildOffers` groups by `TradeID`, sides by receiving team, and prices each through `tradevalue`. `BuildValuesTable` joins every rostered player onto HKB by `playername.Normalize` and appends HKB's 18 pick assets as a league-wide reference list — picks cannot be attributed to a team because Fantrax never says who holds which. `BuildImpact` replays an offer against the `teamvalue.Row` set and reports my five value dimensions (Total/Hitters/Pitchers/MLB/Minors) before and after, with league rank in each; `addToLeaf` mirrors `teamvalue.Aggregate`'s bucketing exactly. **It returns `(nil, reason)`, never a partial answer** — and the reason is returned rather than swallowed because *pricing and placement are different requirements*: pricing needs only an HKB entry, placing a player in a value leaf needs their current Fantrax roster row. An offer can therefore be fully priced and still have no impact, observed 2026-08-09 with Heriberto Hernandez, who priced cleanly and belonged to no team. Without the reason the tab would quietly omit the section and look like it had decided not to bother. The **offer log** (`log.go`, `dt=YYYY-MM-DD/offers.ndjson` over `internal/ndjsonstore`) is the only record that a declined offer ever existed — Fantrax keeps none, hence `NoBackfill: true` — so it is written even on an empty window, both to advance outcomes and to keep the partition present rather than leaving a hole the Infra gap scan would flag. `InferOutcome` matches a vanished offer's `(player, To)` multiset against the executed feed and labels it `accepted` or **`not-executed`, never `rejected`**: withdrawn, expired and declined are indistinguishable in the data.

**Trades producers and cadence.** Two artifacts on two schedules, because the time-sensitive half is cheap and the expensive half cannot be fresher than HKB's own 8h TTL. `cmd/optimize.go` calls `captureTradeOffers` **hourly** after `lineuprun.Run` — one small league-home call, notably *not* the 10.7 MB player pool — writing `trades/current.json` and appending the log. `cmd/team-values.go` writes `tradevalues/values.json` **daily**, since that job already holds the pool, the HKB rankings and the team names. Both writes **soft-fail**, on the precedent of `cmd/grade.go`'s lineup gaps: a trades hiccup must never take down the hourly lineup apply or the irreplaceable Team Value Store write. The values table is built *before* the dry-run gate so `--dry-run` exercises everything but the write — a producer whose output only materializes in production can only be tested in production. **The pool's position string comes from `PosShortNames`, not `MultiPositions`**: the latter is populated only for players eligible at more than one *named* position, so Juan Soto (OF) and Paul Skenes (SP) come back empty and the Pos column shipped blank for 340 of 515 rows. Deriving from the `Positions` IDs is worse — everyone carries the UT flex slot and Fantrax hides it except where it is a player's only hitting eligibility. `positionDisplay` strips the markup upstream documents on that field (`<b>UT</b>,SP`) because the string lands in a durable JSON artifact.

**Trades API and tab.** `GET /v1/trades` and `GET /v1/trades/values` (`internal/lineupapi/trades.go`) pass the stored bytes through untouched, the same contract as `GET /v1/runs/{id}/progress`. They are on `/v1/*` and therefore passkey-gated **on purpose**: `report/*` is world-readable through CloudFront's default behavior, and an open offer is not something to publish before deciding on it. No new S3 adapter was needed — `s3lineup.Store` is already generic over its prefix despite the package name. The SPA's `trades.js` builds every row with `createElement`/`textContent` for the reason `views.js` documents. It renders **four** verdict states, not two: "too close" (the models disagree) and "cannot be priced" (an asset has no price at all) are different kinds of not-knowing and the tab says which.

**Private dashboard reports (`GET /v1/reports/{name}`, rosterbot-crq.3).** The Trades reasoning above generalized: three more of `projection-site`'s artifacts were the operator's own performance sitting on an unauthenticated URL. `model` (projection accuracy), `gap` (points left on the bench) and `views` (recap readership) now live in `STATE_BUCKET`'s `reports/` prefix — which no CloudFront distribution fronts — and are served by `internal/lineupapi/reports.go` through the same `serveBlob` passthrough as Trades. `value.json` and `football.json` stay on the public `report/` prefix: league-wide standings every manager can already read off Fantrax and Sleeper.

Three choices are load-bearing:
- **The bytes moved, rather than a CloudFront behavior being added to block them.** Blocking `report/{gap,model,views}.json` publicly would leave the private data in a bucket a distribution serves, one behavior edit away from re-exposure — and CloudFront path patterns have no "deny" primitive, so it would have meant an allowlist that a future filename silently falls outside of. **A path that is not served cannot be accidentally re-exposed.** The cost was a producer change; there was no `statePairs` change, because `reports/` is written per-key through `statestore.ReportsStore()` like `trades/`, not bulk-synced from a directory.
- **`{name}` is an allowlist (`reportNames`), not an echoed key.** Go's `ServeMux` already refuses a `/` inside a path segment, so this is the second lock; what it actually buys is that the route can never be widened into a general reader of the `reports/` prefix by adding an object to it.
- **One prefix for all three, unlike the two Trades artifacts.** The rule stated in `layout.go` is producer-and-cadence: Trades split because an hourly job and a daily job would otherwise be judged by whichever object is newest. These three share one producer and one schedule, so one age reading is honest. The residual gap — one of the three soft-failing while the others succeed does not move the Infra row — is recorded in the layout comment rather than papered over.

**Cutover is automatic and worth verifying.** `publishSite` mirrors `./report` with `--delete` scoped to that prefix, and `./report` no longer contains the three files, so the next `ProjectionSite` run deletes `report/{model,gap,views}.json` as orphans and invalidates the distribution. Until that run lands the stale public copies are still readable — so the post-deploy check is an unauthenticated `curl` of the three old URLs expecting 403/404, not merely a working dashboard.

**`internal/recaplog`** — recap-site readership. The recap site is **public and unauthenticated**, so CloudFront access logs are the only signal that anyone reads it; there is no session to attribute a view to, which bounds what this can honestly claim — **a client IP is a network, not a person**. `SiteCdn` writes standard logs to `RecapLogBucket` under `recaplog.Prefix` (`recap/`, which **must** match `LogFilePrefix` in `infra/infra.go` — changing one alone silently yields no data), expiring after 90 days. The package is a leaf: `Parse` (gunzip + positional TSV, skipping the `#Version`/`#Fields` lines and any malformed row rather than failing the object), `IsPageRead`, `BuildModel` and `ReadRecent` are pure over a byte-level `Store` seam, with the S3 implementation in `internal/recaplog/s3recaplog` (a shim over `internal/s3blob`, **read-only** — CloudFront is the only writer, and the task role's IAM is `GetObject` scoped to `recap/*`). `ReadRecent` walks keys **descending** — CloudFront names objects `<dist-id>.YYYY-MM-DD-HH.<hash>.gz`, so that is reverse-chronological to the hour — and stops once the limit is met, keeping the read bounded rather than growing with the retention window. **`IsPageRead` (status 200 + `/` or `*.html`) is load-bearing**: CloudFront logs every object, so without it the table fills with the `/favicon.ico` 403 that accompanies every real browser visit. Field positions are fixed by CloudFront's format and **must not be reordered**; the test fixture carries the real `#Fields:` header so a format change fails a test instead of silently shifting columns. `cmd/projection-site.go`'s `renderViewsSite` publishes the views report to the private `reports/` prefix beside the model and gap ones, soft-failing independently, and is skipped entirely when `RECAP_LOG_BUCKET` is unset (the normal local-dev case — these logs exist only in AWS, so a local `GET /v1/reports/views` correctly 404s). The SPA's `views.js` renders the "Views" tab from `GET /v1/reports/views`. **It builds rows with `createElement`/`textContent`, not `innerHTML`**, because `uri` is attacker-supplied — anyone can request a crafted path against a public site and land it in this table — and `render.js`'s `escapeHtml` escapes `&<>` but **not quotes**, so it is unsafe in an attribute context.

**Infra status (`GET /v1/infra`)** — the dashboard's "Infra" tab. `internal/lineupapi/infra.go` lists every prefix in `layout.All()` and judges each against its declared `MaxAge`, returning a per-artifact `Health` (`ok`/`gap`/`stale`/`missing`/`unknown`) plus object count, size, age, `dt=` partition count and sub-dimension values. It reads **live** rather than serving a precomputed file — deliberately, since a status page built from a scheduled artifact goes stale in exactly the situation it exists to detect and could report "all healthy" while the job that writes it is the thing that died. The listing itself is a one-method `InfraLister` seam: `s3lineup.NewInfra` on Lambda (a bucket-root `s3blob.Blob`, walked with an early stop at `maxKeys`), `lineupapi.NewFileInfraStore` for local `serve`. Every judgement lives in `lineupapi` and is unit-tested without AWS. Two derived signals do the real work: **gap detection** on partitioned series (scanning to *yesterday*, since today's producer may not have run yet), fatal only where `NoBackfill` is set; and **sub-dimension coverage** — the `system=` values under `analysis/grades/` and the per-source dirs under `archive/` — so one shadow system silently stopping shows as a missing chip rather than no error at all. IAM is `s3:ListBucket` only: the endpoint reports listing metadata and never reads an object body, so the Lambda still cannot read `session/` or `claims/` contents.

**`internal/notify`** — notification helpers. `SendPushover` sends push notifications via the Pushover API. Self-contained function taking explicit parameters (no config dependency).

**`internal/opsalert`** — decides whether a finished job run is worth waking an operator, and renders the message. A **stdlib-only leaf**: its only consumer is the `opsnotify` Lambda, and `internal/lineupapi` (where the run ledger's wire types live) transitively pulls `internal/fantrax` and therefore chromedp, so `opsalert.Record` redeclares the seven ledger fields it needs and `internal/lineupapi/opsalert_contract_test.go` (`package lineupapi_test`, so it can import both without `opsalert` importing `lineupapi`) marshals a real `lineupapi.RunDetail` into it to guard the duplication. `Streak(recs, command, userID)` reads newest-first ledger records and returns one of four verdicts: `Started` (first failure after a success), `Escalated` (the `EscalateAt`=3rd consecutive failure, matched on `==` so an eleven-failure outage escalates exactly once), `Recovered` (first success after failures), or `None`. **The whole decision is derived from the append-only ledger**, which is what removes the counter object and the cooldown timer a naive design needs — streak transitions deduplicate themselves. `RUNNING` records are skipped: they are the start-of-run write that the terminal write later overwrites at the same key, so an in-flight sibling job must not break a streak. The message body quotes the **last non-empty line** of the record's `log_tail`, capped at 300 chars *before* append because `SendPushover` truncates at 1024 silently — for the 2026-07-01 outage that line is the `STALE_CLIENT` error itself, which is the difference between "something broke" and a diagnosis.

**Heartbeat: the alert Streak structurally cannot produce (rosterbot-ys8).** `Streak` is reactive — an ECS task has to *stop* for the notifier to hear anything — so a job that never launches (disabled EventBridge rule, broken cron, unreachable cluster) emits no event, writes no ledger record, and produces perfect silence, which is indistinguishable from perfect health. `Overdue(recs, scheds, now)` inverts the direction: it asserts on a timer that every job has a run recent enough to be alive. Three rules are load-bearing:
- **Any status counts as "it launched"**, including `RUNNING` and `FAILED`. The question is strictly whether the job started; whether it then succeeded is `Streak`'s, and treating a failed run as a missed one would double-report every ordinary outage.
- **The lookback is bounded by *time*, not count** (`Horizon` = 2× the longest declared cadence; `ledgerReader.since` walks back to it and stops). A fixed record count is unsound here: the hourly Lineup job writes ~14 records/day, so a weekly job's perfectly healthy run sits ~180 records deep and a 200-record window would drop it on any busy week and report a live job as never having run.
- **Deduplication compares a token, not a key** (`MarkerKey` is per *(job, tenant)*; `AlertToken`/`NeedsAlert` compare the last-run id stored under it). A per-run key looks self-deduplicating and is not: every long outage eventually pushes its last run past the horizon, at which point the key moves and the same outage alerts again — once per horizon, forever. This was caught by a test, not by inspection.

The cadence table itself lives in `infra/infra.go` beside the crons it describes and reaches the Lambda through the `JOB_SCHEDULES` env var, because a tolerance restated in Go would drift from its schedule silently — surfacing only as an alert that never fires. The command string is the join key across all three sides: EventBridge passes it as the container override, `entrypoint.sh` joins argv with spaces into `run-ledger --command`, and `opsalert` matches that exact string.

**Both decisions key on `(command, user_id)`, not on the command alone (rosterbot-crq.1).** Under the per-tenant fan-out of `rosterbot-crq`, N tenants run the *same command string* into the one ledger, and a command-only key inverts both functions silently — the code compiles, runs and reports green. `Streak` walks newest-first where a SUCCESS breaks the streak, so a tenant failing *every* hour grades healthy on its neighbours' successes; `Overdue` keeps the newest run per command, so "Lineup ran recently" is true for everyone the moment any one tenant runs and a tenant whose task stops launching is invisible — the exact rosterbot-ys8 blindness one level down. `Record.UserID`/`Run.UserID` (`user_id`, omitempty) carries it; **empty is an ordinary tenant value, not a wildcard**, so the entire pre-fan-out ledger — where the field is absent from every object — keeps grading as the single tenant it describes, and a cutover ledger holding both keeps the two histories separate in both directions. Three consequences worth knowing: **which tenants `Overdue` asserts on comes from the ledger, not from `Schedule`** (a stdlib-only leaf cannot enumerate users, so the honest set is the tenants seen running that command within the horizon — meaning a tenant that never ran *even once* needs the identity store to detect, while one that ran and *stopped* is always caught); the heartbeat's `MarkerKey` gains the tenant but the **untagged key stays byte-identical**, so markers already in S3 keep deduplicating across the deploy; and the **task path's `dedupeKey` needs no tenant** — fan-out runs one ECS task per tenant per job, so the task id is already per-tenant, pinned by `TestEcsTaskDetail_DedupeKeyIsPerTaskAndThereforePerTenant`. The task path takes the tenant from the stopped run's **own terminal ledger record**, since the ECS event carries none.

**Alert deduplication across deliveries (rosterbot-chs).** EventBridge can deliver one event more than once and async-invoke retries on a returned error; since the verdict is a pure function of a ledger that does not move between deliveries, a repeat recomputes the identical alert and pushes it again. `opsnotify/marker.go` records sent alerts under the `opsalert/` S3 prefix (its own prefix, not `notifications/` — that one is the user-facing feed the dashboard serves). Two invariants: the order is **check → send → mark**, never claim-then-send, because a claim taken before sending must be released on failure and a failed release leaves a permanent suppression — trading a duplicate alert for a missing one; and **every marker-store failure degrades to a duplicate, never to silence**. The task path keys on the **task id alone, not id+`detail.version`** — AWS documents version for exactly this, but ECS can emit several distinct STOPPED events for one task as container state settles, and those are not duplicate deliveries, so version would let each through even though they describe one dead run. Version is written into the marker body instead, where it dates the delivery that won without weakening the key. The prefix expires on a 30-day lifecycle rule, far past EventBridge's retry horizon.

**`internal/roster`** — `CheckRoster` scans the full roster for slot mismatches (healthy players in IL, called-up players in Minors, injured/minor-leaguers in active slots). Suppresses alerts when IL/Minors slots are full. Separate from prospect report — this is about current roster hygiene.

**`internal/schedule`** — hits `statsapi.mlb.com` for game schedule and probable pitchers. `TeamsPlayingOn` returns a `map[string]bool` of playing team abbreviations. `ProbableStarters` returns normalized pitcher name → team abbreviation. Both URLs are `var` (not `const`) to allow test overriding.

**`internal/optimizer`** — pure functions, no I/O. Two parallel optimizers:
- **Hitters** (`OptimizeLineup`): backtracking with pruning to find globally optimal slot assignment maximizing total expected points. Checks `PtsPerGameSource` (type assertion) before falling back to `expectedPts`. `EligibleForSlot` in `fantrax/client.go` handles UT (accepts any hitter) and INF (accepts 1B, 2B, 3B, SS — not C).
- **Pitchers** (`OptimizePitcherLineup`): sorts by hasGame → expectedPts → ID, then assigns to slots. Uses probable starter data to determine if SPs start; when no probable data is available (future dates), SPs default to "has game" if their team plays. Accepts an optional `*GSBudget` for weekly game-start limit awareness.

**Scoring model** — this league scores: `1B`, `2B`, `3B`, `HR`, `RBI`, `R`, `BB`, `SB`, `CS`, `HBP`, `SO`, `GIDP`, `XBH`, `TB`, `CYC`. The stat→points algebra lives in **`internal/scoring`** (the single source): `ApplyHitter`/`ApplyPitcher` take a neutral `HitterLine`/`PitcherLine` of raw counts, derive `1B = H - 2B - 3B - HR` (floored at 0), `XBH = 2B + 3B + HR`, `TB = 1B + 2×2B + 3×3B + 4×HR`, and apply the league weights. The package imports nothing else (so both `fantrax` and `projections` can depend on it without a cycle); `fantrax.ScoringWeights` is a type alias for `scoring.Weights`. Callers adapt their source to a stat line: `projections.ExpectedPtsFromProj`/`PitcherExpectedPtsFromProj` build a line from a projection and divide by games (scoring is linear, so per-game = total/G); the `mlb_backfill` game-log scorers build a line and don't divide (single game). `optimizer` and `waivers` consume these rather than re-implementing the math.

**GS budget** — weekly game-start limit awareness (`GS_TRACKING_ENABLED` env var, false = disabled). When enabled, the pitcher optimizer resolves today's scoring period and fetches its real GS max via `GetGSLimits`, gating SP starts to avoid exhausting the weekly GS allocation on low-value starters while better aces pitch later in the matchup week. A live-fetch error sends a Pushover alert (`PUSHOVER_USER_KEY`) and disables the gate for that run rather than falling back to a stale static number; no configured max just disables the gate silently (nothing to track).
- **Matchup week boundaries** derived from `GetAllMatchups()`: consecutive daily scoring periods where the team faces the same opponent form a matchup week. Computed in `fantrax/matchup_weeks.go` via `MatchupWeekBounds`.
- **Past GS counting**: for each past day in the current matchup week, the `ProbableStarters` API is checked to count how many rostered SPs started.
- **Future demand forecasting** uses a hybrid approach: days with confirmed probable starters use exact counts; days without probables estimate `min(roster SPs whose team plays / 5, active P slots)` (standard 5-man rotation). **The slot cap applies to starts, i.e. after the division, not to the pitcher count before it** — capping first mixes units and understates every day where more rostered SPs have a game than there are pitcher slots (rosterbot-abd: 10 rostered SPs against 6 slots pinned every such day at 1.2 instead of 1.4–2.0).
- **Value-ranked gate** (`optimizer/gs_budget.go`, `applyGSGate`): when remaining budget can't cover every planned start (today + future confirmed + future estimated), pools all of them into one ranking by expected points and keeps only the top `remaining` by value — it does not split the budget proportionally by day/count. Future days without announced probables contribute `ceil(Estimated)` placeholder entries valued at the roster-wide mean SP projection (a real projection, not a scrub), **priced as a marginal-value ladder**: the k-th such entry is worth `placeholder × min(max(Estimated-(k-1), 0), 1)`, i.e. full value while whole units of expected demand remain and the leftover fraction after that. So `Estimated = 1.4` emits one entry at full placeholder and one at 0.4× it. **The weight belongs in the price precisely because the cut spends a whole slot** — the gate's question is "hold this slot or spend it today?", and holding is worth `placeholder × min(E,1)` in expectation against a certain value today. This reads like a units error (every other entry is points-per-start; this one is points × probability) and was filed as one, but pricing the tail at full value would bench a certain 8-pt start to hold a slot for a 20%-likely 12-pt one — and since weekly GS is use-it-or-lose-it, the other 80% is burned, not banked (**rosterbot-idn**, closed as not-a-bug; two tests in `gs_budget_test.go` pin the ladder and fail under the full-value form). Ties prefer today's starters (a certain start) over future ones, then break on player ID. **`certaintyMargin = 0.10`** extends that tie preference to near-ties: an *estimated* future entry must beat today's value by more than 10% to outrank it (confirmed future starts are as certain as today's and are excluded). It prices `P(the estimated start never materializes)`, **not** projection error — SP projection MAE is large (10.4–13.8 FP/G against an SP mean near 12) but symmetric, and haircutting an unbiased estimate biases the ranking rather than de-risking it. The 0.10 itself is an unmeasured prior, not a fitted value. Starters that don't make the cut have `IsStarter` flipped to false, applying the existing `NonStarterSPDiscount` (0.05x). Uses `eps = 1e-9` for float comparison consistency. Locked players are exempt from suppression (their GS is already decided one way or the other).
- The gate only applies to today's optimization (the daily GHA run). Future dates in `--dates` ranges are optimized without the gate since each day gets its own run.
- The `--matchup` flag on the optimize command resolves to all remaining days in the current matchup period (from today through the matchup week end).

**`internal/lineuprun`** — the shared orchestration engine behind both the `optimize` and `shadow` CLI commands: fetches rosters/projections, runs the hitter and pitcher optimizers per date (the parallel `errgroup` pass over `cfg.Dates`), archives projection snapshots, publishes the read-only lineup API JSON, and prints + applies the resulting moves. `Run(ft, cfg, opts)` takes an explicit `Options` struct (projection system, `--dates`/`--matchup` resolution flags, pipeline-detail toggle, snapshot behavior, cache/verbosity) — there is no package-level mutable state shared between callers. `cmd/optimize.go` (a single real/dry-run pass) and `cmd/shadow.go` (one dry-run capture per RoS system, looped) are both thin cobra adapters that parse flags, call `initApp`, build an `Options` value, and call `Run`. `Options.SnapshotRoot` is the exact directory a run's projection snapshots are written into — always set explicitly by the caller (`optimize` passes the flat `.backtest/snapshots/` path; `shadow` passes a per-system partition each loop iteration) — and `Options.ForceSnapshot` is a separate explicit boolean (`shadow` sets it so a capture run always writes regardless of dry-run). This replaced a former package-level `captureSystemRoot` var in `cmd/optimize.go` that `cmd/shadow.go` mutated to redirect snapshot output (its emptiness used to double as both "not in shadow mode" and "use the default directory"), plus a parallel `lastProjectionLoadResult` var that let `shadow` observe per-system projection-data availability only because `runOptimize`'s signature was fixed by cobra — `Run` returns a `Result{HittersNoData, PitchersNoData}` instead (**rosterbot-zbi**).

**Named phases (rosterbot-6rv, complete).** `Run` is a composition of phases, each owning an interface narrow enough to test without a Fantrax client. In pipeline order: **`ResolveDates`** (`dates.go` — expands `--dates all` / `--matchup` and returns the list as a *value*; `Run` no longer writes back into `cfg`), **`LoadInputs`** (`inputs.go` — the six roster/slot/scoring fetches plus the current-period and weekly-periods lookups, returning one typed `Inputs`), **`BlendSources`** (`blend.go` — wraps the base projection sources with recent production), **`ComputeGSBudget`** (`gsbudget.go` — the whole GS fetch cascade), **`OptimizeDates`** (`optimize_dates.go` — the parallel per-date pass, returning `[]dateResult`), **`Emit`** (`emit.go` — snapshot, publish, print, apply, notify). `Run` is 309 lines, down from 1201. Two conventions hold across the phases and are worth preserving:
- **Side effects are returned as decisions, not performed.** `ComputeGSBudget` returns a `GSAlert` for the caller to send rather than calling Pushover itself; `BlendSources` and `ComputeGSBudget` return `Logs []string` rather than writing to the progress display. That is what lets every failure branch be asserted without credentials or an HTTP server. `LoadInputs` is the deliberate exception — it takes a three-method `inputsProgress` because its phase completion has to land *between* two groups of its own log lines.
- **Failure policy is stated once per phase.** `LoadInputs`: the six roster/slot/scoring reads are fatal, the two period lookups are soft and ride along on `Inputs`. `ComputeGSBudget`: every failure disables the gate and none falls back to a stale limit; the live-limit fetch failure additionally requests a Pushover. `BlendSources`: each role falls back to its base source independently.

**`Emit` gates the live write on a type, not on statement order (rosterbot-k0n).** `Emit` is the only phase that mutates remote state, and its one load-bearing ordering constraint — the zero-gain delta check must precede `ApplyLineup` — is expressed in the signature: `applyLineupFor` requires an `applyAuthorization`, and the only way to get a non-inert one is `datePlan.authorize()`, which refuses any disposition but `movesWorthApplying`. Go can't stop a struct literal inside the package from forging one, so the zero value is inert and `applyLineupFor` refuses a nil plan; `TestApplyLineupFor_RefusesAnUnauthorizedApply` pins that. **Why the zero-gain guard exists at all:** the optimizer can construct cosmetic swaps among equally-valued bench players, and Fantrax rejects a payload *atomically* if any player in it is per-player-locked — so submitting a worthless swap can drop genuinely valuable moves alongside it. `Emit` also takes its Pushover sender as an injected `Notify func(string)`, so the apply-path tests never reach the network.

Snapshot archival and lineup publication read the same already-computed results and write to unrelated destinations — **verified independent**, despite the ordering the original issue assumed; neither blocks the other on failure. They precede the apply loop because they describe what the optimizer decided and should be durable whether or not the apply lands.

**The published lineup carries HKB age/value, and every part of that path is optional by construction.** `LoadHKBMeta` (`hkbmeta.go`) maps `hkb.GetPlayers` into `map[string]lineupapi.Dynasty` keyed by `playername.Normalize` — the same join key `claims`/`transactions`/`teamvalue` use, and the one `lineupapi.Build` looks up by via `projections.NormalizeName`. Three properties hold it together. It is **gated on the same condition `publishToday` applies** (`Publisher != nil && (!DryRun || PublishLineupFlag)`), so a shadow run or an ordinary dry-run never pays for a fetch it would discard. Its failure is **soft** — a scrape outage logs a warning and publishes without the columns, because this is decoration on a lineup the optimizer already decided, the opposite of `LoadInputs`' six fatal roster reads. And `Player.Age`/`Player.HKBValue` are **`omitempty`, with zero meaning "HKB has no row"** for both: a client that read 0 as an age would be reading a miss as a measurement, and the miss is routine (a call-up too new for HKB's rankings — the known-unfixable gap `internal/playername` documents). The keying is split into the pure `hkbMeta` and tested through the real lookup side rather than by comparing key strings, since a join key that stops matching is silent — the whole column empties while every player still renders.

**`LoadInputs` fetches concurrently.** The eight reads run in one `errgroup`. Log lines and the phase completion are emitted *after* the group joins, in the original fixed order, and fatal errors are checked in that same order — so neither terminal output nor the error an operator sees depends on which response lands first. This is also why `fantrax.Client.getLeagueInfo` is mutex-guarded: four of these six fetches share that memo.

**Rendering takes an `io.Writer`.** `Options.Out` (nil → `os.Stdout`) carries through `renderDateResult` and every print site in `Run`; `cmd` supplies `os.Stdout`. The board's ~280 lines of positional box-drawing are golden-tested against `internal/lineuprun/testdata/*.golden` — regenerate with `go test ./internal/lineuprun/ -run TestRenderDateResult -update` and **read the diff, it is the review**. Column widths come from `displayWidth`, which measures each rune's East Asian Width (`golang.org/x/text/width`): **Wide/Fullwidth count two columns, Ambiguous counts one**. Ambiguous-as-one is the load-bearing half — the board's box-drawing and marker glyphs (`─ ═ ║ ╔ · ★`) are all Ambiguous and must stay single-width. Codepoint range is not a usable proxy for this and the earlier "BMP ⇒ single-width" rule mis-measured `❌` (U+274C, BMP but Wide), shifting the `│` separator one cell right on every real-life-benched hitter's row (rosterbot-h9q).

**Verifying a change here.** Unit tests do not cover `Run`'s composition, so every change to this package is checked by building a binary from the last good commit into the scratchpad and diffing `--dry-run` output for `--pipeline`, `--matchup` and an explicit `--dates`. Two gotchas that have produced a false regression: use **identical** stream redirection for both binaries (`2>&1` on both), and run them **back-to-back** — live projections and probables drift within the hour and look exactly like a refactor bug.

**`internal/progress`** — live run-progress recording, layered on top of the existing terminal progress bar (`Progress.Start`/`Done`/`Warn`). `Recorder` is a nil-safe package-level hook (mirrors `lineupapi`'s `OutputRecorder` pattern): every phase transition also builds a `Snapshot` (`{phase, pct, phases:[{name,state}], status:"running", updated_at}`, ordered per `PipelinePhases`/`phaseWeight`) and hands it to `Recorder` if one is installed. `cmd/progress.go`'s `installProgressRecorder()` wires it from `RUN_ID`, writing to `runs/<id>/progress.json` — S3 via `internal/lineupapi/s3lineup.NewProgress` (`STATE_BUCKET` set) or locally via `lineupapi.NewFileProgressStore(".lineup/progress")` — and is a best-effort no-op if `RUN_ID` is unset or the store errors. `internal/lineupapi`'s `GET /v1/runs/{id}/progress` route (`ProgressStore.GetProgress`) serves that snapshot, `404` when absent. **Run status stays ledger-owned** — `progress.json` only adds phase detail on top of the `runledger/`-backed `GET /v1/runs`/`GET /v1/runs/{id}` status, never replaces it. Only `optimize` calls into `internal/progress` today (it's wired through `internal/lineuprun`'s pipeline phases); the other allowlisted jobs emit no progress file, so the dashboard SPA's live hero (`web/dashboard/live.js`) falls back to an indeterminate bar for them on the `404`. No new IAM: writes ride the existing `runs/` S3 prefix the run ledger and per-run output already use.

## Dynasty Football

The bot's second sport, added rosterbot-mx6: Sleeper (league/roster state, public read-only API, no key) + StatsGuy (dynasty valuations, `api.statsguyfantasy.com`, no key). **Read-only throughout** — Sleeper's public API has no lineup-write endpoint, so unlike the baseball side there is no optimize-and-apply spine here, only a value store and a trade monitor. `internal/fantrax`, `internal/optimizer`, and everything under "Scoring model" below are baseball-only and untouched by this section.

**`initShared`/`initFootball`** (`cmd/root.go`, `cmd/football_init.go`) — `initApp`'s sport-agnostic middle (cache store wiring, cache-notify, the three activity recorders) was extracted into `initShared()`, called by both `initApp` and the new `initFootball()`. Football commands therefore need **no `FANTRAX_*` env vars at all** — `initFootball` never calls `config.Load`, which would otherwise fail outright without them. New env: `SLEEPER_LEAGUE_ID` (required), `DYNASTY_FORMAT` (default `sf_dynasty`; the StatsGuy format a command's own summary reads — the Dynasty Value Store itself carries all four formats on every row regardless), `FOOTBALL_PUSHOVER_USER_KEY`/`FOOTBALL_PUSHOVER_GROUP_KEY` (default to the base `PUSHOVER_USER_KEY`/`PUSHOVER_GROUP_KEY` pair).

**`internal/sleeper`** — read-only Sleeper client, mirroring `internal/schedule`'s shape (URLs as `var` for test override, `Client{http, CacheDir}`, plain non-context methods). `League`/`Rosters`/`Users`/`TradedPicks`/`Transactions(week)`/`State` cache at `RosterTTL` (15 m — "today, drifts during the day", the same cadence as Fantrax's `todayTTL`); `PlayersNFL` (the full ~14.6 MB NFL player dump, no filter param) caches at `PlayersTTL` (24 h) and must never be called in a loop. `Player.SearchRank` is Sleeper's own depth-chart ranking (lower = more relevant), used only as the starter-selection fallback (see `internal/dynasty` below) — never for pricing.

**`internal/statsguy`** — the dynasty value provider, named after its provider like `internal/hkb`. Base URL is `api.statsguyfantasy.com`, **not** `statsguyfantasy.com` (that domain serves the Next.js SPA shell for `/api/*`). `LoadBundle` fetches `/api/v1/players` (~396 players — 13% of Sleeper's active skill-player universe; no K/DEF/IDP) and `/api/v1/picks` (120 priced pick-tier entries: `"early"`/`"mid"`/`"late"` variants per round for unresolved future picks, plus resolved-slot entries once a draft order settles) and joins into a `Bundle`. **`CacheTTL` is a single exported constant (8 h)** — CLAUDE.md's own lesson from the baseball side (a TTL re-typed as a bare literal at six call sites meant the named constant governed only a quarter of what it appeared to) is what dictated this from the start rather than repeating it. **StatsGuy's player `id` is the Sleeper `player_id` exactly** — measured 2026-08-10, 396/396 valued ids resolve against Sleeper's player dump — so joining players needs no name normalization, unlike every HKB/Fantrax join elsewhere in this repo.

**`internal/dynasty`** — the durable **Dynasty Value Store** (`Row`, one per `(date, team, asset)`) plus `Aggregate`, `SelectStarters`, and the trade grader, following `internal/lineupgap`'s store-plus-model shape rather than `teamvalue`/`valuereport`'s split. **Grain is per-player, not per-team** (`teamvalue.Row`'s shape) — deliberately, so every future breakdown is re-derivable from the stored rows without re-aggregating, and unlike the Team Value Store (`docs/adr/0002`, `NoBackfill: true` — HKB has no history) this store is **not** `NoBackfill`: both the Sleeper roster snapshot and the StatsGuy bundle are re-fetchable, so a missed day is re-runnable. `Row` carries **all four StatsGuy formats as leaves** (`ValueSFDynasty`/`ValueNonSFDynasty`/`ValueSFRedraft`/`ValueNonSFRedraft`) so the dashboard derives the format toggle client-side, matching `teamvalue.Row`'s hitter/pitcher × MLB/minors pattern. `Row` has **no `Unmatched` field at all** (stronger than `teamvalue.Row.Unmatched` round-tripping to nil) — the per-team join-coverage diagnostic (`RosteredCount`/`MatchedCount`/`Unmatched`) is a separate `Coverage` type `Aggregate` returns alongside the rows, since Row's grain is per-asset and there is no natural per-team row to attach it to.
- **`AggregatePlayers`** joins rostered players to the StatsGuy bundle by **exact Sleeper `player_id`** (no normalization — see `internal/statsguy` above). An unmatched player increments the team's `RosteredCount` only and is named in `Coverage.Unmatched`; it produces no `Row` (there is no value to record).
- **`SelectStarters`** tags `IsStarter` from `roster.Starters` (the manager's own lineup selection, filtered of Sleeper's `"0"` empty-slot placeholder), falling back to the `StarterSlotCount` lowest-`SearchRank` players **only** when `Starters` is empty. **Never StatsGuy value** — choosing starters by value would make an unvalued player unselectable and starters-coverage 100% by construction, the exact rosterbot-hx5 failure (a metric that can only emit one value on the data that matters isn't a measurement) this design exists to avoid.
- **`AggregatePicks`** reconstructs every team's owned future picks from `traded_picks` + `league.Settings["draft_rounds"]`: ownership defaults to identity (each team owns its own picks each round/year) and a `traded_picks` record overrides it (Sleeper reports current ownership, not history, so at most one record applies per `(year, round, original owner)`). Draft years come from **whatever years StatsGuy's own grid prices** (`distinctPickYears`), not a hardcoded lookahead. Every pick prices via **`MidVariantPrice`** (`bundle`, `year`, `round`) → the `"mid"`-variant tier, flagged `Estimated: true` — there is no draft order yet for an unresolved pick, so there is no team standing to prefer `"early"`/`"late"` over `"mid"`. `MidVariantPrice` is shared with the trade grader (below) so the store and a trade alert can never price the same pick differently. A round with no `"mid"` price in the bundle is silently skipped, not a crash (measured 2026-08-10: zero of 58 live traded-pick records fell outside StatsGuy's priced grid).
- **`GradeTrade`/`BuildTradeSides`** — the football-trades command's local-sum trade grader. `BuildTradeSides` groups one Sleeper trade transaction's assets (players via `Adds`, picks via `DraftPicks` priced through `MidVariantPrice`, FAAB via `WaiverBudget` as an **always-unpriced** asset — StatsGuy prices dynasty players and picks, not cash) by receiving roster. `GradeTrade` is **deliberately two-branch** (`TradeFavors`/`TradeIncomplete`), not baseball's `tradevalue.Evaluate` three (`favors`/`too-close`/`incomplete`): `tradevalue.PackageDecay` is explicitly **not** ported here — it is documented on the baseball side as "an unmeasured prior, not a measured value" fitted to one HKB observation (rosterbot-492 is open to measure it properly), and StatsGuy's own `/trades/evaluate` applies no decay (measured: `9361+1757=11118` exactly, a plain sum), so local summation is arithmetically identical to calling it. With only one pricing method there is no second method to disagree with, hence no `too-close` state. Any unpriced asset on any side → `TradeIncomplete` (the same verdict-suppression discipline as `tradevalue.Evaluate`); football's own picks are ~100% priceable where baseball is pick-blocked on 36% of verdicts, so this branch should rarely fire from picks — FAAB-only trades are the more likely source now that FAAB is modeled at all. **A trade where every side totals zero assets is also `TradeIncomplete`, not a 0-0 "favors" tie** — found on a real live-league 3-way trade during verification: with no defensive check, `Raw()==0` on every side still sorts to a lexical "winner" at a nonsensical `+0%`/`+200%`-style margin, the same rosterbot-hx5 failure shape (a statistic confidently answering a question that had no real input).

**Starters Value is the headline, not the full-roster total** — the gate pre-commitment from the 2026-08-10 coverage-gate spike (bd memory `dynasty-football-coverage-gate-2026-08-10`; see also the *Starters Value*/*Coverage Spread* glossary entries in `CONTEXT.md`). Measured against the real league: starters coverage was 100% on all 12 teams that day (PASS, ≥95% target) — re-verified 2026-08-11 at 11/12 teams still 100%, the twelfth having genuinely shifted its live roster since — while full-roster coverage spread was 21.1pp (best 100.0%, worst 78.9%; FAIL against a ≤10pp target). Reporting the full-roster total as the headline would silently understate rosters carrying more unvalued bench/depth players without saying so. The full-roster total still ships (both `football-values`' printed summary and the dashboard's Football tab), visually demoted beside its own matched/rostered coverage counts, rather than hidden — the choice was disclosure, not suppression, mirroring how the baseball side's `roster-shape` line handled its own denominator-coverage gap (rosterbot-8dl).

**`Coverage` is persisted, not just printed** (`coverage.ndjson`, written by `football-values` alongside `values.ndjson` in the same date partition, via `Writer.WriteCoverage`/`Reader.ReadAllCoverage`). This was a real gap discovered while building the dashboard tab: `Row`'s per-asset grain cannot reconstruct `RosteredCount` after the fact — an unmatched player produces no `Row` at all — so the coverage counts the dashboard needs to show ("matched/rostered counts... gate pre-commitment") only exist if captured at write time, unlike `teamvalue.Row`, whose per-*team* grain carries `RosteredCount`/`MatchedCount` directly. `Coverage.Unmatched` still carries `json:"-"`, same discipline as `teamvalue.Row.Unmatched` — only the counts are durable, never the diagnostic name list.

**`dynasty.BuildModel`** (`model.go`, same package as the store per `internal/lineupgap`'s precedent — this is the "...and model" the package's original ticket named) rolls the latest date's rows + coverage into `Model`/`TeamStanding`: both Starters Value and the full-roster total, all four StatsGuy formats each, plus the coverage counts, sorted by `StartersSFDynasty` descending. No historical series (unlike `valuereport.Model`) — the gate pre-commitment this renders is a same-day standings question, not a trend, and the store is new enough that there's no history to chart yet.

**`renderFootballSite`** (`cmd/projection-site.go`, a sixth sibling alongside `renderValueSite`/`renderViewsSite`/`renderGapSite`) reads the Dynasty Value Store's rows and coverage, calls `BuildModel`, and writes `football.json` — soft-failing independently like every sibling, so a football hiccup never blocks the accuracy dashboard deploy. **`web/dashboard/football.js`** renders it as the native "Football" tab: a client-side format toggle (re-sorting by the selected format, since the JSON is only pre-sorted by `sf_dynasty`) and a standings table. Built with `createElement`/`textContent` throughout, **not** `innerHTML` — `views.js`'s rule, not `value.js`'s (the latter predates the discipline and still uses `innerHTML`+`escapeHtml`, which does not escape quotes and is unsafe in attribute contexts). Verified live in a real browser against production-shaped data (WebAuthn bypassed at the DOM level for local testing, the same technique rosterbot-81n used): correct sort, correct format-toggle re-sort, correct coverage warn-coloring, zero new console errors, and an `{empty:true}` response renders the same "collecting data" message `views.js` uses for its own empty case.

**`football-values`** (`cmd/football_values.go`) — the daily producer. Fetches the Sleeper league/rosters/users/traded-picks/players, loads the StatsGuy bundle, calls `dynasty.Aggregate`, and appends today's rows to the Dynasty Value Store: local `.footballvalue/`, or S3 `analysis/football-values/` when `STATE_BUCKET` is set (`statestore.FootballValueWriter`/`Reader`, following the `TeamValueWriter`/`Reader` `pick[T]` precedent exactly). Runs 14:45 UTC — after `Archive` (14:15) and `TeamValues` (14:30), before `ProjectionSite` (15:00) reads it, the same staging `TeamValues` uses. `layout.FootballValues` is `Durable`, 2-day `MaxAge`, and **not** `NoBackfill` (per-player grain is re-derivable, unlike `TeamValues`). Unlike `cmd/sync.go`'s `statePairs` bulk dir↔prefix sync, this store — like `teamvalue` — writes per-key directly via its typed statestore constructor, so `.footballvalue/` is deliberately **absent** from `statePairs`.

**`football-trades`** (`cmd/football_trades.go`) — polls Sleeper transactions for newly completed trades and pushes a graded Pushover alert (to `FootballPushoverUserKey`, matching baseball's own `internal/transactions` "Trade Alert" precedent — personal, not the league-wide broadcast `PushoverGroupKey` role plays for `gs-check`). **`pollWeeks`** polls week 1 through the current week (`sleeper.NFLState.Week`), not just the current week: Sleeper's transaction round-bucketing for offseason/preseason trades was an open question at design time (`state.week` was 1 / `season_type` `"pre"`), and re-polling old weeks is nearly free — the dedup marker keys on `transaction_id` regardless of which week surfaces the record. **Idempotent via one dedup marker object per `transaction_id`** under `football/trades/` (`layout.FootballTrades` — `Durable`, deliberately **no `MaxAge`** and **absent from `All()`**, mirroring `Progress`'s exclusion: markers are written only when a trade happens, so a quiet league writes nothing for weeks and any age check would misread the normal case as stale), written **check → send → mark**, never claim-then-send (rosterbot-chs) — a marker-store failure degrades to a duplicate alert on the next poll, never to silence. `statestore.FootballTradeMarkers()` reuses the existing `lineupapi.BlobStore`/`blobStore` machinery (`Get`+`Publish`, the same seam `TradesStore`/`TradeValuesStore` already use) rather than inventing new storage infra. `--dry-run` skips both the send and the mark entirely (not merely the send) — marking during a dry-run would be unsafe: a later real run would see the marker and silently skip a trade that was never actually alerted. Verified live against the real league: two consecutive real (non-dry-run) runs are idempotent by construction (run 1: N graded/sent, run 2: N already-alerted/0 sent).

## Idempotency

The optimizer must produce identical output given the same inputs. Key invariants:
- **Stable sort**: player ranking uses player ID as tiebreaker (`scored[i].Player.ID < scored[j].Player.ID`) so equal-scoring players always appear in the same order.
- **Epsilon comparison**: the backtracking optimizer uses `eps = 1e-9` for floating-point comparison to avoid flip-flopping between equivalent assignments.
- **Minimal changes**: when two assignments produce the same total points (within epsilon), the optimizer prefers the one with fewer roster moves (`changes < bestChanges`).
- **Period-specific roster**: for future dates, the optimizer fetches the roster for that period (`GetHitterRosterForPeriod`) so it sees already-applied lineups. A second run with the same inputs produces "No changes needed".
- **Verification**: after any optimizer change, run the command twice with the same inputs and confirm the second run shows "No changes needed" for all dates.
