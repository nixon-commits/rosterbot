# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make build              # build binary + lambda module (or: go build -o rosterbot .)
make build-modules      # cross-compile every nested Go module (lambda/, opsnotify/, infra/)
make check-pins         # assert shared `replace` pins agree across all four go.mod files
make lint               # golangci-lint across all four modules (hard-fails if not installed)
make lint-install       # install the pinned golangci-lint (GOLANGCI_LINT_VERSION in the Makefile)
make install            # install to $GOPATH/bin
make test               # run all unit tests (or: go test ./internal/...)
go test ./internal/optimizer/...  # run a specific package's tests
make dry-run            # run optimizer locally without applying changes
go run . optimize --dry-run --dates 2026-04-01  # test a specific date
go run . optimize --dry-run --dates 2026-03-26:2026-03-28  # test a date range
go run . optimize --dry-run --dates all  # test full season from today
go run . optimize --dry-run --matchup    # test remaining days in current matchup period
go run . prospects --dry-run  # run prospect report locally
go run . gs-check --dry-run          # check league-wide GS violations for the most recently completed period
go run . transactions --dry-run      # check recent trades with HKB valuations
go run . waivers --dry-run           # Statcast-driven free-agent picks (top 15 by default)
go run . waivers --dry-run --top 25 --positions OF,SP   # bigger list, position filter
go run . backtest                                    # backtest last completed matchup week
go run . backtest --dates 2026-04-13:2026-04-19      # backtest a specific window
go run . backtest --skip-projections                 # lineup-only backtest (faster)
go run . optimize --dry-run --snapshot               # write projection snapshots in dry-run (non-dry-run runs write by default)
go run . recap --out /tmp/recap.html                 # render weekly HTML recap (most recent completed week)
go run . recap --dates 2026-04-20:2026-04-26 --out /tmp/recap.html  # specific window
go run . recap --out /tmp/recap.html --open          # render and auto-open in default browser
go run . recap-site --out dist                       # render every completed week into a static site dir
go run . recap-site --out dist --open                # build site and auto-open dist/index.html
go run . shadow                                      # capture today's projections from all 4 RoS systems (read-only; for model comparison)
go run . shadow --dates 2026-06-30                   # capture a specific date
go run . archive --dry-run           # capture today's ephemeral data (HKB, projections, Savant, prospects); --dry-run prints sizes
go run . archive --date 2026-08-21   # capture today; a past --date is refused (the sources have no history)
go run . version-check               # probe Fantrax with the pinned API version; fails on confirmed STALE_CLIENT or a gate that stopped discriminating
make clean-cache        # rm -rf .cache/  (cold-pass baseline before make run-all)
make run-all            # exercise every command in dry-run / read-only mode + print cache size
```

**`make run-all` is the canonical end-to-end smoke test** — it iterates every CLI command in dry-run / read-only mode with `time` on each step and prints the final `.cache/` size. Use it for two things: (1) a single-command sanity check before pushing changes, and (2) observing cache behavior — stderr `cache hit:` / `cache miss:` lines show what each command touched. **Whenever you add a new top-level CLI command (a new `cmd/<x>.go` registered on `rootCmd`), append a corresponding line to the `run-all` recipe in the `Makefile`** so the smoke target stays comprehensive. Pair with `make clean-cache && make run-all` for a cold pass, then `make run-all` again to see warm-cache behavior.

After making code changes, always run `make lint` and `go mod tidy` to catch issues early. Note: `gofmt` runs automatically via a PostToolUse hook on every Edit/Write, and a second hook runs `golangci-lint run ./...` over the root module (falling back to `go vet` with a printed notice if the binary is missing).

**Lint config lives in one `.golangci.yml` at the repo root**, shared by all four modules — golangci-lint walks up from each module dir to find it, so `make lint` loops the modules the way `build-modules`/`test-modules` do rather than trusting a root `./...` to descend. Three settings are load-bearing. **Both output caps are disabled** (`max-issues-per-linter: 0`, `max-same-issues: 0`): golangci-lint defaults to truncating its own report at 3 issues of the same kind and 50 per linter, which reported "41 errcheck issues" against a real count of 230 when the gate was introduced — a linter that stops counting reports clean for the same reason the GS forecast reported "0 starts suppressed" all season. And **errcheck excludes only the print family plus `(net/http.ResponseWriter).Write`** — 148 sites with no recoverable failure mode; every other unchecked error is a hard failure, tests included, so each `_ =` in the tree is a deliberate decision rather than a default.

The third is **`nilerr` plus `nolintlint` with `require-explanation`** (rosterbot-w33l), which together make a deliberate soft-fail carry a written reason. `nilerr` is narrower than "flags soft-fails": measured 2026-08-31 with golangci-lint v2.13.1, it fires only where a function whose last result is `error` returns a nil error on a branch guarded by `err != nil` **and the checked value is not used inside that branch**, so a soft-fail that prints or interpolates its error is exempt — it detects *degrade to silence* specifically. The exclusion is SSA-value based rather than syntactic, so an error reached through a **struct field** is still flagged even when the block prints it (`cmd/version_check.go`'s two annotations are exactly that, and document code that already degrades to noise). The whole root module yields 6 findings; `lambda/`, `opsnotify/` and `infra/` yield 0. Five became `//nolint:nilerr` annotations (two in `cmd/version_check.go`, three on `FileInfraStore.ListPrefix`'s walk skips, which cite the open **rosterbot-xi3p** rather than settling it); the sixth was fixed, because it sat in a security regression test whose walk would have reported "no strays" over a directory it could not read. `nolintlint` is what turns nilerr's guarantee from *forces a decision* into *forces a reason*: `require-explanation` rejects a bare directive, and the unused-directive check (`allow-unused` defaults false) fails the build on a stale or misplaced one — measured, that is what keeps each of the five annotations load-bearing rather than decorative. Bundling it cost exactly one annotation (`internal/archive/archive.go`'s pre-existing bare `//nolint:errcheck` gained a reason).

**`lambda/`, `opsnotify/` and `infra/` are SEPARATE Go modules** (each with its own `go.mod`) — the root `go build ./...` / `go vet ./...` / `go mod tidy` do **not** descend into them. Two guards now exist: `.github/workflows/ci.yml` runs `make build-modules` on every PR (a stale nested module blocks merge), and `.github/dependabot.yml` watches all four module directories and **groups** them into one PR so root and nested modules never drift apart. CDK bundles `lambda/` and `opsnotify/` as `GoFunction` assets, so a stale `go.mod` in any of them only surfaces as a failed `cdk deploy`. They pull the root module via `replace ../`, so **every dependabot bump to a shared root dep re-stales them** (this broke the dashboard-v2 deploy twice — first `lambda/`, then `opsnotify/`). After touching a nested module (or after a dep bump), run `make build-modules`; fix a failure with `cd <dir> && go mod tidy`. `make build` runs it automatically so the break fails locally instead of at deploy.

**A third guard covers what `build-modules` structurally cannot**: each module that imports a forked dep carries its **own** `replace` line for it (root `go.mod` and `lambda/go.mod` both pin `github.com/pmurley/go-fantrax` to a fork commit), and nothing makes them agree. `build-modules` only notices the drift when the bump changes an API — which is exactly why rosterbot-7i3 *looked* covered. In the real recovery scenario, bumping `auth_client.APIVersion`'s **string** with no API change, a stale `lambda/go.mod` compiles clean, CI stays green, and the Lambda ships the old constant; `version-check` can't see it either, since it probes the root binary's pin only. **`make check-pins`** (run by CI and by `make build`) asserts that any module path replaced in more than one `go.mod` resolves to the same target everywhere. It compares **version-pinned replaces only** — `replace <root> => ../` appears in both `lambda/` and `opsnotify/` and the strings match, but only by luck, since a filesystem path resolves against its own module dir; filtering on a non-empty version drops those honestly rather than passing them by accident. Missing `jq` is a hard error, not a skip — a guard that silently no-ops is the false-confidence failure this one exists to kill (rosterbot-00e).

Tests require no credentials — all network dependencies are mocked via interfaces or test servers.

For local dev, create a `.env` file (gitignored) with `FANTRAX_USERNAME`, `FANTRAX_PASSWORD`, `FANTRAX_LEAGUE_ID`, `FANTRAX_TEAM_ID`, `FANTRAX_IL_SLOTS`, `FANTRAX_MINORS_SLOTS`. Loaded automatically by `godotenv`.

Optional env vars with defaults: `GS_TRACKING_ENABLED` (false) — enables games-started tracking, used by both the optimizer (weekly GS budget) and gs-check (league-wide violation detection). The real min/max are always fetched live from Fantrax's own per-period `getTeamRosterInfo?view=GAMES_PER_POS` configuration (see `internal/fantrax.GetGSLimits`) — there's no numeric env var for the limit itself, since Fantrax scales it whenever a period spans more than one calendar week (season opener, All-Star break). `PROSPECT_ROLLING_DAYS` (14), `PROSPECT_MIN_GAMES` (8), `PROSPECT_RANK_CACHE_HOURS` (168), `PROSPECT_UPGRADE_RANK_THRESHOLD` (20).

GS-check env vars (required only for `gs-check` command): `GS_TRACKING_ENABLED=true`, `PUSHOVER_GROUP_KEY`, `PUSHOVER_API_TOKEN`. If the live GS-limit fetch fails, both `optimize` and `gs-check` send a Pushover alert via `PUSHOVER_USER_KEY`/`PUSHOVER_API_TOKEN` (the personal ops-alert channel, same as the cache's stale-fallback notification) rather than falling back to a stale static number.

## Architecture

The optimizer runs as a single binary (`main.go`) with Cobra subcommands (`cmd/`) that wire together four independent packages:

```
fantrax client  ──┐
mlb schedule    ──┼──► optimizer ──► apply lineup (or dry-run print)
fangraphs proj  ──┘
```

**`internal/cache`** — generic TTL cache using Go generics (`FileCache[T]`). Stores JSON with a `fetched_at` timestamp envelope behind a byte-level **`Store`** seam. `Get(key, fetchFunc)` returns cached data if fresh, otherwise calls `fetchFunc`, saves, and returns. All I/O errors are non-fatal. TTL of 0 bypasses cache (`--no-cache` flag). Storage is pluggable: `fsStore` (default; `<dir>/<key>.json` flat under `.cache/`) and `MemStore` (tests) live in the zero-dep leaf; the S3 adapter `s3store` (`internal/cachestore/s3store`) lives in its own package so the AWS SDK stays out of the leaf, and is itself a thin shim over the shared `internal/s3blob` (see below). `cache.SetDefaultStore(store)` swaps storage process-wide for every `FileCache` without touching the ~30 `New[T](dir, ttl)` call sites (mirrors the `Verbose`/`Notify` package globals). On AWS, `cmd` calls `SetDefaultStore(s3store…)` keyed under the `cache/` prefix when `STATE_BUCKET` is set, so the bot reads/writes the cache per-key live to S3 and `entrypoint.sh` no longer syncs `cache/`. See `docs/adr/0001-s3-not-db-for-cache.md`.

**The stale-fallback alert is edge-triggered on the copy's AGE, and both halves are load-bearing (2026-08-19 FanGraphs outage).** `GetWithStaleFallback` is the degraded path two callers use — `projections`' batting and pitching fetches — and it used to push a Pushover on *every* stale serve. That is level-triggered: it restates a standing condition once per key per run, so when FanGraphs put `/api/projections` behind a **Cloudflare interactive challenge** (`cf-mitigated: challenge`, HTTP 403, holding ~17:00–03:00 UTC and clearing outside it) the result was **30 pushes in 24 hours**, of which the 30th said nothing the 1st had not. An alert nobody can afford to read is worth less than no alert, and it is what hid the one finding that actually cost data — see the Shadow schedule note in `infra/infra.go`.

`internal/cache/stale.go` now decides, on two facts:
- **Age.** Below `StaleAlertAfter` (24 h) the serve is logged and nothing is pushed. Every upstream this path guards refreshes at most daily, so a copy younger than that is the same data a successful fetch would have returned, and paging on it reports a non-event. An **undated** copy (zero `fetched_at`) is never called old — absence of evidence is not evidence, the same rule that stops `internal/roster` listing a player with no position data as ineligible. The pre-fix code would have pushed `106751d old`.
- **A durable marker**, via `layout.StaleCacheAlerts` (`alerts/stale-cache/`). In-process state does nothing here: every scheduled run is a fresh container, so each would re-alert on the same outage. The marker key is the cache key and the **episode identity — the stale copy's `fetched_at` — lives in the BODY**, which is what keeps recovery cheap: clearing a standing alert costs one small marker read, not a re-read of a multi-megabyte payload just to date it. A fresh fetch clears the marker by writing an **empty body** rather than deleting, so the seam stays `Get`+`Publish` (`lineupapi.BlobStore`) with no `Delete`.

Three properties beyond that — all owned by **`internal/alertmarker`**, the stdlib-only leaf every one-shot alert site (stale-cache, IL-start, GS-floor, lineup-apply, football-trades, opsnotify) now delegates its marker loop to: order is **check → send → mark**, never claim-then-send, and every marker-store failure degrades to a **duplicate alert, never to silence** (rosterbot-chs). A **nil** marker store alerts every run rather than staying quiet about something there is no record of — the correct local-dev behavior, shared with `lineuprun`'s IL-start and GS-floor markers. And the artifact is deliberately **NOT PerTenant**, for exactly the reason `layout.Cache` is not: the cache it guards is a league-wide singleton, so the outage is shared and one marker is the correct number — the per-(command, tenant) split `opsalert` *needs* would reintroduce the flood one level down. `StaleCacheAlerts` carries no `MaxAge` and is absent from `All()` (a marker exists only while something is wrong), so `TestStaleCacheAlerts_LayoutChoicesArePinned` pins those exclusions the way `FootballTradeLog`'s are.

**The console line stays unconditional**, so the diagnostic record is complete even when the push is suppressed — the same reasoning as the `il-start check:` and `mlb recency coverage:` lines.

**`projections.fetchJSON` retries, and it is worth being precise about what that buys.** Both FanGraphs fetchers route through it (3 attempts, 1 s then 4 s), and it retries transport errors, 5xx, 429 **and 403** — normally a durable authorization answer, but here the status of an unsolved Cloudflare challenge, and nothing on this endpoint is authenticated so there is no real 403 for the looser rule to mask. It does **not** defeat the challenge window, which moves on a scale of hours; it covers the single-attempt blip that used to burn a whole run's fetch. The protection against the window itself is the stale fallback plus some run landing in the clean hours.

**`internal/statestore/layout`** — the single declaration of the STATE_BUCKET key layout: every prefix the bot writes, its local-dir equivalent, and the operator-facing metadata (`MaxAge`, `Producer`, `Partitioned`, `NoBackfill`, `RecoveryInput`). A **zero-dependency leaf**, because two packages need the table and can't import each other: `statestore` builds typed stores from it (and imports `lineupapi`, so the dependency only runs one way), while `lineupapi` serves it on `GET /v1/infra`. `NoBackfill` marks the one artifact whose missing days are unrecoverable (the Team Value Store — see `docs/adr/0002`), which is what lets the Infra page rank a gap there above a merely stale prefix.

**`internal/statestore`** — the composition root's single owner of the durable-state backend choice: S3 when `STATE_BUCKET` is set (Fargate), else a local directory. It centralizes the one `os.Getenv("STATE_BUCKET")` read (`statestore.Bucket`), the prefix/local-dir layout table for every durable artifact (`cache/`, `analysis/`, `analysis/team-values/`, `runledger/`, `runs/`, `notifications/`, `lineup/` ↔ their `.cache`/`.analysis`/`.teamvalue`/`.lineup/*` local roots), and the sole S3-vs-local branch (`pick[T]`). It exposes one typed constructor per artifact (`CacheStore`, `AnalysisWriter/Reader`, `TeamValueWriter/Reader`, `RunLedger`, `Output`, `Notifications`, `Progress`, `LineupPublisher`). **Only `cmd` imports it** — no leaf imports it back, so the AWS SDK it pulls in (via the three s3 adapters) never reaches leaves like `internal/lineuprun`, which receives its `lineupapi.Publisher` from `cmd` via `Options.Publisher` instead of reading the environment itself. The `cmd/sync.go` bulk dir-sync gating and `cmd/migrate_run_ledger.go` (require-S3) share the one env read via `statestore.Bucket()` but keep their distinct, non-store-constructor behavior. Compatible with ADR-0001.

**An empty tenant is a real mode, but it is not a licence to guess (rosterbot-4b9).** `layout.Artifact.{PrefixFor,LocalDirFor}("")` return the un-segmented pre-migration path, which was the live location until the rosterbot-crq.11 backfill relocated every per-tenant artifact under `user=<uid>/` **and left the old copy in place**. That copy is **frozen, not merely duplicated**, so resolving it is not a stale read that self-corrects — the gap widens by one day per day, and the symptom is the innocuous `N missing` line rather than an error. Measured 2026-08-19: 11 of 12 per-tenant prefixes carry such an orphan, all last written 2026-08-14/15 (the migration date); only `alerts/il-starts/` is clean.

`pick` therefore **refuses** a tenant-less local read when `user=` segments sit beside the path it would fall back to, naming the artifact, the directory and the tenants it found. Three properties are load-bearing:
- **Evidence-based, not unconditional.** A machine that never synced tenant data has exactly one copy and it is the right one; refusing there would break every existing local tree, every hermetic test and every fresh checkout for a mistake nobody made. Absence of evidence is not evidence — the same rule that stops `internal/roster` listing a player with no position data as ineligible.
- **Local-only, and the asymmetry is not an oversight.** A deployed task always declares its tenant (infra sets `ROSTERBOT_USER_ID` on the task definition from SSM; the fan-out overrides it per tenant), and a deployed run that somehow did not is already refused by `resolveCredentialMode` before any store is built, on identical reasoning: a tenancy that is real but unattributable has no safe default. Local dev has no user directory, so nothing refused it there — which is exactly where this landed. Probing S3 instead would cost a `ListObjectsV2` on every store construction to re-derive what the environment already states.
- **The converse is deliberately NOT an error.** A tenant that is set with no data under its segment is an ordinary fresh tenant, including the first run of a new user in production; erroring there would break exactly the case the fan-out exists to serve.

Local dev declares the tenant in `.env` (gitignored), so a local read resolves the same bytes the deployed reader does — verified end to end against the production run recorded in rosterbot-4b9.

**`internal/s3blob`** — the one place aws-sdk-go-v2's S3 client is constructed and driven. A `Blob` is a bucket+prefix scoped view exposing `Get`/`GetWithETag`/`Put`/`PutJSON`/`PutJSONIfAbsent`/`PutJSONIfMatch`/`Delete`/`Walk`/`List`; every key handed to or returned from it is **relative to the prefix** (joined on the way in, stripped on the way out), so key-derived fields parse identically against S3 and against each adapter's local-directory backend — the Analysis Store's `system=` segment, the run ledger's inverted-timestamp ordering. `Get` reports a missing object as `(nil, false, nil)` rather than an error, since absence is an ordinary outcome for every caller (cache miss, run with no captured output yet, unregistered passkey). `Walk` follows `NextContinuationToken` and lets its callback return `false` to stop early — that combination is what makes "newest N" listings safe, and is what rosterbot-432 (a single-page listing letting sub-objects sharing a prefix hide the ledger block) was missing.

**The two conditional writes are the only compare-and-swap in the tree, and exist for exactly one artifact** (rosterbot-crq.2). Every other store here is write-once-per-key; the WebAuthn identity record is read-modify-written by concurrent HTTP requests (register appends a credential, login updates a sign counter, revoke removes one), so a blind `PutJSON` silently drops whichever change lost — a registration that returns 200 and later simply is not there, with nothing logged. `PutJSONIfAbsent` (`If-None-Match: *`) and `PutJSONIfMatch` (`If-Match: <etag>`) push the decision to S3, which is the only place it can be made correctly across independent Lambda invocations; both normalize a lost race onto `ErrPrecondition` — including the 409 `ConditionalRequestConflict` AWS documents alongside the 412, and the 404 an `If-Match` returns when the object was deleted, since all three mean "not the state you asserted" and all three recover by re-reading. This does **not** loosen the rule above: the `Store` interfaces stay unshared, and only the conditional-`PutObject` plumbing is centralized. `s3blobtest` evaluates both preconditions rather than accepting every write — a fake that rubber-stamps conditional writes reports success for precisely the interleaving the condition exists to reject.

All ten S3-backed stores are thin shims over a `Blob`: `s3store` (cache), `s3ndjson` (Analysis + Team Value), and the seven in `s3lineup` (lineups, run ledger, per-run output, progress, notifications, WebAuthn identity, infra listing) plus the ledger `MigrateStore`. Each shim owns only its key layout, its interface shape and its own not-found policy — `s3store` returns the miss, `s3ndjson` turns it into an error because `ReadAll` only ever `Get`s keys it just listed. Before rosterbot-oye each of these hand-rolled `config.LoadDefaultConfig`, a private `api` interface, prefix joining and `NoSuchKey`/`NotFound` mapping, and four of them had their own list loop — of which only one paginated correctly.

**The WebAuthn identity record is the one store here under optimistic concurrency.** `lineupapi.Identity` carries a `Version IdentityVersion` (`json:"-"`) that `GetIdentity` reports and `PutIdentity` conditions on — empty means "create, and fail if a record exists"; non-empty means "write only if still at this version" — with a lost race surfacing as `ErrIdentityConflict` and a successful write advancing `Version` in place. The version **rides on the struct rather than the method signature**, matching the DynamoDB conditional-write this record migrates to (epic rosterbot-crq) and removing the chance for a call site to forget to thread it through; it is **opaque** because the backends disagree on what a version is (S3's ETag, the file store's content SHA-256, DynamoDB's own attribute). The consequence of an unchanged signature is that an implementation ignoring `Version` still compiles, so **`internal/lineupapi/identitytest.Run` is the contract** and every implementation must be run through it. `Config.mutateIdentity` owns the retry: it re-reads and **re-applies the mutation to the current record** (never re-writing a stale snapshot), bounded at 5 attempts, which is what lets a concurrent registration and login both survive. `FileIdentityStore` gets a mutex plus atomic rename, honestly scoped to one process (`serve` is a single-operator dev server); the backend that actually runs concurrently is S3, where the precondition is enforced server-side.

**This must not be used to unify the `Store` interfaces above it.** `cache.Store` (`Get`→`([]byte, bool, error)`/`Put`/`Remove`) is a delete-capable keyed TTL cache with no enumeration; `ndjsonstore.Store` (`Get`→`([]byte, error)`/`Put`/`List`) is an enumerable append-only partitioned log with no delete. Those signatures encode the real lifecycle difference between the Cache and the durable stores that ADR-0001 and ADR-0002 rest on; only the SDK plumbing beneath them is shared. `internal/s3blob/s3blobtest` is the shared in-memory `API` double — it emulates real ListObjectsV2 pagination (lexicographic order, `PageSize` per call, `IsTruncated`/`NextContinuationToken`) precisely because pagination bugs only surface against a fake that actually pages. The real AWS path is exercised by a build-tagged live test: `STATE_BUCKET=<bucket> AWS_REGION=us-west-1 go test -tags live ./internal/s3blob/`, which writes and cleans up under a `scratch/s3blob-live/` prefix and skips when `STATE_BUCKET` is unset. The three s3 adapters it wires are now shims over one shared `internal/s3blob` (rosterbot-oye); their constructor signatures (`New*(ctx, bucket, prefix)`) are unchanged, so `pick[T]` was untouched by that change. `internal/lineupapi/ddbuser` has the same build-tagged live test for its own fake (`ddbusertest`, which is type-sensitive since rosterbot-6my — a numeric `ver` conditioned against a string `:v` read as passing in the old fake, which compared decimal text, while DynamoDB's real type-and-value comparison would reject it every time): `DDBUSER_LIVE_TABLE=<scratch-table> AWS_REGION=us-west-1 go test -tags live ./internal/lineupapi/ddbuser/`, deliberately keyed off a var distinct from production's `IDENTITY_TABLE` so a `.env` pointed at the deployed identity table can never be hit by accident.

**Caching at a glance**: three TTL tiers map to three mutability classes.

| Tier | TTL | Use for | Examples |
|------|-----|---------|----------|
| `PastPeriodTTL` | **∞** (100 y) | Settled past-period snapshots (immutable once the period closes and stops settling) | `fantrax-roster-stats-<teamID>-<season>-<period>`, `fantrax-pitcher-gs-<teamID>-<season>-<period>`, `fantrax-recent-stats-pitcher-<teamID>-<season>-<period>` (hitter recency now comes from the `fantrax-roster-stats` daily series, not a dedicated snapshot), `fantrax-{hitter,pitcher}-roster-<teamID>-<season>-<period>`, `fantrax-gs-limits-<teamID>-<season>-<weeklyPeriod>`, `mlb-schedule-<YYYY-MM-DD>` (past dates) |
| `stableTTL` | 7 d | Season-invariant config | `fantrax-{hitter,pitcher}-slots-<leagueID>`, `fantrax-{hitter,pitcher}-scoring-<leagueID>`, `fantrax-season-range-<leagueID>` |
| `todayTTL` | 15 m | "Today, but stable for a window" — drifts during the day, but fine to reuse for an hourly GHA loop or local-dev iteration | `fantrax-{hitter,pitcher}-roster-<teamID>`, `fantrax-current-period-<leagueID>-<YYYY-MM-DD>`, `fantrax-player-pool-<leagueID>`, `fantrax-minors-roster-<teamID>`, `fantrax-available-prospects-<leagueID>`, `fantrax-pending-trades-<leagueID>`, `fantrax-all-trades-<leagueID>`, `fantrax-all-transactions-<leagueID>` |

**`PastPeriodTTL` is unbounded on purpose, and two invariants are what make that safe** (rosterbot-qoa). It was 30 days until 2026-07-31, which quietly made `recap-site` cost O(season length) — every week older than a month re-fetched from Fantrax on every Monday build (1,637 objects rewritten in one run, wall time 192s→1411s). The two invariants:
- **Volatility.** A period only reaches the past tier once it can no longer move — `periodIsVolatile(period, curPeriod)` (`recentPeriodLookback = 3`) keeps the current period *and the last three closed ones* on `todayTTL`, covering Fantrax's StatsType=1 YTD settling lag and the slop between UTC period math and ET game times. `tierFor` applies it to the `cacheTier` path, `snapshotTTL` to the two caller-supplied snapshot caches (`DailyFantasyPoints`, `GetTeamPitcherStarts`). A bare `period < curPeriod` test was fine at 30 days — a mid-settle capture self-corrected within the month — and is *not* fine now: one day too early pins a wrong snapshot for the rest of the season.
- **Season scoping.** Every key at this tier carries the season year (`seasonScopedKey` → `<prefix>-<teamID>-<season>-<period>`, matching the older `fantrax-period-date-map-<leagueID>-<year>`). Daily *and* weekly period numbers restart each season; the 30-day TTL used to flush that collision for free over the ~6-month off-season, and an unbounded TTL does not.

The one-time cost of the season rename is that every pre-2026-07-31 `fantrax-{roster-stats,pitcher-gs,hitter-roster,pitcher-roster,recent-stats-pitcher,gs-limits}-<teamID>-<period>` object is orphaned — the next `recap-site` build does one cold rebuild (the work that used to happen weekly) and then never again. The orphans are inert; prune at leisure.

A handful of provider-specific TTLs sit outside this scheme: `fangraphs-{bat,pit}-*` (24 h, `projections.ProjectionCacheTTL`), `mlb-handedness` (7 d), `savant-*` (24 h, `statcast.CacheTTL`), `hkb-*` (8 h), `prospect-rankings-*` (168 h via `PROSPECT_RANK_CACHE_HOURS`), `mlb-game-logs-<playerID>-<group>-<season>` (1 h, prospects MiLB game log), `mlb-game-log-<playerID>-<group>-<season>` (1 h, MLB-only game log used by the internal `backfillDailyFPts`), `mlb-season-players-<year>-<sportID>` (24 h, `playername.seasonIndexTTL` — the bulk name→MLBAM index). These predate or sit between the three-tier scheme and use whatever TTL fits the upstream's update cadence. The FanGraphs and Savant TTLs are **single exported constants** (`projections.ProjectionCacheTTL` / `statcast.CacheTTL`, both 24 h matching the once-daily upstream cadence) so every consumer (optimize, backtest, waivers, claims) shares one freshness policy on the shared cache entry — TTL is a per-read max-age against the stored `fetched_at`, not baked into the key, so divergent TTLs across callers would otherwise cause needless refetches.

**Cache key naming**: `<source>-<entity>[-scope...]` where `source` ∈ {`fantrax`, `mlb`, `fangraphs`, `savant`, `hkb`, `prospect`, `mlb-handedness`}, `entity` is the data shape (e.g. `roster-stats`, `pitcher-gs`, `matchups`, `schedule`, `bat`, `pit`), and `scope` is whatever disambiguators apply (teamID, period, leagueID, date). The repeated prefixes are named constants owned by the package that builds them — the whole `fantrax-*` / `mlb-game-log` family in `internal/fantrax/cachekeys.go`, plus `keySavant` (`statcast/load.go`) and `keyFanGraphs` (`projections/fangraphs.go`) — so a prefix rename lands in one place; genuine single-use keys (`mlb-schedule`, `mlb-handedness`, `mlb-game-logs`) stay inline literals. Old `backtest-snapshot-mlb-*` files (pre–roster-stats rename), `backtest-snapshot-*` files (StatsType=2 era), `player-ids.json` (pre-FileCache prospects bulk file), and `mlb-player-id-<name>-<team>` entries (the prospects package's own per-player resolver, replaced by the shared `mlb-player-ids-<sha8>` index in rosterbot-hdiu) are orphaned and safe to delete.

**Claims cursor and ledger**: `.cache/last-claims.json` is a small JSON file written by `internal/claims` after each successful run; it records the most recent transaction timestamp seen so the next run fetches only new events (cursor-based incremental delivery). The audit ledger is written to `.waivers/claims/<date>.json` (one file per UTC calendar date); the `.waivers/claims/` directory is created on first write and is safe to include in the GHA cache alongside `.cache`.

**`Client.SetCache(cacheDir)`** in `internal/fantrax/client.go` enables the file cache for every cached method on `*fantrax.Client`. `cmd/root.go`'s `initApp` calls it on every command's client unless `--no-cache` is set, so commands inherit caching automatically — no per-command opt-in. The cache-plumbing *policy* every cached method shares — short-circuit to the uncached `fetchXxx` sibling when `cacheDir` is empty (the `--no-cache` flag, and how tests stay hermetic), otherwise read-through a `FileCache` at the method's tier TTL — lives in three generic helpers in `internal/fantrax/cached.go`: `cached(c, key, tier, fetch)`, `cachedForPeriod(c, prefix, teamID, period, fetch)`, and `cachedForSeason(c, prefix, teamID, period, tier, fetch)` (GS limits, a fixed tier over a season-restarting period number). Each call site names only its key parts, tier, and fetch (rosterbot-nrr collapsed ~20 hand-copied branches into these). The three-tier scheme is a named `cacheTier` type (`tierToday`→`todayTTL` 15m / `tierStable`→`stableTTL` 7d / `tierPast`→`PastPeriodTTL` ∞), so which tier a method gets is a visible, checkable choice rather than whichever `time.Duration` constant the author typed. Per-period methods (`GetHitterRosterForPeriod`, `GetRecentPitcherStats`, etc.) resolve **both** their tier and their key's season scope from one `c.periodCachePolicy(period)` call — settled periods get `tierPast`, the current and still-settling ones fall back to `tierToday` (see `tierFor`/`periodIsVolatile`) — and the two period-aware helpers call it only *after* the empty-`cacheDir` short-circuit, because the resolution reads the season range and the no-cache path must not trigger it. That read goes through the **cached** `GetSeasonDateRange` (7 d on disk), not the raw `fetchSeasonDateRange`, so repeated per-period calls cost a disk hit rather than a Fantrax round-trip.

**`InvalidatePeriodRosterCache` returns its error (rosterbot-6ds9).** It was void, so all four `Invalidate` calls were discarded. On the local `fsStore` a missing key is not an error, so this is nil in development whatever happens; on S3 `blob.Delete` can genuinely fail, and a failed delete leaves the pre-apply snapshot readable — the rosterbot-sza symptom reached by a different cause. It returns `errors.Join` of every failure rather than the first, and attempts all four keys regardless: stopping early would leave the rest readable while reporting one error, and reporting only the first would name one stale key while another stayed silently readable. The single caller (`internal/lineuprun/emit.go`) **prints** rather than acts — the apply has already landed and is not undoable, so what the failure costs is the next run inside the 15 m `todayTTL` re-proposing moves already in place, and naming it is what separates that from unexplained churn. No Pushover: the window is short and self-healing and the operator has no action to take. Degrade to noise, never to silence.

**`c.periodCacheKey(prefix, teamID, period)` is the one place a per-period key is built**, returning both the key and its tier from a single policy read. It is a method rather than two inlined lines because it wasn't: `InvalidatePeriodRosterCache` assembled its own key by hand, so when rosterbot-qoa spliced the season into the grammar the writer moved and the invalidator didn't. **Removing a nonexistent cache key is not an error**, so the function went on reporting success while dropping nothing for four days (**rosterbot-sza**) — its whole purpose, letting a second `optimize` run after `ApplyLineup` see the applied lineup instead of the pre-apply snapshot, silently not happening, exposed only inside the 15 m `todayTTL` window and so exactly the scenario the **Idempotency** section below prescribes as verification. `TestInvalidatePeriodRosterCache_DropsTheEntryTheReaderWrote` pins the two sides together by driving the real reader rather than comparing key strings, so any future divergence fails regardless of how the key is built. The current-day keys in the same function keep the plain unscoped grammar on purpose — they sit at `todayTTL`, where no period number appears and a stale entry expires on its own.

**`PastPeriodTTL` is exported because it is also an argument, not only a tier.** `DailyFantasyPoints` and `GetTeamPitcherStarts` take their TTL from the caller, and that value used to be re-typed as a bare `30 * 24 * time.Hour` literal at six call sites — so "the" past-period TTL named only a quarter of the caches it appeared to govern, and the two families that actually dominated `recap-site`'s runtime were **not** among them. All six now reference `fantrax.PastPeriodTTL`.

The matchups response is also memoized in-memory per `*fantrax.Client` (via `allMatchups()`) — five different helpers consume the same `GetAllMatchups` payload during a single `recap-site` build, and in-memory is the right scope since the in-progress week mutates intra-day.

**`internal/fantrax`** — wraps `github.com/pmurley/go-fantrax` (public read API) and `go-fantrax/auth_client` (authenticated API + lineup writes). Key details:
- `auth_client` uses chromedp (headless Chrome) to log in and obtain a session cookie. Cookie is cached in `.fantrax-cache/`. On first run or cache miss, a browser opens.
- Credentials read from env: `FANTRAX_USERNAME`, `FANTRAX_PASSWORD`, `FANTRAX_LEAGUE_ID`, `FANTRAX_TEAM_ID`.
- **Fantrax API version** — every `/fxpa/req` POST body must include `"v": "<current>"`. This lives in exactly one place: the exported `auth_client.APIVersion` constant in the go-fantrax fork (`auth_client/fantrax_client.go`), whose doc comment is the runbook (the `curl` probe for the current version string and the unauthenticated STALE_CLIENT-vs-logged-in check). `gs_check.go` builds its `/fxpa/req` payload via `auth_client.BuildFullRequest`, so it — like every other caller — picks up the constant automatically rather than carrying its own copy. When Fantrax deploys a new version and calls start returning `STALE_CLIENT` (empty `responses` array), bump `APIVersion` in the fork; nothing in this repo needs a matching edit. The daily `version-check` command (see Commands) probes Fantrax unauthenticated against the pinned version and fails on a confirmed `STALE_CLIENT`, catching the drift before it hits a real job.

**The probe carries a positive control, because a green reading is only worth what the job's ability to go red is worth** (rosterbot-0a1). Fantrax's gate is a **minimum** check, not an equality check — measured live 2026-08-05, the floor sat between `181.0.0` (`STALE_CLIENT`) and `182.0.0` (`WARNING_NOT_LOGGED_IN`), and `999.999.999` passes, with narrow headroom (upstream `pmurley/go-fantrax` main was pinned one release above the floor that same week). So whenever the pinned probe reads OK, a second probe sends `fantrax.ControlVersion` (`1.0.0`), which a working gate must reject; if it comes back anything but `STALE_CLIENT`, the gate has stopped discriminating and the run fails with `PROBE_BLIND` — without it the job would launch, exit 0, and record SUCCESS while every "version OK" it reported was meaningless, invisible to `opsalert`'s `Overdue` heartbeat, which only asks whether a run *happened*. The control sits deliberately far below the floor so it fails only when the **mechanism** breaks, never when the real probe's **threshold** moves; a control transport error is a warning, not a failure, since the gate already answered the pinned probe moments earlier.
- **Position IDs are numeric strings** (`"001"` = C, `"002"` = 1B, `"003"` = 2B, `"004"` = 3B, `"005"` = SS, `"008"` = INF, `"012"` = OF, `"014"` = UT). These come from the roster API and must be used as-is for slot assignment and eligibility checks. Their semantics live in **`internal/positions`** (the single source of truth): ID constants — filling `"003"`/`"008"`, which upstream `auth_client` omits — plus `SlotName`, `AcceptsINF`, `IsPitcherSlot`, and `HitterBucket` (the C>INF>OF>UT reporting precedence). `fantrax` and `backtest` both import it instead of hardcoding switches.
- This league's active slot names: `C`, `1B`, `2B`, `3B`, `SS`, `INF`, `OF` (×4), `UT` (×3). Mapped in `posNameToID` in `client.go` (which references `positions` constants).
- Scoring group code is `BASEBALL_HITTING` (not `HITTING`).
- **Scoring periods are daily** (period 1 = season opener), though Fantrax merges consecutive days into one period number around multi-day breaks (e.g. the All-Star break) and can insert extra daily periods mid-season (doubleheader/postponed-game makeups) — so plain `1 + days since season start` arithmetic can drift. Matchup data from `GetAllMatchups()` has weekly matchup entries, not daily — don't use it for period lookup.
- **Two distinct period axes, two distinct helpers — do not cross them.** The two axes are distinct Go named types — `WeeklyPeriod` and `DailyPeriod` (`period_types.go`) — so passing a weekly value where a daily one is required (or vice versa) is a compile error, not a silent bug (rosterbot-1i3, the fix for the rosterbot-uv6 / rosterbot-z3b bug class). `GetScoringPeriodsAndTeams()` returns `[]ScoringPeriod` parsed from Fantrax's standings `SCHEDULE` view captions ("Scoring Period N (date - date)"); despite the name, `N` is the **weekly matchup** number (~7 days/period, merged wider around breaks — e.g. period 16 spans 2026-07-13..07-26 across the All-Star break, per `TestFindCurrentPeriod_MergedAllStarBreakPeriod`). `FindCurrentPeriod(periods, date)` / `FindJustEndedPeriod` answer "which weekly period contains/just-ended for this date" from that list — correct for GS-limit lookups (`GetGSLimits` takes the weekly number) and standings-style questions. Roster/apply/GS-snapshot endpoints (`GetHitterRosterForPeriod`, `GetPitcherRosterForPeriod`, `ApplyLineup`, `getPlayerGSSnapshotForPeriod`) are keyed by a completely different, **daily** period number (advances one per calendar day, e.g. 104…110 across a week) that Fantrax never exposes as a list — only as "the current period" via `GetCurrentPeriod()`. **`fantrax.DailyPeriodFor(seasonStart, date)`** (`gs_period_walk.go`) is the single source for that axis — the **Period Map** (see `CONTEXT.md`): the authoritative `periodList` date map first, then `PeriodForDate(seasonStart, date)` day math as its only fallback. It depends on nothing but `(seasonStart, date)` — notably not on "today" nor on `GetCurrentPeriod()`. `GetTeamGS`/`GetTeamPitcherStarts` walk each day of a (weekly) `ScoringPeriod` via **`gsPeriodWalk`**, which calls `DailyPeriodFor` per day — never the weekly `ScoringPeriod.Number` itself, which would make every day in the period fetch the identical snapshot. `internal/lineuprun.Run`'s per-date apply loop (`optimize`/`shadow`) resolves each `--dates`/`--matchup` date to its daily period the same way, via `DailyPeriodFor` directly — **not** via `FindCurrentPeriod`/the weekly `periods` list, and not via a `periods`-first resolver.
  - A prior change (**rosterbot-uv6**, commit 92ed478) mistakenly routed `GetTeamGS`'s daily walk through a periods-list-first resolver (`fantrax.ResolvePeriod`, since deleted); every day then fetched the *same* weekly-numbered snapshot, collapsing all day-over-day deltas to zero and under-counting each team's weekly GS to ~one day's worth. That surfaced as a whole-league false "Under Min" GS alert at the first All-Star-break boundary (2026-07-13) and was reverted to daily numbering (**rosterbot-wd5**).
  - The exact same class of bug independently recurred in the lineup-apply path: `rosterbot-z3b` (2026-07-12) introduced `fantrax.ResolvePeriod` — a periods-list-first, three-tier resolver intended as "the single entry point for mapping a calendar date to its scoring period number" — and wired `internal/lineuprun.go`'s per-date apply loop through it. Its tier 1 trusted the weekly `periods` list as if it were daily-grained; since virtually every in-season date falls inside some weekly period's date range, tier 1 won on nearly every call. When the All-Star break merged two weeks into period 16 (2026-07-13..07-26), every `--matchup` date in that span resolved to the identical period 16, causing the same lineup swap to re-apply and fire a fresh Pushover alert for all 11 dates on every hourly run — the duplicate-alert flood diagnosed 2026-07-14. Fixed by switching the apply loop to `DailyPeriodFor` directly and deleting `ResolvePeriod` (no safe production use case remained: every real caller needs the daily axis, and the weekly `periods` list can't provide it). The baseline-day lookup (`dayBeforePeriod`) resolves via the same `DailyPeriodFor` daily numbering. Historical/backtest-facing period lookups (`DailyFantasyPoints`, `GetTeamPitcherStarts`) are **resolved** (**rosterbot-ren**) via the authoritative season-wide date→daily-period map: `DailyPeriodFor` consults `periodDateMap` (`period_date_map.go`), parsed once from `getTeamRosterInfo`'s `DisplayedLists["periodList"]` dropdown (`"104 (Mon Jul 6)"` … — the label for period N *is* the date whose snapshot lives at period N, so it's self-correcting across Fantrax's mid-season period insertions), cached season-stable (`fantrax-period-date-map-<leagueID>-<year>`, `stableTTL`) plus in-memory memoized like `allMatchups`; it soft-falls-back to naive `PeriodForDate` on any miss/fetch error, so hermetic tests and credential-less renders are unaffected. The Class-A anchored path (lineup-apply + `GetTeamGS`) was **unified onto the same authoritative map** (**rosterbot-2ax**, closed 2026-07-16), and then (**rosterbot-xyk**, 2026-07-25) the two near-twin resolvers were **collapsed into one**: `Client.dailyPeriodForDate` and the anchor tier are gone, leaving a single `DailyPeriodFor(seasonStart, date)` of map → day math. The decision was measurement-driven — against the live `periodList` map (187 entries covering the 2026 season) the **daily axis is strictly 1:1 with calendar days** (zero merged/inserted periods across 122 elapsed days, naive day math agrees with the authoritative map on all 187 dates). So the anchor tier never once supplied an answer day math wouldn't have, while its own input (`GetCurrentPeriod()`) demonstrably lagged a day: on 2026-07-16 it returned 113 for that date while the freshly-refetched periodList map said 113 = 07-15 and 114 = 07-16, so the lineup-apply hot path submitted changes against the already-closed period 113, Fantrax rejected the affected players as "already locked," and `applyLineupWithLockedPlayerRetry` masked the resulting no-op as "Lineup applied successfully" (that retry path trusting an empty/benign post-retry response instead of verifying the change landed is filed separately as **rosterbot-48z**). The merging Fantrax *does* do — the All-Star break — happens on the **weekly** axis only; the two weekly notions (standings-caption `ScoringPeriod.Number` vs `MatchupWeekBounds`) agree exactly across all 23 weeks, so they're one concept reached two ways, documented as *Weekly Period* / *Matchup Week* in `CONTEXT.md` rather than unified in code. `gsPeriodWalk` takes a leading `*Client` param (nil-safe) to thread the map through to `GetTeamGS`/`GetTeamPitcherStarts`.
- **Future lineup apply** requires a two-step confirmation flow: first API call returns a confirmation prompt (`ShowConfirmWindow=true`), second call with the same payload applies the changes. Handled in `ApplyLineup`.

**`internal/projections`** — FanGraphs projections via the `--projections` flag. Supported systems: `steamer`, `depthcharts`, `thebatx`, `atc`, plus their rest-of-season variants `steamer-ros`, `depthcharts-ros`, `thebatx-ros`, `atc-ros`. Default is `depthcharts`; the bot currently runs on `depthcharts-ros` in season. Wraps the configured system with a rolling-stats fallback chained via `ChainedSource`. FanGraphs returns **JSON** (not CSV); player name field is `PlayerName`. The `Projection` struct includes derived stats (`Singles`, `XBH`, `TB`) that must be computed from raw fields before scoring. Separate `Source` (hitters) and `PitcherSource` (pitchers) interfaces.

**Blended scoring** — wraps the configured FanGraphs source with recent Fantrax stats, in the **`BlendSources`** phase (`internal/lineuprun/blend.go`). The recent signal differs by role. **Hitters** use a **trailing 30-day window**: `windowedHitterRecent` reconstructs the per-day FPts series (`DailyFantasyPoints` over the last ~35 days, backfilled) and collapses it via `projections.WindowedRecent` + `WindowWeight(30)` into per-player FP/game + games-in-window, as of today. That splits into two pure pieces worth knowing about — `hitterWindowBounds` (the 35-day lookback, clamped to the opener, ending yesterday) and `collapseHitterWindow` (series → recency map, no client) — because an error in the collapse doesn't fail, it silently shifts every hitter's Expected Points. **Pitchers** still use **season-to-date** YTD FP/G from a single roster snapshot: the Fantrax roster API returns cumulative YTD `FantasyPointsPerGame` regardless of the period requested, so `GetRecentPitcherStats` reads the latest completed period's snapshot. Both fall back to 100% base projection when no recent data. Weights are **dynamic** (not fixed) and shift toward recent stats as a player accumulates a stable sample. The hitter window **replaced** unbounded YTD after `backtest --recency-experiment` (**rosterbot-2nd**) showed w30 beating unbounded YTD by ~1 realized pt/game/day over the season — raw YTD double-counts the in-season signal already regressed into `depthcharts-ros`. Pitchers showed **identical** lineup outcomes across every strategy (pitcher slotting is game-availability-bound, not projection-bound), so they stay on YTD. The harness compares base / ytd / 14d / 30d / decay variants for **both** roles; see `docs/superpowers/specs/2026-06-06-windowed-recency-strategy-replay-design.md`.

**The hitter window is roster-scoped, and that had to be corrected for mid-window acquisitions** (rosterbot-6tw). `DailyFantasyPoints` walks **our own** per-period roster snapshots, so a player's games-in-window is really *games while on our roster* — and since `WindowedRecent` builds its series only from days a player appears in, pre-acquisition days contribute **no row at all** rather than a zero. Nothing distinguished the two: measured 2026-08-11, two 4-period-tenure acquisitions (Antonacci, Neto) both reported ~96% base weight, indistinguishable from a genuine 70-period veteran's 96% — the recency signal `rosterbot-2nd` measured at ~1 realized pt/game/day was switched off for exactly the players a trade had just made hardest to value. `coverImportedHitters` now detects short coverage (`shortCoverageHitters`: first appearance later than the **30-day window** start — not the 35-day fetch start, since the extra lookback days only populate the far edge) and **replaces** those players' entries with ones rebuilt from `fantrax.MLBDailyFPts`. Verified: both acquisitions moved to the everyday-player band while genuine veterans correctly stayed high.

**`MLBDailyFPts` is the roster-independent sibling of `DailyFantasyPoints` and the two must not be merged.** `DailyFantasyPoints` answers *"what did MY team score on this day"* and is consumed by `cmd/grade.go`, `cmd/backtest.go` and `internal/recap` — all of which would be **wrong** if credited with production a player earned on someone else's roster. `MLBDailyFPts` answers *"what did this player produce"*, from their MLB statsapi game log scored with the league's weights, which is the only correct input to a recency window. Replacement rather than splicing is deliberate: the game log already covers the overlapping days, so merging would double-count them. The path **soft-fails** to the roster-derived window, matching `DailyFantasyPoints`' own backfill contract, and prints an `mlb recency coverage:` line **unconditionally** — including the zero case — naming any unmatched player, because a silently truncated window is precisely what kept this invisible for a season. An unmatched name is not automatically a defect — it can mean the player genuinely had no MLB game in the window, and naming him is what turns that into a ten-second check rather than an assumption.
- **Hitters** (`BlendedSource`): `seasonWeight = approxPA / (approxPA + 250)` where `approxPA = GP × 3.8` and **GP is games in the trailing 30-day window** (caps ~26), so recent weight tops out near ~28% but reflects only recent form; base weight = `max(1 - seasonWeight, 0.30)`, never below 30%. `PtsPerGameSource` interface (type assertion) lets the optimizer use pre-computed values.
- **Pitchers** (`PitcherBlendedSource`): role-aware stabilization — SP equal weight at 15 GP, RP at 25 GP; base floor 35%. Requires minimum GP before blending. GP here is season-to-date (YTD snapshot). `PitcherPtsPerGameSource` interface.

**`internal/playername`** — the single home for `Normalize`, the cross-source name-matching key used everywhere Fantrax names get joined against another provider (HKB, FanGraphs, MLB statsapi): `internal/teamvalue`, `internal/claims`, `internal/transactions`, `internal/hkb`, `internal/waivers` (via `ResolveMLBAMIDs`), `internal/recap` (League Leaders), `internal/schedule`, `internal/fantrax` (MLB backfill, apply-lineup scorer IDs), and `projections.NormalizeName` (a thin wrapper, so the optimizer/blending/backtest paths inherit it too). It strips diacritics (NFD decomposition), lowercases, drops periods/commas/apostrophes — including the "smart quote" variants (`'`/`'`) a source's text pipeline may substitute for a straight `'`, and a comma before a suffix ("Guerrero, Jr." vs "Guerrero Jr.") — treats hyphens as word breaks (`"Ha-Seong Kim"` vs `"Ha Seong Kim"`), and strips `Jr`/`Sr`/`II`/`III`/`IV` suffixes. A join miss that isn't one of these known gaps (a call-up too new for HKB's rankings, a genuine nickname like "Vlad" for "Vladimir") isn't fixable by string transformation — see `internal/teamvalue`'s `Unmatched` below for how those surface instead of silently undercounting.

**The normalized key is not unique, so the HKB join resolves through `hkb.Lookup` rather than a map** (rosterbot-5z7). The suffix- and diacritic-stripping that makes the join work is exactly what merges distinct players: measured 2026-08-14, 1752 HKB players collapsed to 1748 keys, with one real name collision confirmed live. The old `BuildLookup` assigned unconditionally, so the last row in scrape order won — and a wrong match is worse than a miss: a miss renders as unknown (every wire field is `omitempty`), while a wrong match renders as a confident number **and counts toward join coverage**, which is what let `team-values` report a team fully matched while one of its rostered players was silently mispriced, in the one store that is `NoBackfill`. Same failure class as `claimName` below, one provider up.
- `Find(name)` declines any contested key. Used where the caller holds only a name and a position (`internal/claims`, `internal/transactions`, the tradeboard offer path, and `lineuprun.hkbMeta` — whose roster carries `InMinors`, where the player *is*, not `MinorsEligible`, what he is *eligible for*; passing one as the other would resolve a called-up prospect against his MLB namesake). `prospects.hkbRanks` also resolves through it — over the prospect-filtered rows only, since its Level filter is what keeps an MLB veteran from contesting a prospect's key; it was the last direct last-write-wins map on this join.
- `FindFor(name, Hint{MLBTeam, MinorsEligible})` disambiguates, and is used by the two sites holding a pool row: `internal/teamvalue` and `tradeboard.BuildValuesTable`. **Neither signal suffices alone** — club settles 3 of the 4 live collisions but not `luis garcia` (both NYY), level settles 3 but not `max muncy` (both MLB), and together they settle all 4. **When the two signals name different rows, it refuses**; so does a signal that rules out every row, since a hint naming a club neither namesake plays for is stale rather than informative.
- **The level signal is one-way, by measurement.** Cross-tabbing `MinorsEligible` against HKB `Level` over 512 cleanly-resolving rostered players: `minors=false → MLB` holds 98%, but `minors=true → non-MLB` holds only 84% — minors eligibility is an eligibility, not a location, and several called-up prospects sit at MLB despite being minors-eligible. Reading it backwards to prefer the minor-league row would be confidently wrong at a real rate. Reproduce with `go test -tags diag -run TestDiagMinorsVsLevel ./internal/hkb/`.
- **Compare clubs with `sameTeam`, never `==`.** The feeds disagree on exactly two of 32 abbreviations — HKB `AZ` vs Fantrax `ARI`, HKB `CWS` vs Fantrax `CHW` — so raw equality would silently never match for Arizona or White Sox players.

**`ResolveMLBAMIDs` (name → MLBAM ID) has three rules that are each load-bearing, all established by live measurement on 2026-08-11** (rosterbot-bms, rosterbot-i52). It is the join key for five call sites — `internal/fantrax` (backfill + `MLBDailyFPts`), `internal/recap` (League Leaders wOBA/FIP), `internal/claims` (Statcast tagging), `internal/prospects` (×2) — so a wrong ID is a wrong join everywhere, not a local glitch.
- **Namesake collisions resolve toward the active player** (`claimName`). MLB's people-search deliberately spans historical players and every affiliated level, so common names collide with retired namesakes; the old unconditional `rp.ByName[k] = p.ID` was last-write-wins, and with the search batches running in parallel the winner was not even stable between runs. Measured live: several rostered players' names resolved to retired same-named players instead of the active one. This produced **confidently wrong data, not a visible failure** — `fetchMLBGameLog` succeeds against the retired namesake, finds no game, and the row is written `FPts=0, HadGame=false` with `needsBackfill` **cleared**, i.e. permanently recorded as a genuine off day. Two active namesakes (MLB has had two Will Smiths) remain genuinely ambiguous; the lower-ID tie-break only guarantees the same answer every run, not the right one. **`"active"` must stay in the `WithFields` mask** — omit it and every `p.Active` is nil, silently collapsing the rule back to lower-ID-wins.
- **A degraded resolution is returned but never cached.** Every error path used to be swallowed (`return nil` per batch, `continue` per detail block) while `fetchAndResolve` returned a nil error, so `cache.Get` persisted a partial or empty result for the full 7-day TTL. Three all-zero entries existed in production, all written in one bulk-build hour. The failure itself is transient and unavoidable — reproduced live across repeated runs — so the fix is `errDegraded`, handed to `cache.Get` purely to suppress the write while the partial map is returned out-of-band. Batches also retry (`searchWithRetry`) before counting as failed.
- **Search sends the raw name first, then the normalized one for misses only.** Neither spelling is a superset: `"A.J. Blubaugh"`, `"T.J. Rumfield"` and `"Zach Cole Jr."` return **0** results raw and resolve normalized (periods and suffixes stripped), while `"Ha-Seong Kim"` is the reverse, since `Normalize` turns its hyphen into a space. The second pass costs extra requests only for names that already failed. A residual gap remains that normalization cannot close: `"Jake Latz"` → MLB's `"Jacob Latz"`, a legal-name/nickname difference.

Verified end-to-end against Sleeper's independent MLB table over 133 real Fantrax names: ID disagreements went to zero and unresolvable names dropped to just Latz. The `diag`-tagged harness lives in `internal/playername/diag_*_test.go` (`DIAG_NAMES=... go test -tags diag`); it never runs in CI.

**The people-search is now the FALLBACK; the primary path is a season-scoped bulk index** (`internal/playername/seasonindex.go`, rosterbot-1x8). `GET /api/v1/sports/{1,11,12,13,14}/players?season=<year>` is fetched once per process (five requests, `mlb-season-players-<year>-<sportID>`, 24 h) and indexed on exactly the three variants `indexPerson` writes. Measured live 2026-08-31 over the 517-name rostered pool: index-only 492 resolved / 12 contested / 13 missed, search-only 516/1, **combined 516 resolved / 1 missed (Jake Latz) with 0 index-vs-search ID disagreements** — parity with the search at 1 search batch instead of 21.
- **The season scope removes the RETIRED-namesake class structurally**, which is the whole point: verified live, the retired Jose Altuve (501447) and inactive Jose Ramirez (691342) are absent from all five 2026 dumps while the active 514888/608070 are present.
- **It does NOT remove namesake ambiguity, and the bead's claim that it does was measured over 133 names rather than over the index.** The live 2026 index holds 6,917 keys of which **55 are contested**, and 12 of the 517 rostered names hit one. Every one of the 5,890 dump rows reports `active:true`, so `claimName`'s active tier is **inert** here and a lower-ID tie-break answers `thomas white` → 695720 (Tommy White) where the search correctly returns 806258. A contested key is therefore **declined** and falls through to the search, on `hkb.Lookup.Find`'s reasoning — a wrong match is worse than a miss, and a miss costs one search batch.
- **An index answer is PINNED (`nameClaim.fromIndex`), not merely written.** The index writes straight into `ResolvedPlayers` while `hydrate` indexes every person any search batch happened to return; without a claim the old `map[string]bool`'s zero value read "incumbent inactive" and any colliding namesake overwrote the index — an active one through the standing branch, a **retired** one through the lower-ID tie-break, retired namesakes usually carrying the lower id. That is rosterbot-bms reappearing through the composition.
- **A partial index is worse than no index, and it arrives two ways.** A failed sport fetch refuses the whole build (measured: dropping sport 1 leaves `luis garcia` uncontested at 472610, answering confidently where the full index declines). The same defect arrives through TIME, so `seasonIndexMinPlayers` (5000) refuses an under-populated dump: measured live, the not-yet-started 2027 season already returns 4,205 players against 5,768-5,965 for each of 2022-2026, and it decontests **both** known collision keys. The floor's failure direction is refusal — slow and exactly as correct as today — never a wrong answer.
- **An index outage is noise, never `errDegraded`.** Every name it fails to answer resolves through the search, so folding it in would suppress the 7-day cache write for a run whose answers are as good as today's. The failed build is memoized per process so a statsapi outage costs one line and five requests, never 186 of each; the negative result never reaches the disk cache. The memo lock is held **across** the fetches — `internal/recap` fans out per team and every worker reaches this path.
- **Two unconditional stderr lines, and the second is the load-bearing one.** The build line reports players/keys/contested; the request line reports names asked / answered by index / declined as contested / left to search. A build line alone cannot distinguish "the index worked" from "the index was present and answered nothing", which is the `il-start check:` / `mlb recency coverage:` precedent.
- **The search fallback is load-bearing for a recurring class, not a rump.** 12 of the 13 rostered-set index misses are players absent from every dump — Justin Steele's 40-man status reads `D60 Injured 60-Day` — because the dumps track current club affiliation, so 60-day-IL players fall out and return on activation. Deleting the search path would lose the injured half of a roster.
- **Deep-pool caveat.** `internal/prospects` resolves the FULL ~10,229-name pool, where the index answers only ~55%. Over a 1,000-name random sample there were **5** index-vs-search disagreements, all on the minor-league tail; checked against Fantrax's own Age column the index matched exactly on four and was merely closer on the fifth, with no case where the search was right — but they are corrections adjudicated by hand, not a proven invariant. `internal/prospects/performance.go` used to run a sixth, independent per-player search path (`resolveMLBPlayerID`) that bypassed the index entirely; it now resolves the whole roster once via `playername.ResolveMLBAMIDs`, the same call `buildRankLookups` makes, so this path carries the same namesake-collision guarantee as the other five call sites (rosterbot-hdiu).

**`internal/transactions`** — trade monitor. `CheckTrades` fetches recent Fantrax league trades (last 24 hours) via `GetRecentTrades`, groups them by `TradeGroupID`, values each side using HKB player rankings, and sends a Pushover notification with the trade report. Uses `playername.Normalize` to join Fantrax player names to HKB data. Requires `PUSHOVER_USER_KEY` and `PUSHOVER_API_TOKEN` for notifications (skips if not set).

**`internal/statcast`** — leaf owner of Baseball Savant data and the derived buy-low / hot **Statcast Signals** (imports only `internal/cache` and `internal/archive`). Holds the **Statcast Bundle** (`Bundle` — the five Savant expected-stats / quality-of-contact slices joined by MLBAM ID), `LoadBundle` (cached at `CacheTTL` = 24 h; cache-key prefix `keySavant` = `"savant"`, unchanged from its former home so existing `.cache/savant-*` entries still hit), the signal engine (`Signal`, `TagHitter`/`TagPitcher` returning `(Signal, SignalMetrics)`), `Thresholds`/`DefaultThresholds`, and `ArchiveArtifacts` (raw-CSV archival). Extracted from `internal/waivers` so `waivers`, `claims`, and `recap` depend on this data leaf — not on each other's command package. `TagHitter`/`TagPitcher` return a `SignalMetrics` of the facts behind the classification; callers own identity/report fields (e.g. `waivers.Candidate` embeds `SignalMetrics`).

**`internal/waivers`** — Statcast-driven waiver wire audit. `Run(ft, today, opts)` fetches the full Fantrax player pool, filters to MLB free agents (FantasyStatus `"FA"` / `"W*"` / empty, excluding `MinorsEligible`), resolves names → MLBAM IDs via `playername.ResolveMLBAMIDs`, and joins each FA against (a) FanGraphs projections (configured system; default `depthcharts`) from `projections.LoadBattingProjections`/`LoadPitcherProjections` for the per-game point projection, and (b) a `statcast.Bundle` of five Baseball Savant CSVs for signal tagging (the Savant loader and signal engine live in **`internal/statcast`**, not here — see below). Two signals fire per player: **BUY-LOW** when xStats outpace surface stats (hitter: `xwOBA - wOBA ≥ 0.030` AND barrel ≥ 9 AND hard-hit ≥ 42; pitcher: `era - xera ≥ 1.00` AND `xwoba ≤ 0.310`) and **HOT** when recent production is backed by quality (hitter: 14d `wOBA ≥ .380` AND `xwOBA ≥ .360` AND season barrel ≥ 8; pitcher: 30d `era ≤ 3.20` AND `xera ≤ 3.50`). When both fire, the row is tagged `BOTH`. Sample guards: hitter season ≥80 PA, hitter 14d ≥20 PA, pitcher season ≥100 TBF, pitcher 30d ≥50 TBF. Defaults live in `statcast.DefaultThresholds()`; tests override. The design separates concerns deliberately — Statcast picks WHO surfaces, FanGraphs scores HOW MUCH — so the league's own `ScoringWeights` (via `ExpectedPtsFromProj`) drive the ranking and FAs without a FanGraphs projection are skipped (accepted v1 limitation). Output: stdout (always), GHA markdown summary (when `GITHUB_STEP_SUMMARY` set), Pushover (when `!DryRun` and creds set; `formatPushover` fits the body to `pushover.MaxMessageLen` on whole blocks via `pushover.Builder` — the shared budget every Pushover formatter now uses: claims, prospects and the transactions `notifyBody` build whole blocks the same way, `cmd/football_trades.go` and `Send`'s backstop use the rune-safe `pushover.Truncate`, and `pushover.ShortName` replaced the twin per-package name shorteners). CSV fetchers (in `statcast/load.go`) have URLs as `var` for test override; column lookup is by lowercased name with aliases so Savant header drift doesn't break parsing. CSVs are cached at 24h TTL (`statcast.CacheTTL`) via `cache.FileCache[T]` keyed by year + window-end-date.

**`internal/claims`** — league-wide CLAIM/DROP recap. `Run(ft, today, opts)` fetches all recent Fantrax transactions via `GetAllTransactions` (cached as `fantrax-all-transactions-<leagueID>`, `todayTTL`), filters to CLAIM and DROP events since the last run using a cursor persisted at `.cache/last-claims.json`, and pairs each CLAIM+DROP by `Transaction.ID` to reconstruct complete moves. Each picked-up player is valued via HKB rankings (reusing the same normalized-name join as `internal/transactions`) to produce a "value gained" metric and a per-team daily leaderboard. When `!opts.NoSignals`, picked-up players are enriched with Statcast signal tags (BUY-LOW / HOT / BOTH) by joining against the `statcast.Bundle` and FanGraphs projections — the same enrichment path as `internal/waivers`. Notable drops (HKB value above `opts.DropsMin` threshold) are flagged with a watch note. Results are written to an audit ledger at `.waivers/claims/<date>.json` (directory created on first write). On an empty claim window the command is a no-op. Sends Pushover when `!opts.DryRun` and creds are set. `opts.Since` overrides the cursor for one-off historical recaps without resetting the cursor state.

**`internal/backtest`** — grades past work against actual outcomes. Two analyses:
- **Lineup grading**: for each past day, computes an actual-points total (sum of FPts for active-slot players) and a hindsight-optimal total (the existing optimizer run against a `hindsightSource` that returns each player's actual FPts as pts-per-game via the `PtsPerGameSource` / `PitcherPtsPerGameSource` interfaces). `Gap = actual - optimal`; negative means points left on bench. SP-eligible pitchers who actually appeared are fed to the optimizer as "probable starters" so the `NonStarterSPDiscount` (0.05x) doesn't apply in hindsight.

  **The hindsight source floors each player's value at zero (`hindsightValue`), and that floor is load-bearing** (rosterbot-0gm). `optimizer.optimalAssignment` fills every slot it can and only leaves one empty when *no* eligible player remains — sound for a live lineup, where projections are never negative, and wrong here, where the values are realised outcomes that go negative. Unfloored, a negative day gets forced into a free slot and "optimal" can land *below* the lineup we actually ran — observed 2026-07-02, where a reserve pitcher's -9.00 day was activated into an empty slot, reporting a gap that was positive and therefore impossible by construction (the lineup we ran is itself a feasible assignment). Flooring is not a fudge: benching a player yields exactly 0 and that option is always available, so `max(0, FPts)` *is* the achievable optimum, and it makes `optimal >= actual` provable (the actual lineup's floored value is >= its raw value, and optimal dominates every feasible assignment). The fix was confined to the hindsight source rather than teaching `optimalAssignment` to leave slots empty voluntarily, because that would change live tie-breaks (equal-value "leave empty" branches would grow `ToBench`, churning the roster) and slow the search. `guardOptimal` backstops the invariant: a still-negative gap is clamped to `actual` with a stderr warning, so a future regression surfaces as a warning rather than a healthy-looking green day on the dashboard. Impact of the floor was not one day — over a six-week window, roughly a third of days had understated optima and season efficiency fell by ~1.6pp.
- **Projection grading**: checks `.backtest/snapshots/<YYYY-MM-DD>.json` for archived per-player projection values written by `optimize`. Each snapshot row (`backtest.SnapshotPlayer`) records the projected pts/game plus look-back fields — `status`, `slot`, `locked`, `role`, and `eligibility` (position IDs) — so error can be sliced by position and lineup decision. **There is deliberately no `was_started`.** It existed until rosterbot-x3xo and was `Status == "Active"` restated under a name that claimed deployment; since the winning snapshot is written by the last hourly run of the ET day, by which point finished starters have been rotated back to Reserve, it was wrong in both directions at once. Measured over period 20 against the active-slot GS walk: the walk counted 10 starts, the field claimed 42, and none of the seven days agreed — for pitchers it was a constant 6 (the P-slot count) and marked relievers as "started" daily. **Deployment is not knowable when the file is written**, because the file describes a day still being played; it is joined at grading time instead, from `fantrax.DayRoster`'s own per-day `Active` flag, surfacing as `PlayerProjection.Deployed` and as `SummarizeRosterShape`'s day-keyed lookup. Old files keep the key; Go ignores it on load. When present, grading compares against actual FPts for an overall MAE/Bias/RMSE report, a per-position MAE table (buckets C/INF/OF/UT for hitters via eligibility precedence C>INF>OF>UT, and SP/RP for pitchers via role), and the top-10 signed-error misses (ordered by **absolute** error descending, `worstMisses` in `internal/report/aggregate.go`, tie-broken on player ID — the displayed sign is retained, and the list merely *looks* over-projection-skewed because SP blowups dominate the largest absolute errors). When a day's snapshot is absent, the day is marked `source="missing"`. When a snapshot exists but its `generated_at` falls on a different ET calendar day than the date it projects — a `--matchup` pre-write that was never refreshed on the day itself (e.g. every hourly run that day failed) — the day is marked `source="stale"` and excluded from the rollup, since grading a multi-day-old forecast inflates apparent projection error (`sameETDate` guard in `backtest.go`, keyed on ET since that's the zone the daily runs and matchup-day boundaries are anchored to; a zero `generated_at` predates the field and is graded as before). `FormatReport` prints an "Excluded from grading: N stale, M missing" line listing the dates, so a window thinned by stale/missing days is visible rather than silently shrinking the sample. The hourly `lineup.yml` workflow runs `optimize` (which writes snapshots by default on non-dry-run) and persists `.backtest/snapshots/` in the GHA cache (alongside `.cache`), so production accumulates a snapshot per day from the most recent hourly run. Local backtest runs that need the snapshots have to either (a) replay the workflow's cache or (b) run `optimize --archive-projections` themselves.

Per-day FPts come from `fantrax.DailyFantasyPoints` (in `internal/fantrax/daily_fpts.go`), which walks a period range and diffs consecutive YTD snapshots via `playerStatsFromTables`. This covers both `scGroup=10` (hitting) and `scGroup=20` (pitching). The Fantrax roster API is requested with `StatsType=1` (MLB stats — real per-player season totals) rather than `StatsType=2` (Fantasy Team — team-credited only) so reserve players' production is visible to hindsight callers; without this, the optimal lineup calc in the backtest/recap can never recommend a benched player and efficiency % stays artificially compressed (~95–99% across the league).

Players seen for the first time in the window have their `(deltaFP, deltaGP)` zeroed so the cumulative pre-window YTD doesn't leak in as same-day production (a waiver pickup with a 200-FPts season-to-date YTD would otherwise inject 200 phantom points on the day they appear). The zeroed row is flagged internally via the **unexported** `DayPlayerFP.needsBackfill`, and **`DailyFantasyPoints` resolves it before returning** (via the unexported `backfillDailyFPts` in `internal/fantrax/mlb_backfill.go`): it fetches the player's MLB statsapi game log for that date and computes FPts from raw stats × the league's `ScoringWeights` — bounded to a handful of API calls per recap week, soft-fails to "leave zero" on any error. **Callers never see the placeholder and never pair a second call** — folding the backfill into `DailyFantasyPoints` removed the six-call-site convention where five callers remembered the pairing and `recap.seasonToDateTeamMean` (the WP-model input) silently didn't, deflating every team's season-to-date mean by every mid-window waiver pickup/role crossing (rosterbot-8ue). Two-way crossings (Ohtani moving between the hitters and pitchers tables) are handled the same way: `diffYTD` detects the `prevOther` fallback (role-specific YTDs can't be meaningfully subtracted), zeroes the diff, sets `needsBackfill`, and the backfill computes the role-correct same-day FPts. The end-to-end path is covered by `TestDailyFantasyPoints_ResolvesBackfillInternally` (through the public entry point, via the `fetchPeriodSnapshotFn` seam). Both fixes verified against the Fantrax-authoritative `Matchup.HomeTeam.Points` for a full matchup week (recap matched every team total exactly). Per-period snapshots are cached at `.cache/fantrax-roster-stats-<teamID>-<season>-<period>.json` at `PastPeriodTTL` since settled past periods are immutable. A parallel cache `.cache/fantrax-pitcher-gs-<teamID>-<season>-<period>.json` (same TTL) backs `GetTeamPitcherStarts`, used by the recap to enumerate every active-slot SP start; it's optional (pass `cacheDir=""` / `cacheTTL=0` to bypass, which the live `gs-check` path does because it always wants fresh data), and when the cache hits, the per-day 200ms upstream-throttle in `GetTeamPitcherStarts` is skipped. **Both build one cache per period, not one per window** — the caller hands in a single long TTL and `snapshotTTL` narrows it to `todayTTL` for any period still in the volatility window. `DailyFantasyPoints` has done this since the Sunday-night-recap bug; `GetTeamPitcherStarts` used a single flat-TTL cache until rosterbot-qoa, which was survivable at 30 days and would have pinned the live period for the season at `PastPeriodTTL`.

Snapshot writing is default-on for real (non-dry-run) `optimize` runs so the cron accumulates backtest data automatically. Dry-run stays side-effect-free unless you opt in with `--snapshot` (the older `--archive-projections` flag and `BACKTEST_ARCHIVE=1` env var are kept as backward-compatible aliases). Snapshots are rewritten if the same date is optimized twice, but not blindly last-write-wins: `writeProjectionSnapshot` (`internal/lineuprun/snapshot.go`) merges onto whatever was already archived for that date, and any player row whose EXISTING entry was `Locked` (team game underway/final) survives every later rewrite wholesale — a post-lock rescore (an in-game injury, a rotation back to Reserve) must not overwrite the projection the optimizer actually used when the lineup was decided (rosterbot-w79p; the Cade Cavalli 2026-08-29 case). Every other row, including one locked only in the newer write, still takes the latest write, which is what keeps a `--matchup` pre-write's intraday refinement working. If the day's final write never lands (the day's runs all failed), the snapshot is left as an earlier pre-write and the stale-snapshot guard above excludes it from grading.

**Multi-system capture (`shadow`)** — `cmd/shadow.go` drives the full `internal/lineuprun.Run` pipeline (matchup adjustment included) once per RoS system in dry-run, capturing every system's projection side-by-side for the model-comparison report — no lineup applied, no notification. It shares the orchestration engine with `optimize` (zero pipeline duplication) by calling the same `Run` entry point in a loop: each iteration calls `initApp` fresh and builds an `Options` with `HitterSystem`/`PitcherSystem` both set to `sys` (the per-role split of the former single `ProjectionSystem` field, rosterbot-5qvs — the hourly `optimize` resolves them per role from the tenant's stored preference, explicit `--projections` overriding both), `SnapshotRoot: systemSnapshotDir(shadowSnapshotRoot, sys)` (instead of the flat `.backtest/snapshots/`), and `ForceSnapshot: true`, looping over `shadowSystems` (`steamer-ros`, `depthcharts-ros`, `thebatx-ros`, `atc-ros`). `grade` then loops the same `shadowSystems`, calling `RunProjectionAnalysis(days, systemSnapshotDir(...))` per system (actuals fetched once) and writing each system's rows under its `system=` partition. The hourly `optimize`'s flat snapshot is untouched (it still feeds the local `backtest` command). The EventBridge `Shadow` schedule runs **23:40 UTC** — late ET evening but still the **same ET calendar day as the captured date**, so the snapshot's `generated_at` passes the `sameETDate` stale-guard and is graded by the next 13:30 UTC `grade` run. `.backtest/snapshots-systems/` rides the existing recursive `.backtest/` S3 sync (`del=false`), so the shadow task's `sync-up` and grade task's `sync-down` hand it across Fargate tasks with no entrypoint change.

**GS gate summary** (`gs_gate_summary.go`) — `SummarizeGSGate` reads the same projection snapshots as roster shape below and totals the starts the weekly game-start gate declined, keyed off `SnapshotPlayer.GSSuppressed`. `GateSummary` counts `DaysWithSnapshot` (present AND fresh, per the `sameETDate` rule `RunProjectionAnalysis` uses) separately from `DaysStale`: the gate runs for today's date only, so a `--matchup` pre-write for a future day always carries `GSSuppressed=false` for every pitcher, and counting that day as measured would report a real gap in the run history as a quiet, suppression-free week rather than excluding it the way a missing day already is. `SuppressedPts` is GROSS projected value declined, not a net weekly loss — the budget the gate withheld from the declined start went to a higher-ranked one instead, it wasn't destroyed, so summing it across days does not answer "how many points did this cost." `FormatGateSummary` renders the total suppressed starts/points plus a per-date breakdown for any day with at least one suppression **or protection**. The **floor line prints whenever a minimum was in force, not only when protection fired**: the suppression line reads "0 start(s) suppressed" identically on a healthy week and on one that finished *on* the floor, which is exactly the week that matters, so a summary able to speak only when the ceiling binds cannot describe the failure that actually recurs. `ProtectedStarts`/`ProtectedPts` are disjoint from the suppressed figures and GROSS in the same sense — value that stayed deployed, not value gained; the two are never summed. Zero `FloorDays` renders as "no GS minimum configured", never as "floor 0", which would read as a floor of none rather than an absent one.

**The whole report reaches `--json` and the dashboard** (rosterbot-5cx). `Report.Gate` and `Report.Shape` are computed *before* the `--json` early return and both hang off `!--skip-projections`, since each reads the projection snapshot dir — two of them previously walked it regardless, making the flag a claim the code did not honour. `backtestToWireResult` maps the gate to `lineupapi.BacktestGateOut`; because the dashboard's run viewer is a generic JSON-to-DOM renderer that prints object keys verbatim as headers, **the json names are the labels a reader sees**, which is why `suppressed_pts_gross`/`protected_pts_gross` carry GROSS in the key and `days_with_snapshot`/`days_stale` stay separate. Progress chatter moved to stderr in the same change: `backtest --json` used to emit a human line ahead of the document and was not parseable at all.

**Roster shape** (`roster_shape.go`) is the analytical companion to `GateSummary`: per side, the share of *deployable* projected value the roster fielded, with slot counts and the weekly GS cap alongside. Two denominator rules are load-bearing. **`HasGame` is not the availability test for a starter** — `SnapshotPlayer.ProjPtsPerGame` is the *undiscounted* projection (`NonStarterSPDiscount` is applied downstream of the snapshot, inside `OptimizePitcherLineup`'s local slice) and `HasGame` means only "team plays", so a `HasGame` denominator credits an ace his full projection on four rest days in five and reports rotation cadence identically for every roster in the league; the test is `IsStarter || GSSuppressed`, which reconstructs the *pre-gate* probable-starter set. That puts every start `FormatGateSummary` names into this side's OWNED total, **not** stranded — whether a gate-declined start actually lands in stranded depends on what happens next: `applyGSGate` discounts the pitcher to 0.05x but `OptimizePitcherLineup` still adds him to the slot-assignment pool if he has a game, so on a light slate the pool fits inside the 6 P slots, the suppressed SP is slotted anyway, and his full undiscounted projection lands in fielded instead. **The FIELDED numerator comes from `fantrax.DayRoster`, not the snapshot** (rosterbot-x3xo) — `SummarizeRosterShape` takes `[]fantrax.DayRoster` and builds a per-day `deployed` map from Fantrax's own frozen `Active` flag; a player absent from that day's roster reads as not deployed, the conservative direction. Correcting this moved period 20 from 63%/58% to 77%/100%: the 80.1 "stranded" pitcher points were entirely an artifact of the old field. **IL and Minors are excluded** via `SnapshotPlayer.Status`, since one boolean cannot distinguish a healthy benched player from an injured one and an injury would otherwise read as a structural surplus. Each side is normalized against its own owned value, never against the other, so a roster carrying exactly its slot count reads 100% on both sides whether the league fields 13 hitters or 9 — the comparison cannot reduce to the slot ratio. Rates are value-weighted (`Σfielded / Σowned`), not a mean of daily rates. The block also prints each side's `DeployableCount`/`RosteredCount` as a Coverage line, because the pitcher denominator is often narrow (measured as low as 2 of 13 rostered pitchers) and a rate computed on that base would otherwise read as a confident statement about the whole staff rather than about a couple of probable starters. The two stranded figures share a unit but are never summed: a benched hitter starts tomorrow, a start above the weekly cap is dead, the same GROSS-not-net asymmetry `GSGateReport.SuppressedPts` documents. `Status` and `GSLimit` exist only from 2026-08-06 forward; a fresh snapshot in which *every* status is empty is counted as `DaysPreSchema` and excluded, because the deployable filter would otherwise leave it with zero owned value and make it indistinguishable from a fully-fielded day.

**The pitcher `FieldedRate` measures probable-start COMPLIANCE, not rotation surplus, and `RotationSupply` is the measure that answers the surplus question** (rosterbot-8dl). Once the numerator was corrected the pitcher side read *exactly* 100% on three consecutive live weeks against rosters of 9–13 pitchers: MLB rotation cadence holds the daily probable count inside the 6 P slots at any depth, so the daily frame is structurally incapable of seeing surplus — a statistic that can only emit one value is not a measurement. Rather than refit that denominator (all three candidates in the bead were measured and none separates depth), `RotationSupply` changes the frame to weekly capacity: mean rosterable SP-eligible pitchers per day → `mean × 7 / RotationSize` starts supplied per week, against `GSCapMax`. It moved 105%/108%/110% across the same three weeks the old rate was pinned on, and separates 70% from 152% for genuinely different depths. `SupplyRate` is **withheld and the line not printed at all** when no cap was recorded — the ratio is the whole point, and Fantrax rescales the cap for merged periods, so a bare "supplies 13.2 starts/wk" invites the reader to supply their own denominator. `standardRotationSize` is duplicated from `lineuprun.RotationSize` because `lineuprun` imports `backtest` and the dependency cannot run back; `TestStandardRotationSize_MatchesLineuprun` in the external test package is the only thing preventing a silent divergence.

**`internal/recap`** — Sleeper-style weekly recap. `recap.Run(ft, opts)` aggregates all 12 (or however many) teams in parallel via `errgroup`: for each team it pulls `DailyFantasyPoints` for the matchup week and runs `backtest.RunLineupAnalysis` to compute actual + hindsight-optimal totals, plus `GetTeamPitcherStarts` (a sibling to `GetTeamGS` in `internal/fantrax/pitcher_starts.go`) to enumerate every active-slot SP start with its FPts. H2H pairings come from `GetAllMatchupEntries` (a passthrough wrapper added on `*fantrax.Client`); team weekly scores are aggregated from daily FPts (deterministic, doesn't depend on parsing the upstream `MatchTeam.Total`). Award functions in `awards.go` are pure and unit-tested. **League Leaders** (`leaders.go`, `buildLeaders`) ranks every rostered player league-wide (from `GetFullPlayerPool`, filtered to `FantasyTeamID != ""`) by season-to-date wOBA (hitters) and FIP (pitchers): names → MLBAM IDs via `playername.ResolveMLBAMIDs`, wOBA joined from `statcast.LoadBundle`'s qualified-hitter expected-stats CSV, FIP computed from a batched MLB statsapi season-pitching fetch (`mlbSeasonPitchingURL`, `parseIP` handles `.1`/`.2` thirds) with the FIP constant solved from the rostered-pitcher pool so displayed values land near league average (ranking is constant-invariant); pitchers need ≥`fipMinIP` (30) innings. The whole path soft-fails to nil — the section is `{{if}}`-guarded out when empty, so archived/credential-less renders stay clean. The single-day leaderboards and league-leaders board both badge each row with the owning team's logo (`PlayerLine.OwnerTeamID` / `LeaderLine.OwnerTeamID` → `teamLogo`) instead of a rank number (rank implied by order); default board size is top 5 (`--top`). The season leaderboard (`RenderSite`) follows the same rank-implied-by-order convention: award categories drop the numbered chip (owner logo only), and the season Shellings list badges each row with the pitcher's **MLB-club** logo via `mlbTeamLogo` (abbrev → statsapi team ID → mlbstatic "spots" PNG endpoint; `mlbTeamAbbrevToID` covers both canonical and upstream-variant abbreviations, falling back to a text chip on an unknown code). Two render helpers centralize the avatar markup so award cards stay terse: `teamBadge(logos, id, name)` emits the fantasy-team logo-or-initial chip (used left of the name in Most/Least Efficient and every League Award card — winner-side cards pass `WinnerID`), and `mlbBadge(abbrev)` emits the MLB-club logo-or-text chip (used left of the pitcher name in the Pitching Highlights best/worst cards). Both return trusted `template.HTML` (our own URLs; names HTML-escaped). The renderer (`render.go` + embedded `template.html`) emits a single self-contained HTML file via `Render` (no nav) or `RenderSite` (with a cross-week dropdown). `recap.RunSite(ft, sopts)` (`internal/recap/site.go`) drives the multi-week build: it enumerates every completed matchup week via `GetMatchupWeekByNumber`, calls `Run` for each, and writes `dist/week-NN.html` plus `dist/index.html` (mirror of the latest week). Each page carries a `<select>` dropdown of all weeks. The `recap-site` CLI command exposes this for the GitHub Pages workflow.

**Week-completion signal** — `completedMatchupWeeks` and the `recap` command's range resolver treat a week as renderable when `weekEnd < today` (strict, date-only) **OR** `weekEnd == today AND every MLB game on that final day is over**. The same-day path lets a Sunday-ending week render the same evening once its games conclude. The completion check is `schedule.Client.AllGamesFinalOn(date)` (MLB statsapi `abstractGameState == "Final"`, plus Postponed/Cancelled via `detailedState`; vacuously true when no games are scheduled that day). The Fantrax weekly `Matchup.*.Points` field is **not** used for this — it's a **running in-week score** (non-zero from the week's first games onward), so an earlier `MatchupWeekIsFinal`/`IsMatchupWeekFinal` heuristic that keyed off `Points > 0` was removed for falsely flagging in-progress weeks (it rendered week 10 on its live final Sunday). `completedMatchupWeeks` takes a `dayCompletionChecker` interface (satisfied by `*schedule.Client`) so the cutoff logic is unit-testable without network; on a schedule lookup error the same-day week is conservatively excluded.

**WP model** — `wp.go` exposes `ComputeWPCurve`, `LeadChangeCount`, `MinWinnerWP`. `ComputeWPCurve` is a Go port of the formula Fantrax runs client-side in its live-scoring Angular bundle (`models.CalculateWinProbability` in go-fantrax): deterministic, no Monte Carlo, no sigma. At each of 8 points (pre-week + 7 day-ends) it feeds cumulative actual FPts, a **live-adjusted** weekly projection (`actual_so_far + remaining_days × HomeMeanDaily`, mirroring how Fantrax recomputes `calculatedProjectedTotalsMap` intra-week — without the live adjustment the projection ratio stays flat all week and the chart degenerates to 50% then a snap to 100%), and a uniform `timeLeft = 7 - i` for both teams into the Fantrax formula. Pre-week WP[0] reflects projection ratio (a 60/40 projected favorite starts at ~84/16, not 50/50). Final WP[7] is always 100/0 or 0/100 — on an exact-tie final the Fantrax formula awards the win to "away" (faithful port; ties never happen in practice with float FPts).

**Game of the Week** — always featured at the top of every week (no skip for quiet weeks). Picked by `GameOfTheWeek(curves, matchups)` using `score = LeadChanges + (1 - minWinnerWP)` — the "weeeeeh factor": back-and-forth swings plus how deep the eventual winner sank mid-week. Ties broken by smallest final margin then home `TeamID` asc. Ties (no winner) score with the comeback term zeroed. The hero chart is rendered as a 380×140 SVG with mirrored 100/75/50/75/100% y-axis labels, half tints (green=home favored on top, red=away favored on bottom), team name labels in their respective halves, and dated x-axis ticks. The matchup-results list marks the chosen game with a ⭐ badge.

**Comeback award** — winner whose mid-week WP dropped below `comebackThreshold = 0.30` (eventual-winner's minimum during `Points[1..6]`). Feeds into `AggregateSeasonAwards`. Game of the Week is intentionally excluded from the season leaderboard — it shows at the top of each week's page, so cumulative counts would be redundant.

**Analytics & reporting stores** (`internal/ndjsonstore`, `internal/analysis`, `internal/report`, `internal/teamvalue`, `internal/valuereport`, `internal/lineupgap`) — the durable model-performance/dynasty-value pipeline behind the `grade`/`team-values` commands and the dashboard's Projections/Value tabs. Full detail moved to **`docs/analytics-stores.md`**; read it before touching any of those packages.

**`internal/archive`** — stdlib-only leaf package for durable daily snapshots of ephemeral upstream data that can't be re-fetched later. Defines `Artifact{Filename, Bytes}`, a `Source` interface (`Fetch(ctx, date) ([]Artifact, error)`), `FuncSource` (adapter), `Writer` (writes raw bytes to `.archive/<source>/dt=YYYY-MM-DD/<filename>`), and a shared `Get` raw-fetch helper. Concrete source implementations live in each provider package: `ArchiveArtifacts(ctx, date)` in `internal/{hkb,projections,statcast,prospects}` covers HKB rankings, all four FanGraphs RoS systems (steamer-ros/depthcharts-ros/thebatx-ros/atc-ros, batting + pitching = 8 blobs), the five Baseball Savant CSVs (season plus 14d/30d rolling windows), and the FanGraphs prospect board. The `archive` CLI command (`cmd/archive.go`) runs all sources with per-source isolation — one failure doesn't block others; exits non-zero only if every source fails. Supports `--date YYYY-MM-DD` (default today UTC) and `--dry-run` (fetch + print sizes, write nothing). **`--date` accepts today only** — `resolveArchiveDate` in `cmd/archive.go` refuses any other day, in dry-run too. The sources are not date-parameterised (only two of Savant's five CSVs take a range at all), so a past `--date` never backfilled that day: it wrote *today's* bytes under a historical `dt=`, filling the gap on the Infra page while making the archive silently wrong — strictly worse than the gap. A future date is refused as well, since a `dt=` ahead of today would pin `LatestPartition` permanently fresh and mask staleness. There is deliberately no `--force`: the flag could only ever write data that is wrong, and nothing downstream can tell such a partition from a real one. The corollary is that `layout.Archive` is **`NoBackfill: true`** — a day nobody archived is gone, so the Infra page must rank its gaps beside the Team Value Store's rather than footing them "Re-runnable" (**rosterbot-0l31**). `.archive/` syncs to S3 `archive/` prefix via `statePairs` in `cmd/sync.go`, uploaded append-only (`del=false`, keep-forever). Distinct from the TTL cache (which overwrites on expiry) and additive to the projection snapshot/Analysis Store.

**Trade valuation and the Trades tab** (`internal/tradevalue`, `internal/tradeboard`, the trades producers/cadence, `/v1/trades*`, and the private `/v1/reports/{model,gap,views}` split) — full detail moved to **`docs/trades.md`**; read it before touching `internal/tradevalue`, `internal/tradeboard`, `cmd/trades.go`, or `internal/lineupapi/{trades,reports}.go`.

**`internal/recaplog`** — recap-site readership. The recap site is **public and unauthenticated**, so CloudFront access logs are the only signal that anyone reads it; there is no session to attribute a view to, which bounds what this can honestly claim — **a client IP is a network, not a person**. `SiteCdn` writes standard logs to `RecapLogBucket` under `recaplog.Prefix` (`recap/`, which **must** match `LogFilePrefix` in `infra/infra.go` — changing one alone silently yields no data), expiring after 90 days. The package is a leaf: `Parse` (gunzip + positional TSV, skipping the `#Version`/`#Fields` lines and any malformed row rather than failing the object), `IsPageRead`, `BuildModel` and `ReadRecent` are pure over a byte-level `Store` seam, with the S3 implementation in `internal/recaplog/s3recaplog` (a shim over `internal/s3blob`, **read-only** — CloudFront is the only writer, and the task role's IAM is `GetObject` scoped to `recap/*`). `ReadRecent` walks keys **descending** (CloudFront names objects `<dist-id>.YYYY-MM-DD-HH.<hash>.gz`, so that is reverse-chronological to the hour) and stops once the limit is met, keeping the read bounded rather than growing with the retention window. **`IsPageRead` (status 200 + `/` or `*.html`) is load-bearing**: CloudFront logs every object, so without it the table fills with `/favicon.ico` 403s from every real browser visit. Field positions are fixed by CloudFront's format and must not be reordered; the test fixture carries the real `#Fields:` header so a format change fails a test rather than silently shifting columns. `cmd/projection-site.go`'s `renderViewsSite` publishes the views report to the private `reports/` prefix beside the model and gap ones, soft-failing independently, and is skipped entirely when `RECAP_LOG_BUCKET` is unset (the normal local-dev case — these logs exist only in AWS, so a local `GET /v1/reports/views` correctly 404s). The SPA's `views.js` renders the "Views" tab from `GET /v1/reports/views`. **It builds rows with `createElement`/`textContent`, not `innerHTML`**, because `uri` is attacker-supplied — anyone can request a crafted path against a public site and land it in this table — and `render.js`'s `escapeHtml` escapes `&<>` but **not quotes**, so it is unsafe in an attribute context.

**Infra status (`GET /v1/infra`)** — the dashboard's "Infra" tab. `internal/lineupapi/infra.go` lists every prefix in `layout.All()` and judges each against its declared `MaxAge`, returning a per-artifact `Health` (`ok`/`gap`/`stale`/`missing`/`unknown`) plus object count, size, age, `dt=` partition count and sub-dimension values. It reads **live** rather than serving a precomputed file — deliberately, since a status page built from a scheduled artifact goes stale in exactly the situation it exists to detect and could report "all healthy" while the job that writes it is the thing that died. The listing itself is a one-method `InfraLister` seam: `s3lineup.NewInfra` on Lambda (a bucket-root `s3blob.Blob`, walked with an early stop at `maxKeys`), `lineupapi.NewFileInfraStore` for local `serve` — both set `PrefixListing.Truncated` on a degraded read, the S3 side on hitting its cap and the local side on an entry its walk couldn't read (rosterbot-xi3p), since neither cause changes what a reader should do with the resulting floor. Every judgement lives in `lineupapi` and is unit-tested without AWS. Two derived signals do the real work: **gap detection** on partitioned series (scanning to *yesterday*, since today's producer may not have run yet), fatal only where `NoBackfill` is set; and **sub-dimension coverage** — the `system=` values under `analysis/grades/` and the per-source dirs under `archive/` — so one shadow system silently stopping shows as a missing chip rather than no error at all. IAM is `s3:ListBucket` only: the endpoint reports listing metadata and never reads an object body, so the Lambda still cannot read `session/` or `claims/` contents.

**"Re-runnable" is a checked claim, not the default (rosterbot-fix-8bf02c).** The page used to foot every gap outside a `NoBackfill` artifact with "Re-runnable", an assumption stated as a fact. A day is graded by joining its actuals against **the projection snapshot captured on that day**, so an Analysis Store gap is recoverable exactly when `backtest/` still holds that day's capture — a `Shadow` outage that captures nothing (the `sameETDate` stale-guard correctly rejects a backdated re-capture) leaves a permanently ungradeable day, which used to sit in the same list as an ordinary re-runnable one. `layout.Artifact.RecoveryInput` names the prefix a missing day must be re-derived from (`Analysis` → `backtest/`); `recoveryFor` reads it, and `ArtifactStatus.LostGaps` reports the subset that has no input. Three properties are load-bearing. **Loss is a positive finding**: the zero-value `recovery` answers "recoverable" to everything, so an artifact with no declared input, or one whose input listing failed, never has days written off — and that failure is visible anyway as the input artifact's own `HealthUnknown` row on the same page. **It is a per-day check, not a per-artifact flag**, because the whole distinction is that one series holds both kinds of gap at once. And **`LostGaps` deliberately does not move `Health`**: a `NoBackfill` artifact escalates because a gap there is exceptional, whereas an unrecoverable day in an otherwise-recoverable series never heals, so escalating would pin the row red for the season with no action that could clear it — a permanent red is how a status page teaches you to stop reading it, the same reasoning that stops `findGaps` scanning past yesterday. Because the projection snapshots are named `<date>.json` with no `dt=` segment, both listers now read a day from a `YYYY-MM-DD.<ext>` basename as well as from a Hive partition; only `Partitioned` artifacts are gap-scanned, so filling `Partitions` for a flat prefix adds a fact without changing a verdict.

**A deliberately-skipped day is named, not merely uncounted (rosterbot-36r).** rosterbot-u9u had `grade` write a `no-actuals.json` marker for a day no rostered player played, which correctly stopped the gap scan counting a hole — and left that day indistinguishable from a graded one in `Partitions: N`. `PrefixListing.SkippedDays` / `ArtifactStatus.Skipped` now name them, on the predicate **"a marker is the ONLY object under that day"**. Both halves are load-bearing. The **filename** is the only signal available at all: the Infra Lambda holds `s3:ListBucket` and no `s3:GetObject`, so it can never read `SkipMarker.Reason` — which is why `analysis.SkipMarkerFilename` is exported rather than a literal in three places. And **"only"** is not belt-and-braces: `cmd/grade.go` writes the marker unconditionally on that run's judgement, `analysis.Writer` has no delete counterpart anywhere in the tree, and the default grade window re-grades the trailing 3 days — so a day marked skipped on Monday can receive real rows on Tuesday with the marker still beside them. Keying on the marker's presence alone would label such a day skipped forever, with nothing able to clear it. A truncated S3 walk **withholds the field entirely** rather than guessing: within a `dt=` day, `no-actuals.json` sorts before `system=…` (n < s), so a walk stopping between them sees the marker and not the grades, and would report a graded day as skipped (rosterbot-u734 covers the same exposure in the older fields). Like `LostGaps`, `Skipped` deliberately does **not** move `Health` — the day is correct by construction, and colouring the row for it is how a status page teaches you to stop reading it.

**A tenant qualifier that disambiguates nothing is not rendered.** Per-tenant gaps are still *computed* per tenant (unioning `dt=` values across tenants hides a day present for one and missing for another), but the label carries the tenant id only when `len(Tenants) > 1`. The deployment has one tenant whose id is an 87-character opaque WebAuthn handle, and prefixing it onto every gap buried five dates under five copies of the same string. Where it is carried, `infra.js` leads with the date and trails a six-character muted tag with the full id in a `title`.

**A prior All-Star-break gap was the rosterbot-u9u `SkipMarker` arriving after the fact.** The marker code landed weeks after that break and `grade` only revisits a trailing 3-day window, so those dates were never re-examined and no marker was ever written until manually backfilled with a dated `grade --dates` run. **Dry-run first is the rule for a dated `grade` backfill**: if the range had graded rather than skipped, the run would have written a full slate of `actual=0` rows into the accuracy store for every system rather than a marker, which is corruption rather than a no-op.

**`internal/notify`** — the fantasy-event dispatcher. Call sites emit `notify.Send(ctx, Event{Kind, Title, Message})`; the dispatcher writes the durable activity-feed record **first** (its id rides in the APNs payload — tap-to-open needs it, so the ordering is load-bearing and pinned by `TestFeedRecordSurvivesADeliveryFailure`), then fans out to best-effort sinks: APNs (per-tenant device fan-out with dead-token pruning on `apns.ErrDeviceGone` only) and Pushover while `PUSHOVER_FANTASY_DUAL_SEND` is set (the cutover flag — deliberately not keyed off `PUSHOVER_USER_KEY`, which the operator channel owns permanently). `Send` errors only on a failed feed write. Wired once in `cmd.initShared` (`installNotifyDispatcher`); the recipient is the ambient tenant (`ROSTERBOT_USER_ID`), so no recipient parameter threads through any call chain. **Exactly nine fantasy call sites route through it; four operator sends (connect blocked, stale-cache fallback, GS limit fetch failure, shadow projection status) still call `SendPushover` directly** — their audience is the operator and they must not depend on the infrastructure whose health they report. `gs-check` does both, permanently: dispatcher + the retained `PUSHOVER_GROUP_KEY` league broadcast (app-less league mates are unreachable by APNs; duplicate delivery for anyone on both channels is accepted). The Pushover HTTP client itself lives in **`internal/pushover`**, a stdlib-only leaf, because `notify` now pulls `lineupapi` (→ fantrax → chromedp) through its sinks and the `opsnotify` Lambda sends Pushover without any of that; `notify.SendPushover` stays exported as a thin delegate so operator call sites never moved. **Every dual-send push still lands on the one deployment `PUSHOVER_USER_KEY` regardless of which tenant's job sent it** (rosterbot-b1oh) — `PushoverSink.TenantLabel`, resolved per run by `cmd.resolveTenantLabel` from the tenant's `DisplayName`, prefixes the title (`"[label] title"`) so a tester's push doesn't read as the operator's own team; it stays empty (untagged, unchanged from before this field existed) for a single-tenant/local-dev run, for the operator's own tenant (`OPERATOR_USER_ID`, a self-tag would be pure noise), and whenever the identity lookup has nothing to offer.

**`internal/apns`** — APNs sender: stdlib ES256 provider-token JWT (`ecdsa.Sign` + `FillBytes`, **never `SignASN1`** — DER comes back as `InvalidProviderToken`, which reads like a credentials problem), cached 50 min per process; HTTP/2 `POST /3/device/<token>` with `apns-topic` = the device record's `bundle_id`. The host is routed by the device's **stored** `environment` (sandbox|production), never inferred: a sandbox token on the production host answers `BadDeviceToken`, byte-identical to a dead token, and the pruning rule would silently delete every development device. `ErrDeviceGone` fires only on 410/`Unregistered` and 400/`BadDeviceToken`.

**Push device store** — `lineupapi.PushDevice`/`PushDeviceStore` (registered via `POST/GET/DELETE /v1/push/devices`, session-only — the bearer token has no UserID to attach a device to, `handleConnect`'s precedent; registration answers the stable `{"id"}` the iOS client persists for sign-out revocation). Implementations: `FileUserStore` (devices under the user's dir so `DeleteUser` sweeps them) and `ddbuser` (`USER#<uid>/PUSHDEVICE#<id>` items plus a `PUSHTOKEN#<token>` → `USER` pointer, the CRED#-style cross-user lookup). **Registration is idempotent on token AND steals it globally**: a token already held by a *different* user deletes that user's record in the same registration — the previous owner's expired session can never issue its own revocation, so this is the only moment the stale record can be reaped, and skipping it leaks the device into the old owner's notification fan-out forever. `pushdevicetest.Run` is the contract; both implementations must pass it.

**`internal/opsalert`** — decides whether a finished job run is worth waking an operator, and renders the message. A **stdlib-only leaf**: its only consumer is the `opsnotify` Lambda, and `internal/lineupapi` (where the run ledger's wire types live) transitively pulls `internal/fantrax` and therefore chromedp, so `opsalert.Record` redeclares the eight ledger fields it needs and `internal/lineupapi/opsalert_contract_test.go` (`package lineupapi_test`, so it can import both without `opsalert` importing `lineupapi`) marshals a real `lineupapi.RunDetail` into it to guard the duplication. `Streak(recs, command, userID)` reads newest-first ledger records and returns one of four verdicts: `Started` (first failure after a success), `Escalated` (the `EscalateAt`=3rd consecutive failure, matched on `==` so an eleven-failure outage escalates exactly once), `Recovered` (first success after failures), or `None`. **The whole decision is derived from the append-only ledger**, which is what removes the counter object and the cooldown timer a naive design needs — streak transitions deduplicate themselves. `RUNNING` records are skipped: they are the start-of-run write that the terminal write later overwrites at the same key, so an in-flight sibling job must not break a streak. The message body quotes the **last non-empty line** of the record's `log_tail`, capped at 300 chars *before* append because `SendPushover` truncates at 1024 silently — for the 2026-07-01 outage that line is the `STALE_CLIENT` error itself, which is the difference between "something broke" and a diagnosis.

**Heartbeat: the alert Streak structurally cannot produce (rosterbot-ys8).** `Streak` is reactive — an ECS task has to *stop* for the notifier to hear anything — so a job that never launches (disabled EventBridge rule, broken cron, unreachable cluster) emits no event, writes no ledger record, and produces perfect silence, which is indistinguishable from perfect health. `Overdue(recs, scheds, now)` inverts the direction: it asserts on a timer that every job has a run recent enough to be alive. Three rules are load-bearing:
- **Any status counts as "it launched"**, including `RUNNING` and `FAILED`. The question is strictly whether the job started; whether it then succeeded is `Streak`'s, and treating a failed run as a missed one would double-report every ordinary outage.
- **The lookback is bounded by *time*, not count** (`Horizon` = 2× the longest declared cadence; `ledgerReader.since` walks back to it and stops). A fixed record count is unsound here: a high-frequency job's daily record volume would push a low-frequency job's perfectly healthy run out of any small fixed window, reporting a live job as never having run.
- **Deduplication compares a token, not a key** (`MarkerKey` is per *(job, tenant)*; `AlertToken`/`NeedsAlert` compare the last-run id stored under it). A per-run key looks self-deduplicating and is not: every long outage eventually pushes its last run past the horizon, at which point the key moves and the same outage alerts again — once per horizon, forever (caught by a test, not by inspection).

The cadence table itself lives in `infra/infra.go` beside the crons it describes and reaches the Lambda through the `JOB_SCHEDULES` env var, because a tolerance restated in Go would drift from its schedule silently — surfacing only as an alert that never fires. The command string is the join key across all three sides: EventBridge passes it as the container override, `entrypoint.sh` joins argv with spaces into `run-ledger --command`, and `opsalert` matches that exact string.

**Both decisions key on `(command, user_id)`, not on the command alone (rosterbot-crq.1).** Under the per-tenant fan-out of `rosterbot-crq`, N tenants run the *same command string* into the one ledger, and a command-only key inverts both functions silently: `Streak` walks newest-first where a SUCCESS breaks the streak, so a tenant failing *every* hour grades healthy on its neighbours' successes; `Overdue` keeps the newest run per command, so "Lineup ran recently" is true for everyone the moment any one tenant runs — the exact rosterbot-ys8 blindness one level down. `Record.UserID`/`Run.UserID` (`user_id`, omitempty) carries it; **empty is an ordinary tenant value, not a wildcard**, so the entire pre-fan-out ledger keeps grading as the single tenant it describes. Consequences: which tenants `Overdue` asserts on comes from the ledger, not `Schedule` (a stdlib-only leaf can't enumerate users, so a tenant that never ran even once needs the identity store to detect it, while one that ran and stopped is always caught); the heartbeat's `MarkerKey` gains the tenant but the untagged key stays byte-identical, so existing S3 markers keep deduplicating across the deploy; and the task path's `dedupeKey` needs no tenant, since fan-out already runs one ECS task per tenant per job — it takes the tenant from the stopped run's own terminal ledger record, since the ECS event carries none.

**A `connect` exit code alone cannot say what `Streak` needs to know (rosterbot-cnn9).** `cmd/connect.go`'s routeTenant path exits 0 on a credentials/team fault specifically so this package does not page the operator, which makes that SUCCESS row indistinguishable from a real recovery — and under a Fantrax outage that alternates with tenant faults, every such row broke the failure streak and `EscalateAt` was never reached. The fix rides on the ledger record rather than the connection record `lineupapi.Run.Connect` joins in at HTTP read time, because opsalert cannot import lineupapi at all (the chromedp weight this whole leaf exists to avoid); `Record.Outcome` mirrors `lineupapi.Run.Outcome`, written via `RUN_OUTCOME_FILE` and read back by `run-ledger --outcome`. `Streak` reads a SUCCESS carrying `OutcomeTenantActionable` as evidence about nothing: None when it is the newest record (not a false Recovered, and not a silent skip either, which would re-report the older streak), and dropped from history entirely when older, so it neither breaks a failure streak nor extends one.

**Build drift: the question neither `Streak` nor `Overdue` asks (rosterbot-7p1i).** Both of those are about **runs**, and a run executing a stale image satisfies them perfectly — the ledger records a healthy SUCCEEDED job and the heartbeat sees a fresh launch, while the code doing the work is days behind main. They answer "did the job run", never "is it the right image". The gap is not hypothetical: CodeBuild's `ConcurrentBuildLimit` **throttles** an excess build rather than queueing it, and rejects it at the webhook *before a build record exists*, so a merge landing inside another build's window produces no build, no outcome, no event and nothing red anywhere. It dropped two deploys in two days (6056658, bb1cc1e); the only evidence in the entire system was an HTTP 400 in a GitHub webhook delivery log.

`opsalert.Check` compares main's HEAD against the newest commit that actually built, and `BuildDriftRule` runs it every two hours. Four properties are load-bearing:
- **The baseline is read from CodeBuild, not accumulated from the build-outcome events this same Lambda already receives.** A check derived from the event stream it is auditing cannot see that stream fail — the same reason `internal/roster`'s `CheckILStarters` joins against MLB's probables instead of asking Fantrax whether Fantrax believes a player is injured.
- **`AlertToken` is the BUILT sha, not the head sha**, and that choice is the entire dedup. The built sha is precisely the value that does *not* move while the trigger is broken — main keeps advancing, the last good build does not — so one outage records one token and every later tick recognises it. Keying on the head would alert once per merge for as long as the outage lasted. `NeedsAlert`'s middle case mirrors `Missed.NeedsAlert`: once alerted, losing sight of the baseline must not read as a fresh outage forever.
- **Blindness is never a finding.** An unreadable GitHub or CodeBuild, and a head commit that cannot be *dated*, all return "no finding" rather than an alert — a check that cries wolf on healthy deploys gets muted, which costs more than the narrow gap. `driftGrace` (30 m) exists for the same reason: a merge younger than a build legitimately has no build yet. But **an empty baseline IS a finding** — a project that has never built successfully is drifting by any definition.
- **`GITHUB_REPO`/`BUILD_PROJECT` are set by the CDK from the same literals that declare the webhook source and the project**, the `JOB_SCHEDULES` principle one rule over: a checker that restated its target's coordinates could drift from the thing it checks. IAM is two read actions scoped to the project ARN; the check never starts a build. Verify live with `DIAG_BUILD_PROJECT=… go test -tags diag -run TestDiagBuildDrift ./` in `opsnotify/`.

**The `-1` on `ConcurrentBuildLimit` is an assertion, not a value anyone wants.** The limit was set to 1 and reverted the same day (rosterbot-ill) by *deleting the line* — and **the revert never took effect**. CloudFormation does not clear a CodeBuild property you stop sending; AWS states the rule on `CfnProject` ("to unset or remove a project value via CFN, explicitly provide the attribute"). Measured 2026-08-20, six days and ~68 deploys later: the deployed template carried no `ConcurrentBuildLimit` while the live project still reported `1`. So an omitted property is not an assertion that it is unset — it is silence, and the resource keeps whatever it had. `-1` is the API's remove-the-limit sentinel (the field reads back *absent*) and the CFN schema puts no minimum on it. **Anywhere this repo "removes" a property to change behaviour, the claim is unverified until the live resource is read, not the template.**

**Alert deduplication across deliveries (rosterbot-chs).** EventBridge can deliver one event more than once and async-invoke retries on a returned error; since the verdict is a pure function of a ledger that does not move between deliveries, a repeat recomputes the identical alert and pushes it again. `opsnotify/marker.go` records sent alerts under the `opsalert/` S3 prefix (its own prefix, not `notifications/` — that one is the user-facing feed the dashboard serves). Two invariants: the order is **check → send → mark**, never claim-then-send, because a claim taken before sending must be released on failure and a failed release leaves a permanent suppression — trading a duplicate alert for a missing one; and **every marker-store failure degrades to a duplicate, never to silence**. The task path keys on the **task id alone, not id+`detail.version`** — AWS documents version for exactly this, but ECS can emit several distinct STOPPED events for one task as container state settles, and those are not duplicate deliveries, so version would let each through even though they describe one dead run. Version is written into the marker body instead, where it dates the delivery that won without weakening the key. The prefix expires on a 30-day lifecycle rule, far past EventBridge's retry horizon.

**Tenant fan-out gate (rosterbot-2twx, 2026-08-17).** `lambda/dispatch` launches a per-tenant job only for tenants whose Fantrax connection is `Usable()` (`ConnVerified`) — a pre-flight of the refusal every launched task applies anyway (`AuthorizeRun`). Without it, minting an invite immediately enrolled the tenant in the hourly fan-out (invite creates the user `active` before they've clicked the link), so every job failed at `tenantcreds` and paged the operator per (command, tenant) — a page-storm beginning the moment a tester was invited. Three rules are load-bearing: the store is **required, not optional** (`dispatch` errors on a nil `conns` — an optional gate silently admitting everyone is the fallback-is-a-valid-value shape); a connection-**read failure launches** (fail open — the task's own `AuthorizeRun` is the authority and fails loudly, where a Dynamo blip silently skipping every tenant is the invisible direction); and **`publishRoster` carries only the launchable tenants**, because the roster feeds `opsalert.Overdue`'s never-ran discovery and publishing every active tenant would re-page for exactly the never-connected testers the gate just silenced. A previously-running tenant whose connection breaks still gets one Overdue alert (their old runs age past the horizon), which is the intended "this tenant went dark" signal.

**Tenant management routes (`internal/lineupapi/tenants_admin.go`).** `POST /v1/tenants/invite` (dashboard twin of `cmd/invite.go` — same record shape, member/active/`AutoApply:false`, email attested by the minting admin), `POST /v1/tenants/{id}/recovery` (enrollment for an existing user — the recovery half of the one primitive), `POST /v1/tenants/{id}/status` (park/reactivate; self-park refused — lockout with no dashboard path back), `POST /v1/tenants/{id}/auto-apply` (operator kill switch; the self-serve twin is `/v1/me/preferences`), `POST /v1/tenants/{id}/team` (the dashboard twin of `cmd/user_set_team.go` and the only path out of connect's `no_team` refusal — it writes through `ClaimTeam`, never the profile field, since a profile-only write leaves the team unclaimed and assignable to a second tenant, and it refuses a *re*assignment because `ClaimTeam` takes the new claim without releasing the old, orphaning a team nothing on the page could explain; note `TenantSummary.TeamID` merges the connection record's team over an empty profile one, so it cannot tell an assignment from an inheritance and `tenants.js` labels the button **Set team** unconditionally rather than claiming otherwise), `DELETE /v1/tenants/{id}` (`UserStore.DeleteUser`: profile, credentials + their lookup indexes, the connection record, and the email/team uniqueness claims **released** — a delete leaving them behind would poison that email and team forever, the same trap that makes `ClaimTeam` refuse moves; the tenant's durable S3 artifacts stay as inert orphans, and self-delete is refused). Nested one level under a tenant, `GET /v1/tenants/{id}/runs` (full ledger), `GET /v1/tenants/{id}/runs/{runID}` (log tail, exit code, connect verdict — rosterbot-iymz) and `GET /v1/tenants/{id}/runs/{runID}/output` (captured stdout) are the admin drill-down (rosterbot-f0th) below the bounded per-row summary `GET /v1/tenants` carries; each resolves via `tenantViewOf(ctx, path uid)` and stamps its connect verdict with `tenantConnectRun`, never `lastConnectRun` (which keys off the caller, not the tenant in the path). All under `/v1/tenants/`, gated as a unit by the `adminOnlyRoutes` prefix — `TestTenantStatus_MemberForbidden` pins that the prefix reaches them. **`GET /v1/tenants` lists via `ListUsers`, not `ListActive`**: the two listings answer different questions, and conflating them broke one — the fan-out must skip a parked tenant, while the admin page must keep showing them, since its row is the only reactivate control there is. `TenantSummary.Passkeys` is `*int`: nil = credential store could not answer, 0 = invited but never registered — conflating them would tell the operator to re-invite someone whose account is fine. The minted token appears exactly once, in the mint response (only its hash is stored); `tenants.js` renders it as `<origin>/?token=…` with a copy box.

**Connect classifies on evidence, and a failure after the login is not a verdict on the password (rosterbot-ch0s).** Fantrax issues an `FX_RM` cookie only once it has accepted a username and password, so holding one is Fantrax's own statement that the credentials are fine. `classifyLogin` returns that cookie as a `loginProof` alongside its verdict, and `cmd/connect.go`'s failure handling has **four** routes rather than two: `routeTenant` (demote to `needs_reconnect`, tell the tenant, exit 0), `routeOperator` (status untouched, exit non-zero), `routePostAuth` — `ConnInterrupted` + `verification_interrupted`, tenant told, operator paged by the non-zero exit — and `routeInternal`, its mirror on the other side of the login: a fault on OUR side (a KMS decrypt, a DynamoDB read, the task's own KMS/DynamoDB wiring) stopped the check before Fantrax was ever asked, so it writes `ConnCheckFailed` + `check_failed` rather than `ConnInterrupted`, which would falsely claim a proven login (rosterbot-spb9); it writes onto the record it can read back, and a record it cannot read is left alone rather than overwritten blind, with the tenant told through the feed, the operator through the exit code, and the pending copy bounded at `connectInFlightWindow`. `routeFor(class)` is the single definition, because `cmd/session_ladder.go`'s `stop` is a **second live writer** of connection status and the two must not disagree; the ladder takes the same third route but leaves the status **verified**, so its next scheduled run simply retries (writing `interrupted` there would make `AuthorizeRun` refuse a tenant with nothing to fix), and reports on the console rather than the feed, since a feed entry on a path that keeps running would restate one outage ~24 times a day. `routeInternal` is unreachable from the ladder by construction — `classifyLogin` only classifies evidence from an attempted login — so `stop`'s switch groups it with `routeOperator` defensively rather than letting an unrecognised route fall into the tenant-blaming default.

Four properties are load-bearing. **The classifier branch requires a cookie AND a named post-auth failure** (`IdentityErr` or `PersistErr`), not a bare `FXRM != ""`: the fork's `LoginWithBrowser` states that "a rejected password reaches this line too" immediately before it reads the cookie jar, and nobody has measured whether `FX_RM` survives a rejection — a bare test would tell every wrong password that the password is fine and invite the unbounded retries that trigger Fantrax lockout. **Every route writes**: an earlier attempt added a non-demoting path that wrote nothing, leaving the record `ConnPending` and the dashboard at "Checking your credentials…" forever. **`ClaimTeam` splits three ways** — `ErrTeamTaken` demotes, `ErrUserConflict` is our bug and returns a hard error, anything else is a transient — because collapsing them told tenants "that team is already claimed" for a DynamoDB blip. And **all three UI surfaces handle the new status**: `settings.js`, `tenants.js` (`CONN_TONE` *and* `attentionFrom`, whose fallback for a status it does not know attributes a failing run to the operator and otherwise returns "—" — rosterbot-v1ro, so a tenant stuck at `pending` still surfaces a failing job) and `app.js`'s global banner, pinned by `TestConnectStatusReachesEveryRenderingSurface`.

`fantraxLogin` installs `FANTRAX_COOKIES` from the proven cookie before the identity call, which is **load-bearing rather than hygiene**: `auth_client.GetCookies` consults it, then the cache file, then falls back to a **full second headless login**. `ConnInterrupted` does not block resubmission the way `ConnPending` does, so `handleConnect` carries a one-minute `connectInterruptedCooldown` — the same minute the tenant-facing copy promises. **Not yet closed:** the fork discards its cookies on all three post-persistence error returns (`os.Create`, `json.Marshal`, `f.Write`), so `PersistErr` cannot be non-nil in production and the filed 2026-08-17 incident still classifies as a challenge/timeout; `IdentityErr` (a Fantrax 5xx inside `auth_client.NewClient`) is live today.

**Two per-tenant data-scope rules from the same audit.** `GetPendingTrades` is the one cached Fantrax response that depends on WHO is logged in (the offer list visible to the authenticated team), so its key now carries the team (`fantrax-pending-trades-<leagueID>-<teamID>`) unlike the league-wide caches beside it — the old league-scoped key served tenant A's offer view to tenant B through the shared `cache/` prefix, and B's `NoBackfill` offer log recorded a world that never existed (`TestGetPendingTrades_CacheIsScopedToTheCredentialTeam`). And the **views report publishes only into the operator's partition** (`viewsReportBelongsHere`, gated on the task-def's `OPERATOR_USER_ID` env var): model and gap are per-tenant data, views is the same deployment-wide CloudFront readership digest (visitor IPs included) on every run, and the fan-out was publishing it to every tester's Views tab. The gate fails closed — tenant set, operator env missing → skip — because the operator missing their views report surfaces as a soft-fail warning while a member receiving it surfaces nowhere.

**`internal/roster`** — `CheckRoster` scans the full roster for slot mismatches (healthy players in IL, called-up players in Minors, injured/minor-leaguers in active slots). Suppresses alerts when IL/Minors slots are full. Separate from prospect report — this is about current roster hygiene.

**Its four alert types were hitter-only until rosterbot-2hc, and the reason is worth keeping** — `CheckRoster` is fed by `GetFullHitterRoster`, which filtered `if !isHitter(rp) { continue }`. The doc comment said "scans the full roster" and `SlotCounts` genuinely covered all players, so the gap read as covered; only the *player list* was filtered. The method is now `GetFullRoster` with no filter, and the flattening is split into the pure `collectFullRoster` so section coverage is testable without an authenticated client.

**`CheckILStarters` is the cross-source companion, and it exists because the same-source check structurally cannot fire.** `HealthyInIL` asks Fantrax whether a player in an IL slot is injured — but `Player.IsInjured` is *only* `models.HasInjury(rp.Icons)`, Fantrax's own editorial icon, which lags real activations. So while a club has activated a pitcher and named him a probable starter, Fantrax still flags him injured and the existing alert stays silent through exactly the window where the start is still recoverable. `CheckILStarters(players, probables, date)` joins IL-slotted players against MLB statsapi's probable starters — an independent source — via **`playername.MatchProbable`**, the one shared probable-starter classification (NotProbable / ConfirmedStarter / TeamMismatch) that the pitcher optimizer and the GS-budget forecast also call, so the three joins cannot drift (they used to be three hand-copies, two pinned as "byte-identical" by prose alone and the third unremarked). Plain `==` on the club is safe inside it since both sides already pass through `teams.Normalize`, so the `AZ`/`ARI` class of mismatch cannot arise. A name that hits but whose club disagrees is returned separately rather than dropped, because a lagging trade on either side would otherwise turn into a silent non-alert.

**The cost asymmetry is what makes this alert-worthy rather than optimizer work**: `fetchPitcherRosterForPeriod` reads only `ActiveRoster + ReserveRoster`, so an IL pitcher never reaches the optimizer at all. The start is lost outright, not mis-slotted, and there is no downstream recovery.

`internal/lineuprun`'s `reportILStarts` owns delivery: it checks today and today+`ilStartLookahead` (1, so tomorrow — today is still recoverable before lock, tomorrow buys a full day), prints, and pushes each finding once. Dedup is one marker per **(player, start date)** under `layout.ILStarts` — the date is in the key on purpose, since a pitcher stranded across two separate starts is two things worth hearing about where a player-only key would alert once and then go quiet for the season. Order is **check → send → mark** (rosterbot-chs); a marker read or write failure degrades to a duplicate, never to silence, and `--dry-run` skips both the send and the mark (marking on a dry run would mute a later real alert that never went out). `Notify` here returns an `error`, unlike `Emit`'s void seam, because check→send→mark is only sound if "sent" is actually known. Every failure is soft — this runs inside the hourly lineup job and a statsapi hiccup must not take it down.

**The `il-start check:` coverage line prints unconditionally, including the all-zero case**, on the same reasoning as `mlb recency coverage:`. This check's normal output is silence, so without the input counts a genuinely clean roster and a structurally blind check are indistinguishable — the failure this repo has hit before (rosterbot-hx5, rosterbot-6tw). `IL=0` means nothing to find; `probables=0` means the feed is empty; those are different problems and only the line separates them. Measured live: substantial IL and probable-starter counts on both sides with zero matches — a real, not a blind, zero.

**`internal/schedule`** — hits `statsapi.mlb.com` for game schedule and probable pitchers. `TeamsPlayingOn` returns a `map[string]bool` of playing team abbreviations. `ProbableStarters` returns normalized pitcher name → team abbreviation. Both URLs are `var` (not `const`) to allow test overriding.

**`internal/optimizer`** — pure functions, no I/O. Two parallel optimizers:
- **Hitters** (`OptimizeLineup`): backtracking with pruning to find globally optimal slot assignment maximizing total expected points. Players are valued through `projections.PointsPerGame` — the one shared assert-and-fallback (blended `PtsPerGameSource` value when the source provides it, else derived from the season projection); the pitcher optimizer, `MatchupAdjustedSource` and `lineuprun`'s GS-forecast pricing use the same accessor pair, so the fallback semantics cannot drift across the four sites they used to be hand-copied at. `EligibleForSlot` in `fantrax/client.go` handles UT (accepts any hitter) and INF (accepts 1B, 2B, 3B, SS — not C).
- **Pitchers** (`OptimizePitcherLineup`): sorts by hasGame → expectedPts → ID, then assigns to slots. Uses probable starter data to determine if SPs start; when no probable data is available (future dates), SPs default to "has game" if their team plays. Accepts an optional `*GSBudget` for weekly game-start limit awareness.

**Scoring model** — this league scores: `1B`, `2B`, `3B`, `HR`, `RBI`, `R`, `BB`, `SB`, `CS`, `HBP`, `SO`, `GIDP`, `XBH`, `TB`, `CYC`. The stat→points algebra lives in **`internal/scoring`** (the single source): `ApplyHitter`/`ApplyPitcher` take a neutral `HitterLine`/`PitcherLine` of raw counts, derive `1B = H - 2B - 3B - HR` (floored at 0), `XBH = 2B + 3B + HR`, `TB = 1B + 2×2B + 3×3B + 4×HR`, and apply the league weights. The package imports nothing else (so both `fantrax` and `projections` can depend on it without a cycle); `fantrax.ScoringWeights` is a type alias for `scoring.Weights`. Callers adapt their source to a stat line: `projections.ExpectedPtsFromProj`/`PitcherExpectedPtsFromProj` build a line from a projection and divide by games (scoring is linear, so per-game = total/G); the `mlb_backfill` game-log scorers build a line and don't divide (single game). `optimizer` and `waivers` consume these rather than re-implementing the math.

**GS budget** — weekly game-start limit awareness (`GS_TRACKING_ENABLED` env var, false = disabled). When enabled, the pitcher optimizer resolves today's scoring period and fetches its real GS max via `GetGSLimits`, gating SP starts to avoid exhausting the weekly GS allocation on low-value starters while better aces pitch later in the matchup week. A live-fetch error sends a Pushover alert (`PUSHOVER_USER_KEY`) and disables the gate for that run rather than falling back to a stale static number; no configured max just disables the gate silently (nothing to track).

**The gate is two-sided, and the two bounds fail differently** (rosterbot-dpm). `GetGSLimits` always returned both, and the call site discarded the minimum with `_`, so the floor was not representable downstream even in principle — the only component that knew it existed was `gs-check`, which reports it the day *after* the period closes, when the penalty is already incurred. `GSBudget.Floor` now carries it and `NeedForFloor()` is the floor-side counterpart to `Remaining()`. A missing **maximum** still disables the gate (nothing to gate against); a missing **minimum** is an ordinary league configuration and must not, so zero is a value here rather than a failure.

**Protection cannot create a start, so the floor also gets an ALERT while the week is still open** (`internal/lineuprun/gs_floor.go`, rosterbot-cs9p). `gs-check` raises `ViolationMin` off `FindJustEndedPeriod` — strictly the morning after the period closed, when the penalty is already taken — and protection inside the gate only stops the ceiling side making a short week worse. The one lever that actually closes a day is a roster claim, and a claim needs lead time. `reportGSFloor` therefore fires from the hourly `optimize` run, reading the `*GSBudget` `ComputeGSBudget` just built and fetching nothing of its own.

Three properties carry it. **Supply is credited from TOMORROW onward, never from today**: today's starts enter `GSBudget.Used` the moment Fantrax settles them and nothing at this seam separates a settled start from a pending one — the exact ambiguity that made the old live-roster count diverge every evening (rosterbot-cg8l). `GSBudget.TodayUnsettled` (rosterbot-ogtq) now credits today's confirmed-but-unlocked probables against `Need` inside `evaluateGSFloor` for exactly that seam — restricted to pitchers actually occupying an active P slot and capped at the slot count, since Used only ever reflects active-slot deltas — so only the estimated-for-today subset and the brief locked-but-not-yet-settled window remain uncredited. **The firing window is bounded at BOTH ends, and the upper bound is the one that was measured rather than reasoned.** `gsFloorMinDaysLeft` (2) keeps the alert actionable, since an alert on the final evening names a problem no claim can still fix. `gsFloorMaxDaysLeft` (4) keeps it out of the early week, and exists because the first version fired on a healthy one: excluding today is right, and before `TodayUnsettled` it left the projection missing exactly today's starts, worst at week start where `Need` was simultaneously maximal because `Used` was still zero. Measured on the real Period 21 snapshots, Monday reads confirmed 3 + estimated 7.4 → **8.92 credited against a Need of 10**, on the week the bead designates as must-not-fire; the Lineup cron runs hourly 14:00–03:00 UTC, so `Used` stays 0 through every daytime run and the false alert was near certain every Monday — spending, under per-period dedup, the only alert that week could raise. That 8.92/10 arithmetic predates `TodayUnsettled` and was not re-measured against the corrected `Need` formula, so **4 may now be more conservative than the corrected projection needs** — it has not been re-swept. **The projection itself is not wrong**: `Used` + undiscounted supply reads 13.40 on both Monday and Tuesday, matching the audit's own ~13.4. Only its split into banked and still-to-come is uninformative that early, so the guard refuses to evaluate rather than reweighting anything — the choice `periodIsVolatile` makes for a period still settling. 4 rather than 5 because Tuesday reads −0.12, inside firing noise, where Wednesday reads −2.36. Inside the window the rule needs no urgency coefficient: as probables are announced the estimate collapses into confirmations and a day on which none of our arms was named stops contributing at all. That same collapse is what makes the empty days *nameable* — a day cannot be known empty in advance (on both zero-start days of period 20 our clubs played and other pitchers started), so the alert becomes possible at exactly the moment it becomes specific. The cost is deliberate: a week already doomed on Monday is not announced until Wednesday, because a Monday alert that is wrong most weeks mutes the channel.

**`gsFloorEstimateCredit` (0.8) is an UNMEASURED PRIOR, the same standing as `certaintyMargin`.** It is bracketed rather than fitted: Period 21 finished roughly +3 clear of its minimum and must not fire, which floors the credit (over-discounting makes a healthy week look short, and an alert that fires on a healthy week gets muted); Period 20 finished exactly ON its floor at +0.2 and must fire, which caps it (crediting the estimate in full makes those two weeks indistinguishable). Confirmed starts are deliberately **not** discounted — a named club is as certain as today, and discounting them would flatten the very signal the trigger reads. The sweep needs `gs_floor`/`gs_forecast` in the projection snapshots, which only start in Period 21, so the first gradeable week is 2026-08-31 (rosterbot-1tia).

Dedup is one marker per **(season, weekly period)** under `layout.GSFloorAlerts` (`alerts/gs-floor/`, PerTenant like `ILStarts` — the minimum is a per-team obligation, so two short tenants are two problems). Order is **check → send → mark**, a marker failure degrades to a duplicate and never to silence, `--dry-run` skips both, and nil markers alert every run rather than going quiet. The season is in the key because weekly period numbers restart each year (the correction rosterbot-qoa made to the past-period cache keys). The `gs floor check:` coverage line prints **unconditionally**, including on a comfortable week, for the same reason as `il-start check:` — this check's normal output is silence, so without the inputs a healthy week and a structurally blind trigger read identically, which is how the forecast reported 0.0 all season (rosterbot-1jvj).

**Promotion, as the bead originally specified it, is not implementable, and that is a measurement not an opinion.** MLB names the probables, so nothing the optimizer does can manufacture a start: on both zero-start days of period 20 our clubs played and *other* pitchers took the ball. The only real lever is refusing to spend the ceiling gate against a week already short, so `applyGSGate` computes a `floorReserve` and tops `keepToday` back up in the same value order the cut used, reporting the rescued starts as `GSGateReport.Protected`. Two properties are load-bearing. **`floorReserve` subtracts CONFIRMED future starts only, never `Estimated`** — staking the floor on rotation math's ~1-in-5 claim over a club that has named nobody is precisely how a floor-bound week ends up under the floor, and weekly GS is use-it-or-lose-it so the unspent probability is burned rather than banked. And **the clamp to `remaining` makes the ceiling constraint a consequence rather than an assertion**: the cut placed at most `remaining` entries, the top-up raises the count to at most `floorReserve ≤ remaining`, so protection provably cannot push the week past `Limit`. Note the practical consequence for a roster that habitually finishes at the minimum: the floor dominates the ceiling for most of most weeks and the gate will rarely suppress, which is the correct outcome for such a roster and self-corrects as `Used` climbs and `NeedForFloor()` falls to zero.
- **Matchup week boundaries** derived from `GetAllMatchups()`: consecutive daily scoring periods where the team faces the same opponent form a matchup week. Computed in `fantrax/matchup_weeks.go` via `MatchupWeekBounds`.
- **Used-GS counting walks Fantrax's own per-day snapshots, today included** (rosterbot-cg8l). `ComputeGSBudget` gets the whole figure from one `GetTeamGS` call over `weekStart..today` — the same active-slot YTD-delta walk `gs-check` uses league-wide — so a start is counted from that day's frozen roster state, not from the roster as it looks now. Today used to be counted separately by `countTodayStarts`, off the **live** roster (active + team locked + today's probable). That answers "is he active NOW" when the question is "did he start TODAY", and the two diverge every evening: once a pitcher's game ends a later hourly run rotates him back to Reserve for tomorrow and his already-spent start silently drops out. Production on 2026-08-19 read 1/12 through the afternoon, peaked at the correct 5/12 at 00:00Z, then fell to 3/12 an hour later and stayed there; the next morning's walk over the same days reported 5. Measured live against Fantrax, the walk recovers exactly the four Wednesday starts the live-roster count lost (`DIAG_GS_TODAY=2026-08-19 DIAG_GS_WEEK_START=2026-08-17 go test -tags diag -run TestDiagGSWalkIncludesToday ./internal/fantrax/`). Two consequences: **`gsPeriodWalk`/`GetTeamGS` now cap the walk at today rather than yesterday**, with the caller's `sp.EndDate` deciding how far to go — `gs-check` grades a period that closed yesterday, so the cap never binds there — and a period that **starts today** now walks that day instead of returning nil, which is what makes a start on the week's opening day visible before the following morning. It also removed a silent failure mode: a statsapi outage used to zero today's contribution to `Used` (the old count needed `LockedTeams` **and** `ProbableStarters`), where the walk does not consult the schedule at all. The error direction was over-permissive — the gate believed 9 starts remained when 7 did — benign at the GS floor and inverting against the max. This only became load-bearing once rosterbot-1jvj revived the forecast; before that the gate never suppressed anything, so a wrong used-count could not bite.
- **Future demand forecasting is hybrid PER CLUB, not per day** (rosterbot-1jvj). Each rostered SP lands in exactly one bucket for a given future day: named as its club's probable → a confirmed start counted exactly; club plays but has named nobody yet → rotation-math demand (`SPs / 5`); club plays and named someone else → nothing, the day is settled for us; club idle → nothing. **The slot cap applies to starts, i.e. after the division, not to the pitcher count before it** — capping first mixes units and understates every day where more rostered SPs have a game than there are pitcher slots (rosterbot-abd) — and it bounds the day's **combined** confirmed + estimated total, since confirmed starts have already claimed slots the estimate may not re-spend.
- **The grain is the whole correctness story, and getting it wrong made the fallback dead code for the entire season.** Until rosterbot-1jvj the two regimes were selected per DAY on `len(probs) > 0` — the size of the **league-wide** probables map. MLB trickles probables out up to a week ahead, so that map is essentially never empty on a future day: measured against statsapi on 2026-08-19, every remaining day of the matchup week already carried some announced probables against 18–30 clubs playing. **A single announcement for any club, ours or not, zeroed the entire day**, and the estimate branch only ever ran on a day the league had announced literally nothing — measured end to end on the real roster, `FutureDemand()` read **0.00** where the per-club fix reads **5.80**. The damage was not confined to the display: `applyGSGate` ranks today's starters against today + future demand, so with future demand structurally zero it saw no competition for the remaining budget and **never suppressed anything** — which is the mechanism behind the chronic `0 start(s) suppressed … 0.0 gross projected pts` line that appears in every backtest and had been read as normal. Which clubs have announced is derived from the probables map's **values** (a club appears there iff one of its games has a non-null `probablePitcher`), which is per-club information from the same payload; `len(probs)` is a league-wide count and says nothing about any particular club.
- **`FutureDemand()` and `applyGSGate` must both SUM a day's two regimes, never prefer one.** `ConfirmedStarters` covers the clubs that have named a starter and `Estimated` covers the clubs that have not, so they describe **disjoint** sets of our pitchers; the old either/or read discarded the estimate on every partially-announced day, which is most of them. The two accumulations sit in different packages and must stay in step — the display reports `FutureDemand()` while the gate re-derives the same total inline.
- **A schedule-seam failure is FATAL to the gate, not a degraded forecast.** `buildGSForecast` returns an error; both `TeamsPlayingOn` and `ProbableStarters` used to discard theirs, which made an upstream outage indistinguishable from a genuinely quiet week. The tempting middle ground — keep the partial forecast, since an under-count only makes the gate suppress *less* — does not survive the probables case: losing that map drops confirmed starts (worth 1.0 each) while promoting every already-settled club into the estimate (worth 0.2 each), so the error runs in an **unknown direction**. `ComputeGSBudget`'s standing rule exists precisely so nobody adjudicates that per failure mode: a wrong budget silently mis-shapes pitcher usage for the rest of the week, and no budget does not. The forecast is simply the last step of the same cascade. It raises **no Pushover**, unlike the GS-limit fetch — a statsapi blip is transient and self-heals on the next hourly run, where a Fantrax config read that stops working does not. Cost is bounded by cadence rather than by severity: one blip costs one run's gate.
- **The loop aborts on the first unreadable day** (`TestBuildGSForecast_StopsAtTheFirstUnreadableDay`): the week's total is already disqualified, so the remaining days teach nothing and there is no reason to spend more round-trips on a seam that just failed.
- **This is safe only because a gameless day is not an error.** Verified live: statsapi returns HTTP 200 with an empty `dates` array for an off-day, so `TeamsPlayingOn` yields an empty map and a nil error. Were absence encoded as an error, making the seam fatal would disable the gate on every off-day and across the All-Star break — the exact window where period math is already hardest.
- The live harness that reproduced and verified this is `internal/lineuprun/diag_gsforecast_test.go` (build-tagged `diag`, `DIAG_SP_TEAMS=... DIAG_WEEK_END=... go test -tags diag -run TestDiagGSForecast`), which takes the roster as club abbreviations so it needs no credentials or chromedp login.
- **Value-ranked gate** (`optimizer/gs_budget.go`, `applyGSGate`): when remaining budget can't cover every planned start (today + future confirmed + future estimated), pools all of them into one ranking by expected points and keeps only the top `remaining` by value — it does not split the budget proportionally by day/count. Future days without announced probables contribute `ceil(Estimated)` placeholder entries valued at the roster-wide mean SP projection (a real projection, not a scrub), **priced as a marginal-value ladder**: the k-th such entry is worth `placeholder × min(max(Estimated-(k-1), 0), 1)`, i.e. full value while whole units of expected demand remain and the leftover fraction after that. So `Estimated = 1.4` emits one entry at full placeholder and one at 0.4× it. **The weight belongs in the price precisely because the cut spends a whole slot** — the gate's question is "hold this slot or spend it today?", and holding is worth `placeholder × min(E,1)` in expectation against a certain value today. This reads like a units error (every other entry is points-per-start; this one is points × probability) and was filed as one, but pricing the tail at full value would bench a certain start to hold a slot for a merely-likely future one — and since weekly GS is use-it-or-lose-it, the unspent probability is burned, not banked (**rosterbot-idn**, closed as not-a-bug; `gs_budget_test.go` pins the ladder). Ties prefer today's starters (a certain start) over future ones, then break on player ID. **`certaintyMargin = 0.10`** extends that tie preference to near-ties: an *estimated* future entry must beat today's value by more than 10% to outrank it (confirmed future starts are as certain as today's and are excluded). It prices `P(the estimated start never materializes)`, **not** projection error — SP projection MAE is large but symmetric, and haircutting an unbiased estimate biases the ranking rather than de-risking it. The 0.10 itself is an unmeasured prior, not a fitted value — and it **cannot be swept from archived data**, because `DayForecast` was never persisted (the GS walk records what happened, not what was believed, and the probables cache merges in place rather than keeping a time series). `Snapshot.GSForecast` now archives the gate's forward view per day so the sweep becomes possible going forward; it can only be accumulated, never backfilled, and any pre-2026-08-19 value would read ≈0 anyway since the rotation-math branch was unreachable until rosterbot-1jvj. Starters that don't make the cut have `IsStarter` flipped to false, applying the existing `NonStarterSPDiscount` (0.05x). Uses `eps = 1e-9` for float comparison consistency. Locked players are exempt from suppression (their GS is already decided one way or the other).
- The gate only applies to today's optimization (the daily GHA run). Future dates in `--dates` ranges are optimized without the gate since each day gets its own run.
- The `--matchup` flag on the optimize command resolves to all remaining days in the current matchup period (from today through the matchup week end).

**`internal/lineuprun`** — the shared orchestration engine behind both the `optimize` and `shadow` CLI commands: fetches rosters/projections, runs the hitter and pitcher optimizers per date (the parallel `errgroup` pass over `cfg.Dates`), archives projection snapshots, publishes the read-only lineup API JSON, and prints + applies the resulting moves. `Run(ft, cfg, opts)` takes an explicit `Options` struct (projection system, `--dates`/`--matchup` resolution flags, pipeline-detail toggle, snapshot behavior, cache/verbosity) — there is no package-level mutable state shared between callers. `cmd/optimize.go` (a single real/dry-run pass) and `cmd/shadow.go` (one dry-run capture per RoS system, looped) are both thin cobra adapters that parse flags, call `initApp`, build an `Options` value, and call `Run`. `Options.SnapshotRoot` is the exact directory a run's projection snapshots are written into — always set explicitly by the caller (`optimize` passes the flat `.backtest/snapshots/` path; `shadow` passes a per-system partition each loop iteration) — and `Options.ForceSnapshot` is a separate explicit boolean (`shadow` sets it so a capture run always writes regardless of dry-run). This replaced a former package-level `captureSystemRoot` var in `cmd/optimize.go` that `cmd/shadow.go` mutated to redirect snapshot output (its emptiness used to double as both "not in shadow mode" and "use the default directory"), plus a parallel `lastProjectionLoadResult` var that let `shadow` observe per-system projection-data availability only because `runOptimize`'s signature was fixed by cobra — `Run` returns a `Result{HittersNoData, PitchersNoData}` instead (**rosterbot-zbi**).

**Named phases (rosterbot-6rv, complete).** `Run` is a composition of phases, each owning an interface narrow enough to test without a Fantrax client, in pipeline order: `ResolveDates` (`dates.go`), `LoadInputs` (`inputs.go` — the six roster/slot/scoring fetches plus period lookups, returning one typed `Inputs`), `BlendSources` (`blend.go`), `ComputeGSBudget` (`gsbudget.go`), `OptimizeDates` (`optimize_dates.go` — the parallel per-date pass), `Emit` (`emit.go` — snapshot, publish, print, apply, notify). `Run` shrank from 1201 lines to 309. Two conventions hold across the phases and are worth preserving:
- **Side effects are returned as decisions, not performed.** `ComputeGSBudget` returns a `GSAlert` for the caller to send rather than calling Pushover itself; `BlendSources` and `ComputeGSBudget` return `Logs []string` rather than writing to the progress display. That is what lets every failure branch be asserted without credentials or an HTTP server. `LoadInputs` is the deliberate exception — it takes a three-method `inputsProgress` because its phase completion has to land *between* two groups of its own log lines.
- **Failure policy is stated once per phase.** `LoadInputs`: the six roster/slot/scoring reads are fatal, the two period lookups are soft and ride along on `Inputs`. `ComputeGSBudget`: every failure disables the gate and none falls back to a stale limit; the live-limit fetch failure additionally requests a Pushover. `BlendSources`: each role falls back to its base source independently.

**`Emit` gates the live write on a type, not on statement order (rosterbot-k0n).** `Emit` is the only phase that mutates remote state, and its one load-bearing ordering constraint — the zero-gain delta check must precede `ApplyLineup` — is expressed in the signature: `applyLineupFor` requires an `applyAuthorization`, obtainable only via `datePlan.authorize()`, which refuses any disposition but `movesWorthApplying`. The zero value is inert and `applyLineupFor` refuses a nil plan; `TestApplyLineupFor_RefusesAnUnauthorizedApply` pins that. **Why the zero-gain guard exists at all:** the optimizer can construct cosmetic swaps among equally-valued bench players, and Fantrax rejects a payload *atomically* if any player in it is per-player-locked — so submitting a worthless swap can drop genuinely valuable moves alongside it. `Emit` also takes its Pushover sender as an injected `Notify func(string)`, so the apply-path tests never reach the network.

**The guard has exactly one exception, and it is not a softening of it (rosterbot-uhq).** A move set correcting an ILLEGAL current assignment — a player occupying a slot his positions no longer permit — is slot-only by construction, so nobody's active membership changes and rosterbot-6i4's delta values it at exactly zero; unconditional suppression therefore dropped it on every hourly run forever, and the lineup never converged. Both optimizers now publish `IneligibleBefore` (active players whose current slot their positions do not permit, via the shared `ineligibleActive` with each side's own predicate), `planDate` promotes such a set to `movesWorthApplying` marked `Required`, and `emitDate` prints a `Required slot fix:` line naming the players. A player with **no position data is never listed**: absent evidence is not evidence of ineligibility, and the alternative fails catastrophically — if the roster feed ever stopped populating `Positions`, every active player would look ineligible at once and every zero-gain shuffle would be submitted, reinstating precisely the churn rosterbot-6i4 removed. A cosmetic shuffle among legally assigned players is still suppressed on the existing path.

Snapshot archival and lineup publication read the same already-computed results and write to unrelated destinations — **verified independent**, despite the ordering the original issue assumed; neither blocks the other on failure. They precede the apply loop because they describe what the optimizer decided and should be durable whether or not the apply lands.

**The published lineup carries HKB age/value, and every part of that path is optional by construction.** `LoadHKBMeta` (`hkbmeta.go`) maps `hkb.GetPlayers` into `map[string]lineupapi.Dynasty` keyed by `playername.Normalize` — the same join key `claims`/`transactions`/`teamvalue` use, and the one `lineupapi.Build` looks up by via `projections.NormalizeName`. Three properties hold it together. It is **gated on the same condition `publishToday` applies** (`Publisher != nil && (!DryRun || PublishLineupFlag)`), so a shadow run or an ordinary dry-run never pays for a fetch it would discard. Its failure is **soft** — a scrape outage logs a warning and publishes without the columns, because this is decoration on a lineup the optimizer already decided, the opposite of `LoadInputs`' six fatal roster reads. And `Player.Age`/`Player.HKBValue` are **`omitempty`, with zero meaning "HKB has no row"** for both: a client that read 0 as an age would be reading a miss as a measurement, and the miss is routine (a call-up too new for HKB's rankings — the known-unfixable gap `internal/playername` documents). The keying is split into the pure `hkbMeta` and tested through the real lookup side rather than by comparing key strings, since a join key that stops matching is silent — the whole column empties while every player still renders.

**`LoadInputs` fetches concurrently.** The eight reads run in one `errgroup`. Log lines and the phase completion are emitted *after* the group joins, in the original fixed order, and fatal errors are checked in that same order — so neither terminal output nor the error an operator sees depends on which response lands first. This is also why `fantrax.Client.getLeagueInfo` is mutex-guarded: four of these six fetches share that memo.

**Rendering takes an `io.Writer`.** `Options.Out` (nil → `os.Stdout`) carries through `renderDateResult` and every print site in `Run`; `cmd` supplies `os.Stdout`. The board's ~280 lines of positional box-drawing are golden-tested against `internal/lineuprun/testdata/*.golden` — regenerate with `go test ./internal/lineuprun/ -run TestRenderDateResult -update` and **read the diff, it is the review**. Column widths come from `displayWidth`, which measures each rune's East Asian Width (`golang.org/x/text/width`): **Wide/Fullwidth count two columns, Ambiguous counts one**. Ambiguous-as-one is the load-bearing half — the board's box-drawing and marker glyphs (`─ ═ ║ ╔ · ★`) are all Ambiguous and must stay single-width. Codepoint range is not a usable proxy for this and the earlier "BMP ⇒ single-width" rule mis-measured `❌` (U+274C, BMP but Wide), shifting the `│` separator one cell right on every real-life-benched hitter's row (rosterbot-h9q).

**Verifying a change here.** `Run`'s composition is covered hermetically: the five dependencies it used to construct inline (schedule client, the two FanGraphs loaders, handedness, HKB meta) are nil-defaulting `Options` fields resolved once by `withDefaults` (`deps.go`), and `TestRun_SecondRunAppliesNothing` (`run_test.go`) drives every phase through `Run` twice against an in-memory stack — the second pass must apply nothing, which is the Idempotency rule as a 0.4s unit test. `TestOptionsWithDefaults` pins each nil default to the production implementation **by function identity**, so a wrapper that could drift fails the test. In tests populate ALL FIVE fields via a `withFakeDeps`-style helper — a forgotten field silently reaches the real network. The binary-diff ritual remains the check for changes that alter **live behavior** (valuation, rendering, schedule interpretation) rather than wiring: build a binary from the last good commit into the scratchpad and diff `--dry-run` output for `--pipeline`, `--matchup` and an explicit `--dates`. Two gotchas that have produced a false regression: use **identical** stream redirection for both binaries (`2>&1` on both), and run them **back-to-back** — live projections and probables drift within the hour and look exactly like a refactor bug.

**`internal/progress`** — live run-progress recording, layered on top of the existing terminal progress bar (`Progress.Start`/`Done`/`Warn`). `Recorder` is a nil-safe package-level hook (mirrors `jobwire`'s `OutputRecorder` pattern): every phase transition also builds a `Snapshot` (`{phase, pct, phases:[{name,state}], status:"running", updated_at}`, ordered per `PipelinePhases`/`phaseWeight`) and hands it to `Recorder` if one is installed. `cmd/progress.go`'s `installProgressRecorder()` wires it from `RUN_ID`, writing to `runs/<id>/progress.json` — S3 via `internal/lineupapi/s3lineup.NewProgress` (`STATE_BUCKET` set) or locally via `lineupapi.NewFileProgressStore(".lineup/progress")` — and is a best-effort no-op if `RUN_ID` is unset or the store errors. `internal/lineupapi`'s `GET /v1/runs/{id}/progress` route (`ProgressStore.GetProgress`) serves that snapshot, `404` when absent. **Run status stays ledger-owned** — `progress.json` only adds phase detail on top of the `runledger/`-backed `GET /v1/runs`/`GET /v1/runs/{id}` status, never replaces it. Only `optimize` calls into `internal/progress` today (it's wired through `internal/lineuprun`'s pipeline phases); the other allowlisted jobs emit no progress file, so the dashboard SPA's live hero (`web/dashboard/live.js`) falls back to an indeterminate bar for them on the `404`. No new IAM: writes ride the existing `runs/` S3 prefix the run ledger and per-run output already use.

## Idempotency

The optimizer must produce identical output given the same inputs. Key invariants:
- **Stable sort**: player ranking uses player ID as tiebreaker (`scored[i].Player.ID < scored[j].Player.ID`) so equal-scoring players always appear in the same order.
- **Epsilon comparison**: the backtracking optimizer uses `eps = 1e-9` for floating-point comparison to avoid flip-flopping between equivalent assignments.
- **Minimal changes**: when two assignments produce the same total points (within epsilon), the optimizer prefers the one with fewer roster moves (`changes < bestChanges`).
- **Period-specific roster**: for future dates, the optimizer fetches the roster for that period (`GetHitterRosterForPeriod`) so it sees already-applied lineups. A second run with the same inputs produces "No changes needed".
- **Verification**: after any optimizer change, run the command twice with the same inputs and confirm the second run shows "No changes needed" for all dates.
